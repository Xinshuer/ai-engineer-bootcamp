@@ concept
title: SELECT、AS、LIMIT、DISTINCT
--- body
一条查询从 `SELECT` 开始：**要哪些列**，`FROM` **哪张表**。

- 列名之间用逗号隔开；`AS` 给结果列起个名字（别名）
- 列可以是算出来的：`prompt_tokens + completion_tokens AS total_tokens`，就像 Python 的 `r["prompt_tokens"] + r["completion_tokens"]`
- `LIMIT 5`：最多返回 5 行
- `SELECT DISTINCT model`：去掉重复的行，像第 8 天的 `set`。写两列就是去掉重复的「组合」
- `SELECT *` 取全部列，只在探索数据时用；正式的查询把要的列写清楚（第 25 天会看到，在 BigQuery 里 `SELECT *` 还会多花钱）

SQL 的关键字不分大小写，习惯上写成大写；结尾的分号可写可不写。
--- code
SELECT id,
       clause_id,
       prompt_tokens + completion_tokens AS total_tokens,
       latency_ms / 1000.0 AS latency_s
FROM reviews
LIMIT 5;
-- 再试试这一条（把上面整条换掉）：SELECT DISTINCT model, prompt_version FROM reviews;

@@ concept
title: WHERE：挑出需要的行
--- body
`WHERE` 后面写条件，只留下条件**成立**的行，相当于列表推导式里的 `if`：

- 比较：`=`（只有一个等号）、`<>`（不等于，`!=` 也行）、`<`、`>=`
- 组合：`AND`、`OR`、`NOT`。**`AND` 比 `OR` 先算**，两个混着用时一定加括号
- `topic IN ('payment', 'termination')`：等于其中任何一个
- `pages BETWEEN 5 AND 12`：包括两头的 5 和 12
- `heading LIKE '%Renewal%'`：`%` 代表任意多个字符，`_` 代表一个字符
- 文字用**单引号**。双引号在 Postgres 里表示列名，别混用

方言差别：SQLite 的 `LIKE` 不分英文大小写，Postgres 和 BigQuery 的 `LIKE` 分（Postgres 另有 `ILIKE`）。这个库里的时间是 `'2026-09-05 13:17:04'` 这样的文字，文字比较正好就是按时间先后。
--- code
SELECT id, contract_id, clause_id, heading, risk
FROM reviews
WHERE (topic = 'payment' OR topic = 'termination')
  AND risk <> 'low';

@@ concept
title: NULL：「不知道」
--- body
审查失败的两行（`id` 1047 和 1061），`verdict`、`risk`、`rule_ids` 都是 **NULL**：不是空字符串，也不是 0，而是「没有值 / 不知道」。

- 任何值和 NULL 比较，结果还是「不知道」，而 WHERE 只留下**成立**的行。所以 `verdict = NULL` 永远一行也找不到，要写 `verdict IS NULL` 或 `IS NOT NULL`
- 同样，`verdict <> 'accept'` 也**不会**返回失败的那两行；`NOT IN (...)` 一样
- `COALESCE(verdict, 'failed')` 返回第一个不是 NULL 的值，用来给默认值。SQLite 和 BigQuery 还有 `IFNULL`，Postgres 没有；`COALESCE` 到处都能用

Python 里 `None == None` 是 True，SQL 里 `NULL = NULL` 却不成立。这是面试最爱问的一点。
--- code
SELECT id,
       clause_id,
       verdict,
       COALESCE(verdict, 'failed') AS verdict_or_failed,
       error
FROM reviews
WHERE verdict IS NULL;

@@ concept
title: ORDER BY：排序和前 N 名
--- body
- `ORDER BY cost_usd DESC`：从大到小；不写或写 `ASC` 是从小到大
- 多列：`ORDER BY contract_id, cost_usd DESC`：先按第一列排，第一列一样的再按第二列
- 前 N 名 = `ORDER BY ... LIMIT N`。**没写 ORDER BY 的结果，顺序没有任何保证**，不要依赖它
- NULL 排在哪头，各个数据库不一样（SQLite 和 BigQuery 从小到大时 NULL 在最前，Postgres 在最后）

经典陷阱：`clause_id` 是**文字**，文字一个字符一个字符地比，`'10.1' < '8.1'`（因为 `'1' < '8'`），和 Python 的 `sorted(["8.1", "10.1"])` 一样。按数字排要先转成数字：`CAST(clause_id AS REAL)` 把 `'10.1'` 变成 10.1。这个办法只在小数点后面都是一位数时才对（`'8.10'` 会变成 8.1，排到 `'8.9'` 前面），更稳的做法是拆成两段整数分别排（`substr`、`instr` 是 SQLite 的字符串函数，Postgres 可以用 `split_part`）：

```sql
ORDER BY CAST(substr(clause_id, 1, instr(clause_id, '.') - 1) AS INTEGER),
         CAST(substr(clause_id, instr(clause_id, '.') + 1) AS INTEGER)
```
--- code
SELECT clause_id,
       heading,
       CAST(clause_id AS REAL) AS as_number
FROM reviews
WHERE contract_id = 101
ORDER BY clause_id;
-- 把 ORDER BY clause_id 改成 ORDER BY as_number 再运行，比较两次的顺序

@@ concept
title: 聚合：把很多行变成一个数
--- body
聚合函数把很多行「折叠」成一个值，像 Python 的 `len`、`sum`、`max`：

- `COUNT(*)` 数**行**；`COUNT(verdict)` 只数 verdict **不是 NULL** 的行；`COUNT(DISTINCT topic)` 数有几种不同的值
- `SUM`、`AVG`、`MIN`、`MAX` 都会**跳过 NULL**
- `ROUND(x, 2)` 保留 2 位小数。平均数和钱都这样处理，结果才好读，也好比较（Postgres 的 `ROUND(x, 2)` 只接受 `numeric` 类型，钱一般就存成 `NUMERIC`；浮点数要先写 `x::numeric`）

陷阱：**整数除以整数，结果还是整数**。SQLite 和 Postgres 里 `1 / 2` 是 0，所以两个 SUM 相除很容易得到 0。先乘 `1.0` 变成小数：`ROUND(1.0 * a / b, 3)`。BigQuery 不一样：它的 `/` 总是返回小数（`5 / 2 = 2.5`），整数除法要写 `DIV(5, 2)`。
--- code
SELECT COUNT(*) AS all_rows,
       COUNT(verdict) AS with_verdict,
       COUNT(DISTINCT topic) AS topics,
       ROUND(AVG(latency_ms), 1) AS avg_latency_ms,
       MAX(latency_ms) AS max_latency_ms,
       ROUND(SUM(cost_usd), 4) AS total_cost_usd,
       SUM(completion_tokens) / SUM(prompt_tokens) AS wrong_ratio,
       ROUND(1.0 * SUM(completion_tokens) / SUM(prompt_tokens), 3) AS output_input_ratio
FROM reviews;

@@ concept
title: GROUP BY 和 HAVING
--- body
`GROUP BY topic`：按 topic 把行分成几组，**每组输出一行**，聚合函数在每组里分别算。就像第 2 天用字典计数：`counts[topic] = counts.get(topic, 0) + 1`。

- SELECT 里的每一列，要么写在 GROUP BY 里，要么包在聚合函数里。SQLite 允许你写一个两样都不是的列（悄悄取组里随便一行的值），Postgres 和 BigQuery 直接报错。**别这么写**
- `WHERE` 在分组**之前**筛**行**；`HAVING` 在分组**之后**筛**组**。所以 `COUNT(*) >= 6` 只能写在 HAVING 里

数据库执行的逻辑顺序和书写顺序不一样：

FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT

所以在 SELECT 里起的别名 `n`，ORDER BY 能用（它排在 SELECT 后面），WHERE 不能用（它排在前面）。HAVING 也排在 SELECT 前面：Postgres 的 HAVING 不认别名，要把 `COUNT(*)` 再写一遍，这样写在哪个数据库都能跑。SQLite 很宽松，WHERE、HAVING 里写别名它常常也接受，别被它惯坏了。
--- code
SELECT topic,
       COUNT(*) AS n,
       ROUND(AVG(latency_ms)) AS avg_latency_ms
FROM reviews
WHERE verdict IS NOT NULL
GROUP BY topic
HAVING COUNT(*) >= 6
ORDER BY n DESC, topic;

@@ concept
title: CASE WHEN：贴标签、按条件计数
--- body
`CASE` 是 SQL 里的 if / elif / else：从上往下，第一个成立的 WHEN 生效；都不成立就用 ELSE，没写 ELSE 就是 NULL。

```sql
CASE WHEN latency_ms >= 5000 THEN 'slow'
     WHEN latency_ms >= 2500 THEN 'ok'
     ELSE 'fast' END
```

两种用法：

- **贴标签**：放在 SELECT 里，生成新的一列，还可以按它分组
- **按条件计数**：`SUM(CASE WHEN verdict = 'redline' THEN 1 ELSE 0 END)` 数出每组里有几条 redline。一条查询就能同时算好几种计数，不用查好几次

Postgres 和 SQLite 还有更短的 `COUNT(*) FILTER (WHERE verdict = 'redline')`；BigQuery 里写 `COUNTIF(verdict = 'redline')`（第 25 天）。`SUM(CASE ...)` 哪里都能用，面试时写它最稳。
--- code
SELECT CASE WHEN latency_ms >= 5000 THEN 'slow'
            WHEN latency_ms >= 2500 THEN 'ok'
            ELSE 'fast' END AS speed,
       COUNT(*) AS n,
       SUM(CASE WHEN model = 'deepseek-v4-pro' THEN 1 ELSE 0 END) AS v4_pro,
       COUNT(*) FILTER (WHERE verdict = 'redline') AS redlines
FROM reviews
GROUP BY speed
ORDER BY MIN(latency_ms);

level: 2
--- prompt
9 月 2 日有 3 条审查，9 月 5 日有 8 条，9 月 3 日和 4 日没有。`created_at` 是 `'2026-09-05 13:17:04'` 这样的文字。这条查询返回几行？
