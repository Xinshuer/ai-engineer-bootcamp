@@ concept
title: assert: the smallest test
--- body
`assert condition, "message"`: if the condition is true, nothing happens; if it is false, Python raises `AssertionError`, and the message becomes the error message.

```python
assert section_of("10.1") == "10", "two-digit section"
```

In the end, a test is just **code that calls your function and then asserts something about the result**. On Day 7 you already used `assert` to write examples for yourself.

Two habits:

- Write the message: when it fails, you see at a glance which assumption was wrong; without a message, the AssertionError is empty
- Use `assert` for tests and for checking things that "can't happen"; to validate outside input (model output, a user's file), still use `if ... raise ValueError` (Day 3), because when you run Python with `python -O`, every assert is skipped
--- code
def section_of(clause_id):
    return clause_id.split(".")[0]

assert section_of("8.1") == "8"
assert section_of("12") == "12", "no dot"
print("two checks passed")

# get one expected value wrong on purpose, to see what a failure looks like
try:
    assert section_of("10.1") == "1", "two-digit section"
except AssertionError as e:
    print("AssertionError:", e)

@@ concept
title: Test functions and pytest
--- body
Put your asserts into functions whose names start with `test_`. **One function tests one thing**, and its name says clearly what it tests:

```python
def test_two_digit_section():
    assert section_of("10.1") == "10"
```

On your own computer, pytest automatically finds every `test_` function in the `test_*.py` files and runs them one by one; one failing test doesn't affect the others: `python -m pytest`. Clause Check's `tests/test_split.py` is written this way.

The "Write tests" exercises on this page: the exercise gives you a **correct function**, and also secretly hides a few versions with bugs planted on purpose. Your tests must **all pass on the correct version** and **make each buggy version fail at least one test**. This is called mutation testing: a test is only as good as its ability to catch bugs planted on purpose. The example below shows exactly that.
--- code
def section_of(clause_id):
    return clause_id.split(".")[0]

def test_simple():
    assert section_of("8.1") == "8"

def test_two_digit_section():
    assert section_of("10.1") == "10"

def test_no_dot():
    assert section_of("12") == "12"

# what pytest does is roughly this loop: call each test_ function in turn; if it raises, it failed
def run_tests():
    for test in [test_simple, test_two_digit_section, test_no_dot]:
        try:
            test()
            print("PASSED", test.__name__)
        except AssertionError:
            print("FAILED", test.__name__)

run_tests()

print("--- a buggy version: clause_id[0] ---")
def section_of(clause_id):
    return clause_id[0]

run_tests()

@@ concept
title: How to come up with test cases
--- body
For each function, think of inputs in three groups, and write one test for each idea:

1. **Normal**: the one or two most typical examples
2. **Edge cases**: empty (`""`, `[]`), 0, just one element, **exactly equal** to the limit, a two-digit number like `10.1`, a three-level number like `10.2.1`
3. **Invalid**: broken JSON, an unknown verdict, a negative number. Should the function raise an error or return a default? The test pins that decision down

Bugs love to hide at the edges: `>` and `>=` only give different results when the values are "exactly equal". With examples far from the edge, both the right and the wrong implementation pass.

Write the test name as a sentence, like `test_exactly_at_limit_is_not_split`. When it fails, the name itself tells you what broke.
--- code
def needs_split(text, limit=20):
    return len(text) > limit

def needs_split_buggy(text, limit=20):
    return len(text) >= limit

for text in ["", "short clause", "x" * 20, "x" * 21]:
    print(len(text), needs_split(text), needs_split_buggy(text))

@@ concept
title: Testing errors and floats: raises, approx
--- body
**When it should raise an error, does it really?** Use `pytest.raises`:

```python
import pytest

def test_bad_json_raises():
    with pytest.raises(ValueError, match="not JSON"):
        parse_verdict("Sure! {")
```

The code inside the `with` block must raise `ValueError`, or this test fails (with `DID NOT RAISE`). `match=` is a regular expression searched for in the error message, to make sure the error raised is **this** one.

One of the most dangerous bugs is **swallowing an exception**: on an error, the function quietly returns None; the program doesn't crash, but the result is wrong. `pytest.raises` is made to catch exactly that.

**Don't compare floats (decimal numbers) directly with `==`**: `0.1 + 0.2 == 0.3` is False (binary can't store these decimals exactly). Write `assert x == pytest.approx(0.3)`, which allows a tiny error.
--- code
import pytest

print(0.1 + 0.2, 0.1 + 0.2 == 0.3)
print(0.1 + 0.2 == pytest.approx(0.3))

def parse_risk(text):
    risk = text.strip().lower()
    if risk not in ("low", "medium", "high"):
        raise ValueError(f"unknown risk: {text}")
    return risk

def test_unknown_risk_raises():
    with pytest.raises(ValueError, match="unknown risk"):
        parse_risk("urgent")

test_unknown_risk_raises()
print("test passed")

def parse_risk_swallowing(text):
    try:
        return parse_risk(text)
    except ValueError:
        return None

print("swallowed:", parse_risk_swallowing("urgent"))

@@ concept
title: Debugging: reproduce, then guess, change one thing at a time
--- body
When you hit a bug, don't rush to change the code. Go in this order:

1. **Reproduce**: find the **smallest** input that fails every time (one clause, not the whole contract)
2. **Read the traceback**: start from the bottom line; first look at the error type and message, then at the line of code right above them
3. **Look at the values in between**: print them with `repr(x)` or the f-string `{x=}`. `repr` shows invisible spaces and line breaks, and tells `'8.1'` apart from `8.1`
4. **One hypothesis at a time**: "I guess the field name is wrong" → print to check → change it only if you were right; change one thing at a time
5. **Add a test**: turn that smallest input into a test, and this bug can never come back
--- code
reply = "flag\n"
print(reply == "flag")
print(repr(reply))
print(f"{reply=}")

cid = 8.1
print(f"{cid=}", type(cid).__name__)

row = {"clause_id": "8.1", "risk_level": "high"}
print(f"{row=}")
print(sorted(row))

@@ concept
title: logging: keep a record of what the program does
--- body
`print` is fine for a quick look; a long-running program (for example Clause Check turned into a service like `api.py`) should use `logging`:

- Every record has a **level**: DEBUG (details) < INFO (normal progress) < WARNING (a problem, but it can go on) < ERROR (something failed)
- One line of configuration decides which levels are shown and in what format, so you never have to delete your debugging statements: set it to WARNING in production and it goes quiet; change it to DEBUG while you investigate and you see every detail

```python
logging.basicConfig(level=logging.INFO, format="%(levelname)s %(message)s")
logger = logging.getLogger(__name__)
logger.info("clause %s -> %s", cid, verdict)
```

`getLogger(__name__)` gives each file a logger with its own name. Use `%s` placeholders and pass the values as arguments, instead of building the string yourself first: when the record is filtered out, even the work of building the string is saved.
--- code
import logging

logging.basicConfig(level=logging.INFO, format="%(levelname)s %(name)s: %(message)s")
logger = logging.getLogger("clausecheck.review")

for cid, verdict in [("3.1", "accept"), ("8.1", "redline")]:
    logger.debug("raw reply for %s", cid)
    logger.info("clause %s -> %s", cid, verdict)
logger.warning("clause %s: HTTP %d, retrying", "10.1", 429)

@@ concept
title: Common bug patterns
--- body
These bugs come up again and again, and interview "find the bug" questions love them too:

- **Off-by-one**: `range(1, len(xs))` misses the first one; `text[:n]` and `text[:n - 1]` differ by one character
- **`>` vs `>=`**: only shows up when the values are exactly equal
- **Mutable default argument**: `def f(tags=[])` (Day 8)
- **Removing while looping**: `for x in xs: xs.remove(x)` skips elements
- **`is` vs `==`**: `is` checks "is it the same object". Always compare values with `==`; use `is` only in `is None`
- **`//` vs `/`**: `2 // 3` is 0
- **Forgetting return**: the function quietly returns None
- **Shadowing a built-in name**: after you write `list = [...]`, you can no longer use `list(...)`
--- code
ids = ["3.1", "8.1", "10.1"]
print([ids[i] for i in range(1, len(ids))])
print(2 // 3, 2 / 3)

verdicts = ["accept", "accept", "flag"]
for v in verdicts:
    if v == "accept":
        verdicts.remove(v)
print(verdicts)

def label(risk):
    if risk == "high":
        return "HIGH RISK"
    "normal"

print(label("high"), label("low"))

type: predict
title: What assert prints
level: 1
cards: assert: the smallest test
--- context
You can't write tests without `assert`: it checks a condition and raises an error if the condition doesn't hold. This code uses it to block invalid verdicts, for example when the model put the risk level where the verdict should be.
--- prompt
Write the output. Notice that the last assert has no message.
--- code
def check_verdict(v):
    assert v in ("accept", "flag", "redline"), f"bad verdict: {v}"
    return v

print(check_verdict("flag"))
try:
    check_verdict("HIGH")
except AssertionError as e:
    print("AssertionError:", e)
try:
    assert len([]) > 0
except AssertionError as e:
    print("no message:", repr(str(e)))
--- explain
When an assert passes, it does nothing, and the function returns as usual. When it fails, the message after the comma becomes the error message; without a message, the error message is the empty string `''`, and to find the problem you have to dig through the code. So give the asserts in your tests a message, or at least make the test function's name say clearly what it tests.

type: choice
title: Which test catches it?
level: 2
cards: How to come up with test cases; Common bug patterns
--- context
The web page shows the clause list in pages of 10, so first it has to work out how many pages there are. This time you don't write code; you pick a test to check code someone else wrote.
--- prompt
`pages(n_clauses)` should return how many pages it takes to fit all the clauses (10 per page; a last page that isn't full still counts as a page). The implementation below has a bug. Which test catches it?
--- code
def pages(n_clauses, per_page=10):
    return n_clauses // per_page
--- options
- `assert pages(20) == 2`
- `assert pages(0) == 0`
- `assert pages(10) == 1`
- `assert pages(25) == 3`
answer: 4
--- explain
The first three inputs all divide exactly, so the buggy version gets them right too. **All tests passing doesn't mean there are no bugs**: pick inputs that go down the path where it goes wrong. Here that is the case "with a remainder": for 25 clauses it computes 2 pages. When you write tests, first ask yourself: for which kind of input is this function most likely to get it wrong? A correct version is `(n_clauses + per_page - 1) // per_page` or `math.ceil(n_clauses / per_page)`.
