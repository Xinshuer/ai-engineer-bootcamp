title: Data warehouses and BigQuery
bq: yes
--- body
BigQuery on this page is simulated: the SQL runs on SQLite in your browser, which imitates a few BigQuery features; the Python client's calls and return structures match the real SDK (google-cloud-bigquery), though only the parts this course uses are implemented. In a real project, run `pip install google-cloud-bigquery` and set up credentials, and you're ready.

Yesterday's SQLite / Postgres is a **business database** (OLTP): each read or write touches a few rows, and it must be fast and have transactions. Once Clause Check is live, every review produces one row of trace data. Over time that adds up to hundreds of millions of rows, and the people in charge want a **dashboard**: how much each customer cost per month, the prompt cache hit rate, latency p95, the redline rate and failure rate of each prompt version. Questions that "scan a big stretch of history" like these are the job of a **data warehouse** (OLAP).

BigQuery is Google Cloud's data warehouse:

- **Serverless**: no machines to manage; you just write SQL and pay for what you use
- **Columnar storage**: each column is stored separately and only the columns a query uses are read, so even scanning hundreds of millions of rows is fast
- Names have three parts: `project.dataset.table`, for example `clausecheck-dev.clausecheck.reviews` (on this page the project is called clausecheck-dev and the dataset clausecheck). In SQL, wrap a full name that includes the project in backticks, like the FROM in the example below
- It is built for analysis, not as an application's backend database: it is not good at changing single rows often
- When you create a dataset you choose its **location** (for example the `EU` multi-region, or `europe-north1` in Finland), and you can't change it afterwards. Trace data may contain customer information, so following common GDPR practice it goes in the EU by default

The AWS equivalents:

- BigQuery ↔ Amazon Redshift (data warehouse)
- BigQuery external tables (querying files in Cloud Storage) ↔ Amazon Athena (querying files in S3 directly with SQL)
--- code
SELECT model, COUNT(*) AS reviews, ROUND(SUM(cost_usd), 4) AS cost_usd
FROM `clausecheck-dev.clausecheck.reviews`
GROUP BY model
ORDER BY reviews DESC

title: Billing: how many columns and partitions you scan
lang: py
--- body
With on-demand pricing, BigQuery charges by the **bytes scanned** by a query. The official pricing page says 6.25 US dollars per TiB, with the first 1 TiB each month free (prices change; the official pricing page is the source of truth). The other model is capacity pricing (editions: you pay for how many compute slots you use, for how many hours), which teams with heavy use often choose; today covers on-demand only. Because storage is columnar:

- Bytes scanned = the full size of **every column the query uses** (anything that appears in SELECT, WHERE, JOIN or GROUP BY counts), no matter how many rows come back. `SELECT *` reads every column and is the most expensive
- `LIMIT 10` does **not** scan less; on a table without partitions or clustering, neither does `WHERE`
- Every table a query uses is billed at least 10 MB; queries that fail and queries answered from the cache are free. If you only want to see what the data looks like, use the table's Preview tab in the console (free)
- **Partitioned tables**: `PARTITION BY DATE(created_at)` cuts the table into one block per day. When WHERE compares the partition column directly with a constant (`created_at >= TIMESTAMP('2026-09-01')`), only those days' partitions are read. Turn on `OPTIONS (require_partition_filter = TRUE)` when you create the table, and any query without such a filter fails with an error
- **Clustering**: `CLUSTER BY customer_id` stores each customer's data together, so filtering on it can skip many blocks. How much it saves is only known once the query has run, so a dry run's estimate on a clustered table is an upper bound

This page can't simulate partitions and clustering, so below we do the math for an imaginary table with "200 million rows a year".
--- code
TIB = 2 ** 40
PRICE_PER_TIB = 6.25                 # example price; the official pricing page is the source of truth
ROWS = 200_000_000                   # imaginary: one year live, one row per review
BYTES_PER_ROW = {                    # average bytes per row for each column: 8 for numbers and times, about 2 + length for text
    "id": 8, "contract_id": 8, "clause_id": 6, "heading": 22, "topic": 15, "verdict": 8,
    "risk": 6, "model": 16, "prompt_version": 4, "prompt_tokens": 8, "completion_tokens": 8,
    "cache_hit_tokens": 8, "latency_ms": 8, "cost_usd": 8, "error": 2, "created_at": 8,
    "rationale": 400,                # the model's reasoning: the column that takes the most space
}

def usd(columns, share_of_rows=1.0):
    scanned = ROWS * share_of_rows * sum(BYTES_PER_ROW[c] for c in columns)
    return scanned / TIB * PRICE_PER_TIB

runs_per_month = 12 * 24 * 30        # the dashboard refreshes every 5 minutes
print(f"SELECT * ... LIMIT 10          ${usd(BYTES_PER_ROW):.3f} per run")
print(f"SELECT created_at, cost_usd    ${usd(['created_at', 'cost_usd']):.4f} per run")
print(f"  + 30 of 365 day partitions   ${usd(['created_at', 'cost_usd'], 30 / 365):.5f} per run")
print(f"dashboard with SELECT *        ${usd(BYTES_PER_ROW) * runs_per_month:,.0f} per month")
print(f"dashboard, 2 cols, partitions  ${usd(['created_at', 'cost_usd'], 30 / 365) * runs_per_month:,.2f} per month")

title: The GoogleSQL dialect: table names, division, COUNTIF
bq: yes
--- body
BigQuery's SQL is called GoogleSQL. The SELECT, JOIN, CTEs and window functions from the last two days all work as usual. Here are the places where it differs from SQLite that you'll use today (this page simulates them, and you can use them in exercises marked as BigQuery syntax):

- Table names need the dataset: `clausecheck.reviews`; or write the full name including the project, wrapped in backticks (the key below Esc in the top-left corner of the keyboard), like the FROM in the example below. Writing just `reviews` gives a missing dataset error
- `/` always gives a decimal: `7 / 2 = 3.5` (in SQLite and Postgres, dividing two whole numbers gives 3). For whole-number division use `DIV(7, 2)`
- `SAFE_DIVIDE(a, b)`: gives NULL when b is 0, instead of an error. Use it for ratios (hit rate, pass rate)
- `COUNTIF(condition)`: counts the rows that meet the condition, the same as `SUM(CASE WHEN condition THEN 1 ELSE 0 END)` (when there are no rows at all, COUNTIF gives 0 and SUM gives NULL)
- `IF(condition, a, b)`: a shorter CASE WHEN
- The type names are different: `CAST(x AS STRING)`, `INT64`, `FLOAT64`, `BOOL`

Below we compare two models: on average the large model v4-pro produces more than three times as many output tokens as flash, and it is much slower too.
--- code
SELECT
  model,
  COUNT(*) AS reviews,
  COUNTIF(verdict = 'flag') AS flags,
  ROUND(SAFE_DIVIDE(SUM(completion_tokens), COUNT(*)), 1) AS avg_output_tokens,
  IF(AVG(latency_ms) > 5000, 'slow', 'ok') AS speed,
  7 / 2 AS float_div,
  DIV(7, 2) AS int_div
FROM `clausecheck-dev.clausecheck.reviews`
GROUP BY model

title: Time: DATE_TRUNC and TIMESTAMP_DIFF
bq: yes
--- body
The most common time types in BigQuery are `DATE` (a date) and `TIMESTAMP` (a moment in time, in UTC); there are also `DATETIME` and `TIME`, which have no time zone. On this page the time columns are stored as text, but the functions below are simulated following BigQuery's rules:

- `DATE(created_at)`: moment → date
- `DATE_TRUNC(date, MONTH)`: cut back to the start of the month (also WEEK, QUARTER, YEAR). **The value comes first, the unit second**, and the unit is a keyword without quotes: exactly the reverse of Postgres's `date_trunc('month', ts)`. Writing `'MONTH'` gives an error
- Truncating doesn't change the type: a TIMESTAMP cut to the month is still a TIMESTAMP (`2026-09-01 00:00:00`), so "by month" is usually written `DATE_TRUNC(DATE(created_at), MONTH)`, which gives `2026-09-01`
- `WEEK` starts on Sunday (to start on Monday, real BigQuery has `ISOWEEK` or `WEEK(MONDAY)`; this page doesn't simulate them)
- `TIMESTAMP_DIFF(later, earlier, SECOND)`: how many whole seconds apart two moments are (the largest unit is DAY; with DAY it counts full 24-hour periods). To count calendar days or months between them, use `DATE_DIFF(DATE(a), DATE(b), DAY)` (or `MONTH`)

A small limitation of this page: don't give a column an alias that is just a time-unit word, such as `month`, `week`, `day`, `hour` or `year` (the simulator may take it for a unit and quietly compute the wrong result); use names like `month_start`. Real BigQuery doesn't have this problem.

Below: how long each of the two eval runs took. v1 and v2 each finished their 24 runs in about three and a half minutes.
--- code
SELECT
  prompt_version,
  DATE(MIN(created_at)) AS run_date,
  DATE_TRUNC(DATE(MIN(created_at)), WEEK) AS week_start,
  TIMESTAMP_DIFF(MAX(created_at), MIN(created_at), SECOND) AS run_seconds,
  COUNT(*) AS runs
FROM clausecheck.evals
GROUP BY prompt_version
ORDER BY prompt_version

title: BigQuery syntax this page cannot run
bq: yes
--- body
You'll use these every day in real BigQuery, but this page can't simulate them. Learn to recognize them, and be able to write them in an interview:

- `QUALIFY`: like HAVING, but it filters on the results of window functions. "The latest review of each clause" takes one statement:

```sql
SELECT contract_id, clause_id, verdict
FROM clausecheck.reviews
WHERE error IS NULL
QUALIFY ROW_NUMBER() OVER (PARTITION BY contract_id, clause_id ORDER BY created_at DESC) = 1
```

  The way to write it on this page: put ROW_NUMBER in a CTE and use `WHERE rn = 1` outside it (Day 23)
- `APPROX_QUANTILES(latency_ms, 100)[OFFSET(95)]`: an approximate p95. This page computes it with window functions using nearest-rank (the method from Day 13); that's the example below
- `ARRAY_AGG(x)` collects a group of values into an array, `UNNEST(array)` expands an array into rows (like yesterday's json_each), `STRUCT(a, b)` packs several fields into one
- `SELECT * EXCEPT (rationale)`: every column except a few (the columns you leave out aren't scanned, so you don't pay for them)
- AI inside the warehouse: BigQuery ML can call a model from SQL to generate embeddings, and `VECTOR_SEARCH` does vector similarity search over a table (the official docs are the source of truth for how to use them)

In the example: `rn` is the rank after sorting and `n` is the number of rows in the group. The smallest latency among the rows ranked ≥ 0.95 × n is exactly the row ranked ceil(0.95 × n), which is the nearest-rank p95.
--- code
WITH ranked AS (
  SELECT
    model,
    latency_ms,
    ROW_NUMBER() OVER (PARTITION BY model ORDER BY latency_ms) AS rn,
    COUNT(*) OVER (PARTITION BY model) AS n
  FROM clausecheck.reviews
)
SELECT
  model,
  MAX(n) AS n,
  MIN(IF(rn >= 0.95 * n, latency_ms, NULL)) AS p95_ms
FROM ranked
GROUP BY model
ORDER BY model

title: The Python client: queries, parameters, rows
lang: py
cloud: yes
dataset: clausecheck
--- body
In Python you use `google-cloud-bigquery`:

```python
from google.cloud import bigquery
client = bigquery.Client()                    # the project and credentials come from the environment (more on Day 26)
config = bigquery.QueryJobConfig(
    query_parameters=[bigquery.ScalarQueryParameter("cid", "INT64", 103)],
    labels={"feature": "dashboard"},
)
job = client.query(sql, job_config=config)    # submit a query job
rows = list(job.result())                     # wait for it to finish and get all the rows
```

- In the SQL write `@cid`, and pass the value with `ScalarQueryParameter(name, type, value)`; the type is `"STRING"`, `"INT64"`, `"FLOAT64"`, `"BOOL"`, `"DATE"` or `"TIMESTAMP"`. Same idea as yesterday's `?`: **never build values into SQL with an f-string**. Table and column names can't be parameters either
- Read values from a row with `row["verdict"]`, `row.verdict` or `row[0]`; `dict(row.items())` turns it into a dictionary. INT64 → int, FLOAT64 → float, TIMESTAMP → a `datetime` with a time zone (UTC)
- You can loop over `job.result()` only **once**; if you need it twice, wrap it in `list(...)` first
- A mistake in the SQL, a table that doesn't exist: the error is raised by `job.result()`, not by `client.query()`
- `labels` tag the query, so the bill can split costs by feature
- In the real SDK, `job.result().to_dataframe()` turns the result straight into a pandas table (this page has no pandas)
--- code
from google.cloud import bigquery

client = bigquery.Client()
sql = """
SELECT id, clause_id, verdict, created_at
FROM clausecheck.reviews
WHERE contract_id = @cid AND risk = @risk
ORDER BY id
"""
config = bigquery.QueryJobConfig(query_parameters=[
    bigquery.ScalarQueryParameter("cid", "INT64", 103),
    bigquery.ScalarQueryParameter("risk", "STRING", "high"),
])
job = client.query(sql, job_config=config)
rows = list(job.result())
for row in rows:
    print(row["id"], row.clause_id, row[2], row.created_at.isoformat())
print(dict(rows[0].items()))

bad = client.query("SELECT verdict FROM reviews")      # forgot the dataset
print("client.query() did not raise")
try:
    bad.result()
except Exception as e:
    print(type(e).__name__, e)

title: Dry runs, byte limits, and caching
lang: py
cloud: yes
dataset: clausecheck
--- body
Do the math before you spend money:

- **Dry run**: `QueryJobConfig(dry_run=True)`. BigQuery only checks the SQL and estimates how much it will scan; it doesn't really run it, and it's **free**. Read `job.total_bytes_processed`. If the SQL has an error, `client.query()` raises it right away. The official Python sample writes `QueryJobConfig(dry_run=True, use_query_cache=False)`: the estimate ignores the cache
- **Byte limit**: `QueryJobConfig(maximum_bytes_billed=number_of_bytes)`. If the bytes the query is expected to bill go over the limit, the query fails right away and costs nothing. Every table is billed at least 10 MB (10485760 bytes), so with a limit below that, every query that reads a table fails
- The error reason for going over the limit is `bytesBilledLimitExceeded`. With `client.query()` + `result()`, the SDK's error mapping has no entry for this reason, so it reports a 500 `InternalServerError`, **not** `BadRequest`; with another way of calling, the type may be different again. So catch their common parent class `GoogleAPICallError`, then look at `e.errors[0]["reason"]`
- **Cache**: when exactly the same query (down to the spaces) runs again within 24 hours and the table hasn't changed, the result comes straight from the cache (`job.cache_hit` is True) and 0 bytes are billed. When the table has just received streaming inserts, or the query uses a function that changes every time, such as `CURRENT_TIMESTAMP()`, the cache isn't used

Below: how much three queries scan (note the one with LIMIT); a limit that is too low; the same query run twice.
--- code
from google.cloud import bigquery
from google.api_core.exceptions import GoogleAPICallError

client = bigquery.Client()
for sql in [
    "SELECT * FROM clausecheck.reviews",
    "SELECT verdict, cost_usd FROM clausecheck.reviews",
    "SELECT verdict, cost_usd FROM clausecheck.reviews LIMIT 1",
]:
    job = client.query(sql, job_config=bigquery.QueryJobConfig(dry_run=True, use_query_cache=False))
    print(f"{job.total_bytes_processed:>5} bytes  {sql}")

limited = bigquery.QueryJobConfig(maximum_bytes_billed=5_000_000)
try:
    client.query("SELECT verdict FROM clausecheck.reviews", job_config=limited).result()
except GoogleAPICallError as e:
    print(type(e).__name__, e.errors[0]["reason"])

first = client.query("SELECT COUNT(*) AS n FROM clausecheck.evals")
first.result()
again = client.query("SELECT COUNT(*) AS n FROM clausecheck.evals")
print("cache hit:", first.cache_hit, again.cache_hit, "| billed:", first.total_bytes_billed, again.total_bytes_billed)

title: Writing data: streaming and batch loading
lang: py
cloud: yes
dataset: clausecheck
--- body
How does trace data get into BigQuery? There are two ways:

- **Streaming inserts** with `client.insert_rows_json(table_name, list_of_rows)`: the rows can be queried within a few seconds of writing, and you pay for the amount written (official pricing page: 0.01 US dollars per 200 MiB, each row counted as at least 1 KB; the official page is the source of truth). Good for a worker that writes one row each time it finishes a review. It uses the old insertAll (REST) API and is the simplest to write; for new projects Google recommends the gRPC-based Storage Write API, which is cheaper
- **Batch loading**: first write a batch of data to files in Cloud Storage, then import them with a load job. Loading itself is free; good for large amounts of data that aren't urgent

When the row data has problems, `insert_rows_json` **doesn't raise an exception: it returns a list of errors**, and you must check it. Success is `[]`; on failure each entry is `{"index": row_number, "errors": [...]}`. (Only errors about the whole request, such as a missing table or no permission, raise an exception.) By default, **one bad row means none of the batch is written**: the bad row's reason is `invalid`, the other rows get `stopped` and can be sent again as they are. `skip_invalid_rows=True` lets the good rows go straight in.

BigQuery won't block duplicate rows for you: a table can declare a primary key, but it isn't enforced (it's only used to optimize queries). Send the same row twice and it's usually stored as two rows (the `row_ids` parameter only removes duplicates on a best-effort basis). So dashboard queries often have to remove duplicates themselves, for example with QUALIFY to take the latest row of each group. Note: this page's simulation treats `id` as a primary key, so when the same id is sent twice only one row is kept. Real BigQuery is different here.
--- code
from google.cloud import bigquery

client = bigquery.Client()
TABLE = "clausecheck-dev.clausecheck.reviews"
row = {
    "id": 1066, "contract_id": 110, "clause_id": "9.1", "heading": "Warranties", "topic": "warranty",
    "verdict": "accept", "risk": "low", "rule_ids": '["PB-00"]', "model": "deepseek-flash",
    "prompt_version": "v2", "prompt_tokens": 2104, "completion_tokens": 151, "cache_hit_tokens": 1650,
    "latency_ms": 2210, "cost_usd": 0.000327, "created_at": "2026-09-23 10:00:00",
}
bad = dict(row, id=1067, prompt_tokens="many")

errors = client.insert_rows_json(TABLE, [row, bad])
for e in errors:
    print(e["index"], e["errors"][0]["reason"], e["errors"][0]["message"])
print(client.insert_rows_json(TABLE, [row]))
n = list(client.query("SELECT COUNT(*) AS n FROM clausecheck.reviews").result())[0]["n"]
print("rows now:", n)

WITH ranked AS (
  SELECT model, id, clause_id, latency_ms,
         ROW_NUMBER() OVER (PARTITION BY model ORDER BY latency_ms DESC) AS rn
  FROM reviews
)
SELECT model, id, clause_id, latency_ms
FROM ranked
WHERE rn <= 2
ORDER BY model, latency_ms DESC;
--- hints
- Number each row in a CTE: `ROW_NUMBER() OVER (PARTITION BY model ORDER BY latency_ms DESC) AS rn`.

- Finish with `ORDER BY model, latency_ms DESC`.

title: Cache hit rate per contract
level: 2
bq: yes
ordered: yes
cards: The GoogleSQL dialect: table names, division, COUNTIF
--- context
The more input tokens hit the cache, the cheaper the review (Day 12's prefix cache). Looking at the hit rate per contract shows which contracts missed out on that saving.
--- prompt
Cache hit rate = input tokens that hit the cache ÷ all input tokens (Days 12 and 13). Compute each contract's hit rate and return three columns: `contract_id`, `reviews` (the number of reviews), `cache_hit_ratio` (`SUM(cache_hit_tokens)` ÷ `SUM(prompt_tokens)`, `ROUND(..., 3)`), sorted by hit rate from low to high.

Look at the result: the lowest hit rate belongs to 110, which has only 2 reviews. Why do contracts with few reviews have a low hit rate? (Look at the `cache_hit_tokens` of each contract's first review.)
--- solution
SELECT
  contract_id,
  COUNT(*) AS reviews,
  ROUND(SAFE_DIVIDE(SUM(cache_hit_tokens), SUM(prompt_tokens)), 3) AS cache_hit_ratio
FROM clausecheck.reviews
GROUP BY contract_id
ORDER BY cache_hit_ratio;
--- hints
- Sum first, then divide: `SAFE_DIVIDE(SUM(cache_hit_tokens), SUM(prompt_tokens))`. Don't compute a ratio for each row and then take the AVG: that gives short and long requests the same weight, and the result is wrong.
- In SQLite and Postgres, `SUM(a) / SUM(b)` is whole-number division and gives 0; BigQuery's `/` gives a decimal anyway. SAFE_DIVIDE adds one more safety net: when the denominator is 0 you get NULL, and the whole query doesn't fail.
- The first request of each contract finds the cache cold (cache_hit_tokens is 0); only the later requests hit the shared prefix. The fewer the reviews, the bigger the share of that cold request.

title: Cost per customer per month
level: 2

--- context
Customers pay for a plan, but the model costs money for every clause it reviews. Only by adding up model costs per customer and per month do you know what each customer costs, and whether the plan's price covers it.
--- prompt
Work out the costs: what the reviews of each customer cost in each month. Take the month from the **review time**; failed reviews cost money too, so count them as well. Return four columns:

- `month_start`: `DATE_TRUNC(DATE(r.created_at), MONTH)`
- `customer`: the customer's name
- `reviews`: the number of reviews
- `cost_usd`: `ROUND(SUM(cost_usd), 4)`

Sort by month_start from earliest to latest, and within the same month by cost_usd from high to low. Customers without reviews don't need to appear.
--- solution
SELECT
  DATE_TRUNC(DATE(r.created_at), MONTH) AS month_start,
  cu.name AS customer,
  COUNT(*) AS reviews,
  ROUND(SUM(r.cost_usd), 4) AS cost_usd
FROM clausecheck.reviews AS r
JOIN clausecheck.contracts AS c ON c.id = r.contract_id
JOIN clausecheck.customers AS cu ON cu.id = c.customer_id
GROUP BY month_start, customer
ORDER BY month_start, cost_usd DESC;
--- hints
- Reviews reach customers through contracts: reviews → contracts → customers, and all three tables need the dataset.

def safe_query(client, sql, max_bytes):
    config = bigquery.QueryJobConfig(maximum_bytes_billed=max_bytes)
    job = client.query(sql, job_config=config)
    try:

    except GoogleAPICallError as e:

            return None
        raise
    return [dict(row.items()) for row in rows]

from google.cloud import bigquery

TABLE = "clausecheck-dev.clausecheck.reviews"

def stream_reviews(client, rows):
    if not rows:
        return {"inserted": 0, "bad": []}
    errors = client.insert_rows_json(TABLE, rows)
    if not errors:
        return {"inserted": len(rows), "bad": []}
    bad = sorted(e["index"] for e in errors if any(x["reason"] == "invalid" for x in e["errors"]))
    retry = [row for i, row in enumerate(rows) if i not in bad]
    if retry:
        again = client.insert_rows_json(TABLE, retry)
        if again:
            raise RuntimeError(f"retry failed: {again}")
    return {"inserted": len(retry), "bad": bad}

--- prompt
Using BigQuery syntax: the redline rate of each customer in each month, counting only successful reviews (`error IS NULL`), with the month taken from the review time. Return five columns:

- `month_start`: the first day of the month the review is in (DATE)
- `customer`: the customer's name
- `reviews`: the number of successful reviews
- `redlines`: how many of them are redline
- `redline_rate`: redlines ÷ reviews, with SAFE_DIVIDE, `ROUND(..., 3)`

Sort by month_start from earliest to latest, within the same month by redline_rate from high to low, and ties by customer in alphabetical order. Tables: `clausecheck.reviews`, `clausecheck.contracts` (`customer_id`), `clausecheck.customers` (`name`).
--- solution
SELECT
  DATE_TRUNC(DATE(r.created_at), MONTH) AS month_start,
  cu.name AS customer,
  COUNT(*) AS reviews,
  COUNTIF(r.verdict = 'redline') AS redlines,
  ROUND(SAFE_DIVIDE(COUNTIF(r.verdict = 'redline'), COUNT(*)), 3) AS redline_rate
FROM clausecheck.reviews AS r
JOIN clausecheck.contracts AS c ON c.id = r.contract_id
JOIN clausecheck.customers AS cu ON cu.id = c.customer_id
WHERE r.error IS NULL
GROUP BY month_start, customer
ORDER BY month_start, redline_rate DESC, customer;

Write `guarded_query(client, sql, params, max_usd, usd_per_tib=6.25)`, using `from google.cloud import bigquery`:

- `params` is a dictionary `{parameter_name: (type, value)}`, for example `{"cid": ("INT64", 103)}`, with `@cid` in the SQL. Turn them into a list of `bigquery.ScalarQueryParameter(name, type, value)`; `params` can be an empty dictionary
- First do a **dry run** (with the parameters as well, or the dry run fails because it can't find `@cid`); cost = `total_bytes_processed / 2**40 * usd_per_tib`
- If the cost is greater than `max_usd`: `raise ValueError`, and **don't** really run the query
- Otherwise really run it (with the parameters) and return the rows as a list of dictionaries (`dict(row.items())`)

Example: `guarded_query(client, "SELECT id, verdict FROM clausecheck.reviews WHERE contract_id = @cid AND risk = @risk ORDER BY id", {"cid": ("INT64", 101), "risk": ("STRING", "high")}, 0.01)` → `[{"id": 1005, "verdict": "redline"}, {"id": 1006, "verdict": "flag"}]`
--- solution
from google.cloud import bigquery

def guarded_query(client, sql, params, max_usd, usd_per_tib=6.25):
    qp = [bigquery.ScalarQueryParameter(name, type_, value) for name, (type_, value) in params.items()]
    dry = client.query(sql, job_config=bigquery.QueryJobConfig(query_parameters=qp, dry_run=True, use_query_cache=False))
    usd = dry.total_bytes_processed / 2**40 * usd_per_tib
    if usd > max_usd:
        raise ValueError(f"query would cost {usd:.8f} USD, limit {max_usd}")
    job = client.query(sql, job_config=bigquery.QueryJobConfig(query_parameters=qp))
    return [dict(row.items()) for row in job.result()]

  expected,
  prompt_version,
