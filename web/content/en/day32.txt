@@ concept
title: From your runner to StateGraph
--- body
Every piece of the runner you wrote on Day 19 has a counterpart in LangGraph:

- `nodes["review"] = review` → `g.add_node("review", review)`
- `start = "load"` → `g.add_edge(START, "load")`
- `edges["load"] = "review"` → `g.add_edge("load", "review")`
- `edges["summarise"] = route` → `g.add_conditional_edges("summarise", route)` (two cards from now)
- `"END"` → `END`
- `run_graph(...)` → `app = g.compile()`, then `app.invoke(input)` returns the **final state** (a dict)
- `max_steps=20` → pass `{"recursion_limit": 20}` when you call it (Day 31: if you don't, the limit is 10007)

The rules are the same too: a node gets the whole state and returns only **the keys it changed** (a small dictionary); the framework does the merging. `compile()` checks the structure first (an edge pointing to a node that doesn't exist, no starting point, …). The `app` it returns is a Runnable, so it also has `stream` and `batch` (Day 29).

The State is a `TypedDict` (you learned it on Day 19); `total=False` means every key may be missing at the start.

Is it worth it? For a straight-line flow like the one below, plain functions called one after another are enough (that's exactly what `pipeline.py` does). What LangGraph is really worth is checkpoints, interrupts that wait for a person, parallelism and streaming; the docstring at the top of `graph.py` gives exactly this reason.
--- code
from typing import TypedDict
from langgraph.graph import StateGraph, START, END

class State(TypedDict, total=False):
    text: str
    clauses: list[str]
    redlines: list[str]
    summary: str

def load(state: State) -> dict:
    return {"clauses": state["text"].split("\n")}

def review(state: State) -> dict:
    return {"redlines": [c.split()[0] for c in state["clauses"] if "unlimited" in c]}

def summarise(state: State) -> dict:
    return {"summary": f"{len(state['clauses'])} clauses, {len(state['redlines'])} redline(s)"}

g = StateGraph(State)
g.add_node("load", load)
g.add_node("review", review)
g.add_node("summarise", summarise)
g.add_edge(START, "load")
g.add_edge("load", "review")
g.add_edge("review", "summarise")
g.add_edge("summarise", END)
app = g.compile()

final = app.invoke({"text": "3.1 Fees are payable in 30 days.\n8.3 Liability shall be unlimited."})
print(final["summary"], final["redlines"])
print(sorted(final))
print(type(app).__name__)

@@ concept
title: State and reducers
--- body
By default every key is **overwritten**: when two nodes write `verdict` one after the other, the later one wins, just like `{**state, **update}`.

To "add up" instead, give the key a **reducer**:

```python
class State(TypedDict):
    verdict: str                                  # overwrite
    notes: Annotated[list[str], operator.add]     # append
```

When merging, LangGraph calls `operator.add(old value, new value)`, which for lists means joining them. A reducer can be any function that "takes two arguments and returns the merged result", for example one that keeps the higher risk level (you'll write it in the practice). The input to `invoke` goes through the reducer too.

Why it matters: nodes can run in parallel (a later card), and when several nodes in the same step write the same key, only a reducer knows how to combine them.

Classic mistake: a key has a reducer, but the node returns the **whole** list, `{"notes": state["notes"] + ["x"]}`. The old contents get joined on a second time. A node returns only the **new** part.
--- code
import operator
from typing import Annotated, TypedDict
from langgraph.graph import StateGraph, START, END

class State(TypedDict):
    verdict: str
    notes: Annotated[list[str], operator.add]

def legal(state):
    return {"verdict": "flag", "notes": ["legal: cap is 12 months"]}

def cost(state):
    return {"verdict": "accept", "notes": ["cost: within budget"]}

def wrong(state):
    return {"notes": state["notes"] + ["wrong: returned the whole list"]}

g = StateGraph(State)
g.add_node("legal", legal)
g.add_node("cost", cost)
g.add_node("wrong", wrong)
g.add_edge(START, "legal")
g.add_edge("legal", "cost")
g.add_edge("cost", "wrong")
g.add_edge("wrong", END)
out = g.compile().invoke({"verdict": "", "notes": ["input"]})
print("verdict:", out["verdict"])
for note in out["notes"]:
    print(" -", note)

@@ concept
title: Conditional edges
--- body
`g.add_conditional_edges("summarise", route)`: after `summarise` finishes, LangGraph calls `route(state)`, which returns the name of the next node, or `END` (finish right away). Exactly like the routing function from Day 19.

Give the routing function a return type, `-> Literal["approve", "export"]` (that's how `route` in `graph.py` is written):

- From this annotation LangGraph knows which nodes the conditional edge can go to, so it draws the graph correctly
- When the returned name is not in it (for example misspelled as `"Approve"`), it raises `KeyError: 'Approve'` right away, so you find out immediately
- It runs without the annotation too, but a misspelled name **raises no error**: the graph logs a warning and just stops (a later card is all about this)

You can also give the destinations as a third argument: a list, `["approve", "export"]`, or a mapping, `{"yes": "approve", "no": "export"}` (the router then returns yes / no). The effect is the same: the drawing knows the destinations, and a typo raises `KeyError`.
--- code
import operator
from typing import Annotated, Literal, TypedDict
from langgraph.graph import StateGraph, START, END

class State(TypedDict, total=False):
    redlines: int
    path: Annotated[list[str], operator.add]

def summarise(state):
    return {"path": ["summarise"]}

def approve(state):
    return {"path": ["approve"]}

def export(state):
    return {"path": ["export"]}

def route(state) -> Literal["approve", "export"]:
    return "approve" if state["redlines"] > 0 else "export"

g = StateGraph(State)
g.add_node("summarise", summarise)
g.add_node("approve", approve)
g.add_node("export", export)
g.add_edge(START, "summarise")
g.add_conditional_edges("summarise", route)
g.add_edge("approve", "export")
g.add_edge("export", END)
app = g.compile()

print(app.invoke({"redlines": 2})["path"])
print(app.invoke({"redlines": 0})["path"])

@@ concept
title: Parallel branches and supersteps
--- body
LangGraph runs in **steps (supersteps)**: each step runs all the nodes that are due, together; when they have all finished, it merges their updates at once, then decides the next step. When a node has two outgoing edges, both targets run in parallel in the same step (on a normal computer with threads; in this page's browser one after the other, with the same result).

- **Join**: `g.add_edge(["legal_check", "cost_estimate"], "summarise")` (the start written as a list) means `summarise` runs only after **both** have finished, and only once. With just two separate edges, when one branch is longer than the other, `summarise` is triggered **twice**, in different steps (the example below)
- Two nodes in the same step write the same key, and that key has **no reducer**: `InvalidUpdateError: At key 'verdict': Can receive only one value per step. Use an Annotated key to handle multiple values.` The fix is to give it a reducer
- The merge order is fixed (in this version it goes by node name), but it's not the order you added the edges, and not who finished first. Don't rely on it: if you need a stable order, sort it yourself
- Don't `print` inside parallel nodes: on a real machine the threads run in no fixed order, so the output order can differ every time
--- code
import operator
from typing import Annotated, TypedDict
from langgraph.graph import StateGraph, START, END

class State(TypedDict, total=False):
    findings: Annotated[list[str], operator.add]
    runs: Annotated[list[str], operator.add]

def legal_check(state):
    return {"findings": ["legal: liability is unlimited"]}

def cost_check(state):
    return {"findings": ["cost: fees can rise any time"]}

def cost_estimate(state):
    return {"findings": ["cost: +12% per year"]}

def summarise(state):
    return {"runs": [f"summarise saw {len(state['findings'])} finding(s)"]}

def build(join):
    g = StateGraph(State)
    for name, fn in [("legal_check", legal_check), ("cost_check", cost_check), ("cost_estimate", cost_estimate), ("summarise", summarise)]:
        g.add_node(name, fn)
    g.add_edge(START, "legal_check")
    g.add_edge(START, "cost_check")
    g.add_edge("cost_check", "cost_estimate")
    if join:
        g.add_edge(["legal_check", "cost_estimate"], "summarise")
    else:
        g.add_edge("legal_check", "summarise")
        g.add_edge("cost_estimate", "summarise")
    g.add_edge("summarise", END)
    return g.compile()

print("two edges:", build(join=False).invoke({})["runs"])
out = build(join=True).invoke({})
print("joined:   ", out["runs"])
print(sorted(out["findings"]))

@@ concept
title: Loud errors and silent errors
--- body
What LangGraph **reports** (good news: you know right away):

- An edge pointing to a node that doesn't exist: at `compile()`, `ValueError: Found edge ending at unknown node ...`
- No edge leaving `START`: `ValueError: Graph must have an entrypoint ...`
- The same node name added twice: `ValueError: Node ... already present.`
- A node returns something that isn't a dictionary: `InvalidUpdateError: Expected dict, got ...`
- A node reads a key nobody has written: an ordinary `KeyError`

What happens **silently** (the most dangerous kind; tests have to catch it on purpose):

- A node returns a key that isn't in the State (`verdikt`): it's simply dropped
- A routing function (without a `Literal` annotation) returns a node name that doesn't exist: only a warning is logged (the `Task ... wrote to unknown channel ...` line in the output below), and the graph stops
- A node has no outgoing edge: the graph ends there
- A node forgets `return` (returns `None`): treated as "changed nothing"

How to catch them: tests assert the **final state** and the **nodes visited**; routing functions get a `Literal`; when debugging, look at stream (next card).
--- code
from typing import TypedDict
from langgraph.graph import StateGraph, START, END

class S(TypedDict, total=False):
    verdict: str

def run(label, node, route=None):
    try:
        g = StateGraph(S)
        g.add_node("review", node)
        g.add_node("export", lambda s: {})
        g.add_edge(START, "review")
        if route:
            g.add_conditional_edges("review", route)
        else:
            g.add_edge("review", "export")
        g.add_edge("export", END)
        print(f"{label:<16} ->", g.compile().invoke({"verdict": "pending"}))
    except Exception as e:
        print(f"{label:<16} -> {type(e).__name__}: {str(e).splitlines()[0]}")

run("returns a str", lambda s: "flag")
run("reads missing", lambda s: {"verdict": s["risk"]})
run("typo in key", lambda s: {"verdikt": "flag"})
run("forgot return", lambda s: None)
run("route typo", lambda s: {"verdict": "flag"}, route=lambda s: "exprot")

@@ concept
title: stream: see what each step did
--- body
`invoke` gives only the final state. To see "which node changed what in each step", use `stream`:

- `stream_mode="updates"`: each time a node finishes, you get one `{node name: its update}`. When a node wrote nothing into the state (it returned `None`, or the key name was misspelled and dropped), the update here is `None`
- `stream_mode="values"`: after each step you get the **full state** once, and the first one is the input itself (a step that wrote nothing into the state gives nothing)
- Both: `stream_mode=["updates", "values"]`, and each item is a `(mode, data)` tuple

When you debug "silent errors", one look at the updates tells you: a node that should appear doesn't (a misspelled route), or some node's update is `None` (a misspelled key). On Day 34 you'll use it to push progress to the front end. On a real machine, the order of the updates from parallel branches can differ from run to run; don't rely on it.
--- code
from typing import Literal, TypedDict
from langgraph.graph import StateGraph, START, END

class State(TypedDict, total=False):
    text: str
    verdict: str
    exported: bool

def review(state):
    return {"verdict": "redline" if "unlimited" in state["text"] else "accept"}

def route(state) -> Literal["approve", "export"]:
    return "approve" if state["verdict"] == "redline" else "export"

def approve(state):
    return {"verdikt": "approved"}   # misspelled on purpose: see what this step turns into in the updates

def export(state):
    return {"exported": True}

g = StateGraph(State)
g.add_node("review", review)
g.add_node("approve", approve)
g.add_node("export", export)
g.add_edge(START, "review")
g.add_conditional_edges("review", route)
g.add_edge("approve", "export")
g.add_edge("export", END)
app = g.compile()

for update in app.stream({"text": "Liability shall be unlimited."}, stream_mode="updates"):
    print(update)
print("--- values")
for state in app.stream({"text": "Fees are due in 30 days."}, stream_mode="values"):
    print(state)

@@ concept
title: MessagesState and add_messages
--- body
Chat history is the most common kind of state. `MessagesState` is a ready-made State with a single key, `messages`, whose reducer is `add_messages`:

- A node returns `{"messages": [new message]}`, and it is **appended** to the history
- `("user", "hi")` and `{"role": "user", "content": "hi"}` automatically become a `HumanMessage` and get an id
- A new message with the same id **replaces** the old one; `RemoveMessage(id=...)` **deletes** that message (used to trim the history)
- Need more keys? Inherit from it: `class State(MessagesState): clause_id: str`

Classic mistake: writing `messages: list` yourself (no reducer). The one new message a node returns **overwrites** the whole history, and on the next turn the model "has forgotten everything".

The system prompt usually isn't stored in the state; the node puts it at the front only for the model call (`create_agent` does the same). `ChatDeepSeek` inside a node still has thinking turned off: there are no tools here, so leaving it on wouldn't cause a 400, but simple Q&A doesn't need long thinking, and thinking tokens are billed as output; once a node binds tools to the model, it must be off (Day 31).
--- code
from langchain_core.messages import SystemMessage, AIMessage, HumanMessage, RemoveMessage
from langchain_deepseek import ChatDeepSeek
from langgraph.graph import StateGraph, START, END, MessagesState
from langgraph.graph.message import add_messages

model = ChatDeepSeek(model="deepseek-flash", extra_body={"thinking": {"type": "disabled"}})

def chat(state: MessagesState):
    reply = model.invoke([SystemMessage("You answer questions about a SaaS contract.")] + state["messages"])
    return {"messages": [reply]}

g = StateGraph(MessagesState)
g.add_node("chat", chat)
g.add_edge(START, "chat")
g.add_edge("chat", END)
app = g.compile()

out = app.invoke({"messages": [("user", "Is clause 8.1 standard?")]})
out = app.invoke({"messages": out["messages"] + [("user", "And clause 9.2?")]})
print([type(m).__name__ for m in out["messages"]])
print([m["role"] for m in MOCK.calls[-1]["body"]["messages"]])

history = [HumanMessage("Review clause 8.1", id="m1"), AIMessage("accept", id="m2")]
history = add_messages(history, [AIMessage("flag: see Section 12", id="m2")])
print([m.content for m in history])
print([m.content for m in add_messages(history, [RemoveMessage(id="m1")])])

@@ concept
title: Viewing the graph: draw_mermaid
--- body
`app.get_graph().draw_mermaid()` outputs Mermaid text; paste it into GitHub, Notion or mermaid.live to see it as a diagram. How to read it:

- `a --> b;` is a fixed edge; `a -.-> b;` is a conditional edge (a dotted line)
- `__start__` and `__end__` are `START` and `END`

Where a conditional edge can go is read from the routing function's `Literal` annotation (or the third argument). **Without an annotation it doesn't know**: in the second line below, summarise connects straight to `__end__`, and even edges like `approve --> export` are gone (the two nodes are still there, cut off like islands). The drawn graph is wrong (the graph itself still runs). One more reason to write `Literal`.

Compare it with the hand-drawn graph in the docstring at the top of `graph.py`: `load -> review -> summarise -> (redlines?) -> approve -> export`, and the other path goes from summarise straight to export. When you explain the architecture in a PR or an interview, pasting the Mermaid is much clearer than describing it in words.
--- code
from typing import Literal, TypedDict
from langgraph.graph import StateGraph, START, END

class State(TypedDict, total=False):
    redlines: int

def build(route):
    g = StateGraph(State)
    for name in ["load", "review", "summarise", "approve", "export"]:
        g.add_node(name, lambda s: {})
    g.add_edge(START, "load")
    g.add_edge("load", "review")
    g.add_edge("review", "summarise")
    g.add_conditional_edges("summarise", route)
    g.add_edge("approve", "export")
    g.add_edge("export", END)
    return g.compile()

def with_literal(state) -> Literal["approve", "export"]:
    return "approve" if state["redlines"] else "export"

def without(state):
    return "approve" if state["redlines"] else "export"

for route in [with_literal, without]:
    edges = [line.strip() for line in build(route).get_graph().draw_mermaid().splitlines() if "->" in line]
    print(route.__name__, edges)

- It raises `GraphRecursionError` after 25 steps

from typing import TypedDict
from langgraph.graph import StateGraph, START, END

class State(TypedDict, total=False):
    text: str
    clauses: list[str]
    redlines: list[str]
    summary: str

def load(state: State) -> dict:
    return {"clauses": [line for line in state["text"].split("\n") if line.strip()]}

def review(state: State) -> dict:
    return {"redlines": [c.split()[0] for c in state["clauses"] if "unlimited" in c or "any country" in c]}

def summarise(state: State) -> dict:
    return {"summary": f"{len(state['clauses'])} clauses, {len(state['redlines'])} redline(s)"}

def build_app():
    g = StateGraph(State)
    g.add_node("load", load)
    g.add_node("review", review)
    g.add_node("summarise", summarise)
    g.add_edge(START, "load")
    g.add_edge("load", "review")
    g.add_edge("review", "summarise")
    g.add_edge("summarise", END)
    return g.compile()

In the review graph, some keys should keep only the latest value (the verdict, for example), and some should collect the records from every node (notes, for example). This code has three nodes write both kinds of keys in turn; see what is left at the end.

Write the output. `verdict` has no reducer; `notes` has `operator.add`. Notice what `third` returns, and that the input to `invoke(...)` itself also goes through the reducer.

import operator
from typing import Annotated, TypedDict
from langgraph.graph import StateGraph, START, END

class State(TypedDict):
    verdict: str
    notes: Annotated[list[str], operator.add]

def first(state):
    return {"verdict": "flag", "notes": ["first"]}

def second(state):
    return {"verdict": "redline", "notes": ["second"]}

def third(state):
    return {"notes": state["notes"] + ["third"]}

g = StateGraph(State)
g.add_node("first", first)
g.add_node("second", second)
g.add_node("third", third)
g.add_edge(START, "first")
g.add_edge("first", "second")
g.add_edge("second", "third")
g.add_edge("third", END)
out = g.compile().invoke({"verdict": "accept", "notes": ["input"]})
print(out["verdict"])
print(out["notes"])

from typing import Annotated, TypedDict
from langgraph.graph import StateGraph, START, END

ORDER = {"low": 0, "medium": 1, "high": 2}

def max_risk(old, new):
    if ORDER.get(new, -1) > ORDER.get(old, -1):
        return new
    return old

    text: str
    risk: Annotated[str, max_risk]

import operator
from typing import Annotated, TypedDict
from langgraph.graph import StateGraph, START, END

ORDER = {"low": 0, "medium": 1, "high": 2}

def max_risk(old, new):
    return new if ORDER.get(new, -1) > ORDER.get(old, -1) else old

class State(TypedDict, total=False):
    text: str
    risk: Annotated[str, max_risk]
    findings: Annotated[list[str], operator.add]
    decision: str

def check(keyword, level, name):
    def node(state):
        if keyword in state["text"]:
            return {"risk": level, "findings": [name]}
        return {"risk": "low", "findings": []}
    return node

def decide(state):
    return {"decision": {"high": "redline", "medium": "flag"}.get(state["risk"], "accept")}

def build_checks():
    g = StateGraph(State)
    names = []
    for name, keyword, level in [("liability", "unlimited", "high"), ("data", "any country", "medium"), ("payment", "without notice", "medium")]:
        g.add_node(name, check(keyword, level, name))
        g.add_edge(START, name)
        names.append(name)
    g.add_node("decide", decide)
    g.add_edge(names, "decide")
    g.add_edge("decide", END)
    return g.compile()

from langchain_core.messages import RemoveMessage, SystemMessage
from langgraph.graph import StateGraph, START, END, MessagesState

def build_chat(model, keep):
    def trim(state: MessagesState):
        return {"messages": [RemoveMessage(id=m.id) for m in state["messages"][:-keep]]}

    def chat(state: MessagesState):
        reply = model.invoke([SystemMessage("You review SaaS contracts.")] + state["messages"])
        return {"messages": [reply]}

    g = StateGraph(MessagesState)
    g.add_node("trim", trim)
    g.add_node("chat", chat)
    g.add_edge(START, "trim")
    g.add_edge("trim", "chat")
    g.add_edge("chat", END)
    return g.compile()
