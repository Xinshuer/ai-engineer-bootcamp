@@ concept
title: JOIN: connect tables
--- body
Tables are connected by "keys": `reviews.contract_id` points to `contracts.id`, and `contracts.customer_id` points to `customers.id`. `JOIN ... ON ...` puts the rows of two tables whose keys match together into one row, just like looking up an id in a dictionary in Python: `contracts_by_id[review["contract_id"]]`.

- Give tables short aliases: `FROM reviews r JOIN contracts c`, then write `r.clause_id`, `c.title`
- Both tables have an `id` column, so writing just `id` gives the error `ambiguous column name`: put the alias in front
- `ON` says **how the two tables match up**, `WHERE` says **which rows you want**. For JOIN the result is the same wherever you put a condition, but keeping them apart is clearer (with LEFT JOIN it is different; see the next card)
- `JOIN` is `INNER JOIN`: only rows that match on both sides stay
- To connect three tables, write two JOINs, each with its own ON
--- code
SELECT r.id, c.title, r.clause_id, r.verdict, r.model
FROM reviews r
JOIN contracts c ON c.id = r.contract_id
WHERE r.clause_id = '8.1';

@@ concept
title: LEFT JOIN: keep rows without a match
--- body
Customer 6 (Amsterdam Data BV, which only signed up on August 30) has no contracts yet. After `customers JOIN contracts`, it disappears. **LEFT JOIN** keeps every row of the left table, and fills the right table's columns with NULL where nothing matches.

- To count "how many contracts each customer has", write `COUNT(c.id)`: a customer without contracts still has one row (all NULL on the right), and `COUNT(*)` would count it as 1
- The classic bug: putting a condition on the right-hand table in WHERE, for example `WHERE c.status = 'reviewed'`. In the row without a contract, `c.status` is NULL, so WHERE drops it, and the LEFT JOIN quietly turns into a JOIN
- The right way: **put conditions on the right-hand table in ON**: `LEFT JOIN contracts c ON c.customer_id = cu.id AND c.status = 'reviewed'`

Run the example below and look at the last row: the customer is still there, and the contract columns are all NULL.
--- code
SELECT cu.name, c.id AS contract_id, c.title, c.status
FROM customers cu
LEFT JOIN contracts c ON c.customer_id = cu.id
ORDER BY cu.id, c.id;

@@ concept
title: JOIN fan-out: why the total doubled
--- body
One contract has many reviews. After `contracts JOIN reviews`, every column of a contract is **copied** onto each of its reviews (this is called fan-out): contract 101 has 12 reviews, so its `pages` (12 pages) shows up 12 times, and `SUM(c.pages)` comes out as 144 instead of 12.

The fix: **aggregate first, then JOIN**. First summarize reviews into "one row per contract", written in parentheses as a temporary table (give it an alias, so you can refer to it later as `rs.contract_id`), then JOIN it with contracts. Both sides have one row per contract, so nothing fans out:

```sql
JOIN (SELECT contract_id, COUNT(*) AS n
      FROM reviews
      GROUP BY contract_id) rs ON rs.contract_id = c.id
```

When an interviewer asks "why did this total double?", your first thought should be: the JOIN multiplied the rows.
--- code
SELECT c.id,
       c.pages,
       COUNT(*) AS rows_after_join,
       SUM(c.pages) AS wrong_pages
FROM contracts c
JOIN reviews r ON r.contract_id = c.id
GROUP BY c.id, c.pages
ORDER BY c.id;

@@ concept
title: Subqueries: IN, EXISTS, and a single value
--- body
You can put a query inside a query (in parentheses). This is called a **subquery**:

- `WHERE id IN (SELECT contract_id FROM reviews WHERE model = 'deepseek-v4-pro')`: first compute a set of values, then check whether the value is among them
- `WHERE EXISTS (SELECT 1 FROM ... WHERE ... = a column of the outer query)`: only asks "is there any?", and one row found is enough; `NOT EXISTS` finds "none at all"
- **Scalar subquery**: a subquery that returns a single value can be used like a number, for example to compute a percentage of the total: `SUM(cost_usd) / (SELECT SUM(cost_usd) FROM reviews)`
- Trap: if `NOT IN (subquery)` meets even one NULL, it returns no rows at all (yesterday's NULL rules). To find "none", `NOT EXISTS` is safer
--- code
SELECT topic,
       ROUND(SUM(cost_usd), 6) AS cost,
       ROUND(100.0 * SUM(cost_usd) / (SELECT SUM(cost_usd) FROM reviews), 1) AS pct_of_total
FROM reviews
GROUP BY topic
ORDER BY cost DESC;

@@ concept
title: CTE: name each step with WITH
--- body
Once a query gets long, parentheses inside parentheses become unreadable. `WITH` gives each step a name (a **CTE**, short for common table expression), and you read it from top to bottom, like computing a few intermediate variables first in Python:

```sql
WITH per_contract AS (
  SELECT contract_id, COUNT(*) AS reviews
  FROM reviews
  GROUP BY contract_id
)
SELECT ... FROM per_contract p JOIN contracts c ON c.id = p.contract_id
```

- You can write several, separated by commas: `WITH a AS (...), b AS (...)`; later ones can use earlier ones
- A column computed in a CTE (for example `reviews`) is a normal column in the outer query, so you can put it straight into WHERE
- It is the same thing as the subquery in the "JOIN fan-out" card (in parentheses after FROM / JOIN, with an alias), except that it has a name and comes first. Postgres, BigQuery and SQLite all support it, and it is the first choice for long queries in interviews

The example below is the most typical use of a CTE: two different statistics, each first aggregated into "one row per contract", then JOINed together (connecting all three tables directly and then counting would fan out again).
--- code
WITH review_stats AS (
  SELECT contract_id, COUNT(*) AS reviews
  FROM reviews
  GROUP BY contract_id
),
tool_stats AS (
  SELECT r.contract_id, COUNT(*) AS tool_calls
  FROM tool_calls t
  JOIN reviews r ON r.id = t.review_id
  GROUP BY r.contract_id
)
SELECT rs.contract_id, rs.reviews, COALESCE(ts.tool_calls, 0) AS tool_calls
FROM review_stats rs
LEFT JOIN tool_stats ts ON ts.contract_id = rs.contract_id
ORDER BY rs.contract_id;

@@ concept
title: Window functions: every row stays
--- body
GROUP BY **squeezes a group of rows into one row**; a window function **keeps every row**, and just adds a column next to each row that says "how this row stands within its group":

```sql
ROW_NUMBER() OVER (PARTITION BY contract_id ORDER BY cost_usd DESC)
```

- `PARTITION BY`: what to group by (leave it out and the whole table is one group); `ORDER BY`: how to sort within the group
- `ROW_NUMBER()`: 1, 2, 3, 4; ties still get different numbers
- `RANK()`: ties get the same rank, and the numbers after them are skipped: 1, 2, 2, 4
- `DENSE_RANK()`: ties get the same rank, and nothing is skipped: 1, 2, 2, 3
- Aggregate functions can take OVER too: `SUM(cost_usd) OVER (PARTITION BY contract_id)` is the total cost of the whole contract, placed next to each row

Window functions are computed only at the SELECT step, so they **can't go in WHERE** (WHERE runs earlier). To filter on one, put it in a CTE first.
--- code
SELECT contract_id, clause_id, cost_usd,
       ROW_NUMBER() OVER (PARTITION BY contract_id ORDER BY cost_usd DESC) AS rn,
       ROUND(cost_usd / SUM(cost_usd) OVER (PARTITION BY contract_id), 2) AS share_of_contract
FROM reviews
WHERE contract_id IN (104, 108)
ORDER BY contract_id, rn;

@@ concept
title: The latest row per group
--- body
Clause 8.1 of contract 103 was reviewed twice: on August 12 the v1 prompt gave it redline, and on September 18 it was run again with v2 and got flag. Clause 8.1 of contract 109 failed with a 429 the first time, and succeeded when it was run again later. In a report, each clause should count only its **latest** review.

"Take the latest / largest row of each group" is a very common interview question. The recipe has two steps:

1. In a CTE, number each group from newest to oldest: `ROW_NUMBER() OVER (PARTITION BY contract_id, clause_id ORDER BY created_at DESC) AS rn`
2. In the outer query: `WHERE rn = 1`

`GROUP BY` + `MAX(created_at)` alone only gets you the latest time; to get that row's verdict you would have to JOIN back to the original table. ROW_NUMBER does it in one step. Note: SQLite has a special rule. In `SELECT clause_id, verdict, MAX(created_at) ... GROUP BY clause_id`, the ungrouped `verdict` comes from the row with the largest time, so it gives the right result on this page; but in Postgres and BigQuery this is invalid and fails with an error. Don't write it.

BigQuery has a shorter `QUALIFY`. It can't run on this page (SQLite doesn't support it), so just learn to recognize it (for illustration only):

```sql
SELECT clause_id, verdict
FROM `clausecheck.reviews`
WHERE contract_id = 103
QUALIFY ROW_NUMBER() OVER (PARTITION BY clause_id ORDER BY created_at DESC) = 1
```
--- code
WITH ranked AS (
  SELECT id, contract_id, clause_id, verdict, prompt_version, created_at,
         ROW_NUMBER() OVER (PARTITION BY contract_id, clause_id
                            ORDER BY created_at DESC) AS rn
  FROM reviews
  WHERE clause_id = '8.1'
)
SELECT *
FROM ranked
ORDER BY contract_id, rn;
-- add WHERE rn = 1 before the ORDER BY line, then run it again

@@ concept
title: LAG and running totals
--- body
- `LAG(latency_ms) OVER (ORDER BY created_at)`: the value from the **previous row** (the first row has no previous row, so it is NULL); `LEAD` takes the next row. Use it to compute "how much did it change since last time"
- `SUM(cost_usd) OVER (ORDER BY created_at)`: adds everything from the first row up to the current row, which is a **running total**. A small detail: rows with the same sort value (for example two in the same second) are added in together and get the same running total
- Add `PARTITION BY contract_id`, and each contract gets its own separate calculation

To summarize by day or by month, first turn the time into a date: in SQLite, `date(created_at)` gives `'2026-09-05'`, and `strftime('%Y-%m', created_at)` gives `'2026-09'`. Postgres writes `created_at::date` and `date_trunc('month', created_at)`; BigQuery writes `DATE(created_at)` and `DATE_TRUNC(DATE(created_at), MONTH)` (Day 25).
--- code
SELECT id, clause_id, model, latency_ms,
       LAG(latency_ms) OVER (ORDER BY created_at) AS prev_ms,
       latency_ms - LAG(latency_ms) OVER (ORDER BY created_at) AS change_ms,
       ROUND(SUM(cost_usd) OVER (ORDER BY created_at), 6) AS running_cost
FROM reviews
WHERE contract_id = 103
ORDER BY created_at;

`tool_calls` records the tools called during each review. The argument `args` is a piece of JSON text, for example `'{"clause_id": "12"}'`. SQLite gets the value out with `json_extract(args, '$.clause_id')` (BigQuery writes `JSON_VALUE(args, '$.clause_id')`; Day 24 covers JSON columns in more detail).

--- solution
SELECT t.review_id,
       r.clause_id,
       json_extract(t.args, '$.clause_id') AS requested,
       t.ok
FROM tool_calls t
JOIN reviews r ON r.id = t.review_id
WHERE t.tool = 'get_clause'
ORDER BY t.review_id;
--- hints
- Every tool call belongs to one review: `JOIN reviews r ON r.id = t.review_id`.
- `json_extract(t.args, '$.clause_id') AS requested`, then add `WHERE t.tool = 'get_clause'`.
- The failed call (`ok` is 0) wanted clause 99. The tool couldn't find it: the highest clause reviewed in contract 103 is 15.4, so the model most likely made up this cross-reference. @@ item d23-05
type: choice
title: Counting after a LEFT JOIN
level: 2
cards: LEFT JOIN: keep rows without a match; d22:Aggregates: turn many rows into one number
--- context
The monthly report lists how many contracts each customer has, and a customer who just signed up and hasn't uploaded a contract yet (Amsterdam Data BV) is in the customers table too. Before you write this kind of statistic, get clear on what the query gives for such a customer.
--- prompt
Customer 6, Amsterdam Data BV, has no contracts yet. In the query below, what is `n` in its row? And what if you replace `LEFT JOIN` with `JOIN`?
--- code
SELECT cu.name, COUNT(*) AS n
FROM customers cu
LEFT JOIN contracts c ON c.customer_id = cu.id
GROUP BY cu.id, cu.name;
--- options
- With LEFT JOIN, `n` is 1; with JOIN, the row doesn't appear
- With LEFT JOIN, `n` is 0; with JOIN, `n` is still 0
- With LEFT JOIN, `n` is NULL; with JOIN, the row doesn't appear
- `n` is 1 both ways
answer: 1
--- explain
LEFT JOIN keeps this customer, and the right-hand columns are all NULL, but it is still **one row**. `COUNT(*)` counts rows, so it is 1. Only `COUNT(c.id)` (which counts only values that are not NULL) gives 0. JOIN keeps only rows that match on both sides, so a customer without contracts disappears completely. Yet in a report, "customers with 0 contracts" are often the ones most worth attention: they just signed up and haven't really started using it.

Run it, find the cause, and fix it. Three columns `name`, `pages`, `reviews`, sorted by `name` (only customers that have contracts).

Note: the database for this exercise has one extra contract, 111 (CloudNotes Inc's `Mutual NDA (Renewal)`, 3 pages, 1 review), so 108 and 111 both have 3 pages.
--- schema
INSERT INTO contracts VALUES (111, 4, 'Mutual NDA (Renewal)', '2026-09-20 10:00:00', 3, 'reviewed');
INSERT INTO reviews VALUES (1066, 111, '6.2', 'Duration of Confidentiality', 'confidentiality', 'redline', 'medium', '["PB-06"]', 'deepseek-v4-flash', 'v2', 2702, 201, 0, 1804, 0.001052, NULL, '2026-09-20 10:02:05');

       SUM(c.pages) AS pages,
       SUM(rs.n) AS reviews
FROM customers cu
JOIN contracts c ON c.customer_id = cu.id
JOIN (SELECT contract_id, COUNT(*) AS n
      FROM reviews
      GROUP BY contract_id) rs ON rs.contract_id = c.id
GROUP BY cu.id, cu.name

--- hints
- After JOIN reviews, every column of a contract is copied onto each of its reviews: contract 101 has 12 reviews, so its 12 pages are added 12 times (12 × 12 + 6 × 5 + 2 × 2 = 178).

type: sql
title: CTE: contracts that need a person
level: 2
ordered: yes
cards: CTE: name each step with WITH; d22:CASE WHEN: labels and conditional counts
--- context
Lawyers look first at the contracts with the most problems: clauses the model didn't accept and reviews that failed all end up needing a person to handle them.
--- prompt
Write it in two steps with `WITH`:

1. `per_contract`: one row per contract, `contract_id`, `reviews` (the number of reviews), `attention` (the number that need a person: the verdict is not accept, **failed ones count too**)
2. The outer query: JOIN `contracts` to get `title`, and keep only contracts where `attention` is at least 2

Return three columns `title`, `reviews`, `attention`, sorted by `attention` from most to fewest, ties by `title`.
--- solution
WITH per_contract AS (
  SELECT contract_id,
         COUNT(*) AS reviews,
         SUM(CASE WHEN verdict = 'accept' THEN 0 ELSE 1 END) AS attention
  FROM reviews
  GROUP BY contract_id
)
SELECT c.title, p.reviews, p.attention
FROM per_contract p
JOIN contracts c ON c.id = p.contract_id
WHERE p.attention >= 2
ORDER BY p.attention DESC, c.title;
--- hints
- "Not accept, and failed ones count too": `SUM(CASE WHEN verdict = 'accept' THEN 0 ELSE 1 END)`. Writing it the other way round, `CASE WHEN verdict <> 'accept' THEN 1 ELSE 0 END`, misses NULL (yesterday's trap).
- The outer query treats the CTE like a normal table: `FROM per_contract p JOIN contracts c ON c.id = p.contract_id`.
- `attention`, computed in the CTE, is a normal column in the outer query, so just write `WHERE p.attention >= 2`.

--- code
WITH topic_problems AS (
  SELECT topic, COUNT(*) AS problems
  FROM reviews
  WHERE verdict IN ('flag', 'redline')
  GROUP BY topic
  HAVING COUNT(*) >= 3
)
SELECT topic, problems,
       ROW_NUMBER() OVER (ORDER BY problems DESC, topic) AS rn,
       RANK() OVER (ORDER BY problems DESC) AS rnk,
       DENSE_RANK() OVER (ORDER BY problems DESC) AS drnk
FROM topic_problems;
--- options
- `5, 5, 3`
- `5, 3, 3`
- `3, 3, 3`
- `5, 5, 5`
answer: 1
--- explain
Three topics tie at 4. `ROW_NUMBER` ignores ties and numbers the rows 1 to 5 no matter what, so it is 5; `RANK` puts all three tied topics at rank 2 and skips the numbers after them, so the next one is rank 5; `DENSE_RANK` skips nothing, so the next one is rank 3. How to choose: for "only one row per group" (for example the latest row per group), use `ROW_NUMBER`, which guarantees exactly one 1; for "the top three, ties included", use `RANK` or `DENSE_RANK`.
