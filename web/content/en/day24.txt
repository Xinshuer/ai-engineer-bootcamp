title: CREATE TABLE: rules for your data
lang: sql
dataset: clausecheck
--- body
A table is not just a grid that holds data. The **constraints** you write when you create a table are the last gate before bad data gets in: now and then the model returns `risk_level: "critical"` (that is exactly how review 1047 in the sample data failed), and a value like that should never get into the database. Below is the lawyer feedback table `feedback`, already created:

```sql
CREATE TABLE feedback (
  id INTEGER PRIMARY KEY,
  review_id INTEGER NOT NULL REFERENCES reviews(id),
  reviewer TEXT NOT NULL,
  verdict TEXT NOT NULL CHECK (verdict IN ('accept', 'flag', 'redline')),
  note TEXT,
  created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
  UNIQUE (review_id, reviewer)
);
```

- Types: `INTEGER`, `TEXT`, `REAL` (decimal numbers)
- `PRIMARY KEY`: each row's unique number. In SQLite, an `INTEGER PRIMARY KEY` that is given no value takes the next number automatically (Postgres doesn't; there you write `BIGINT GENERATED ALWAYS AS IDENTITY` or `BIGSERIAL`)
- `NOT NULL`: must have a value; `DEFAULT`: the value used when none is given; `UNIQUE`: no repeats (it can be a combination of several columns); `CHECK (...)`: the value must meet the condition
- `REFERENCES reviews(id)`: a **foreign key**; it must point to a row that really exists in reviews
- One table per kind of thing: customers, contracts, reviews and feedback each get their own table, connected by ids (yesterday's JOIN)

Two SQLite traps: foreign keys are **not checked** by default, so run `PRAGMA foreign_keys = ON` first; and types are loose, so you can store `'abc'` in an INTEGER column. Postgres is strict about both.

Run the insert below, then change `'accept'` to `'maybe'`, or delete the `reviewer` column together with its value `'anna'`, run it again, and read the error.
--- schema
CREATE TABLE feedback (
  id INTEGER PRIMARY KEY,
  review_id INTEGER NOT NULL REFERENCES reviews(id),
  reviewer TEXT NOT NULL,
  verdict TEXT NOT NULL CHECK (verdict IN ('accept', 'flag', 'redline')),
  note TEXT,
  created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
  UNIQUE (review_id, reviewer)
);
--- code

VALUES (1005, 'anna', 'accept', 'A 12-month cap is fine for this customer')
RETURNING *;

title: INSERT, UPDATE, DELETE: SELECT first, then change
lang: sql
dataset: clausecheck
--- body
Three statements that change data:

```sql
INSERT INTO customers (name, country, plan, signed_up)
VALUES ('Oslo Maritime AS', 'NO', 'pro', '2026-09-20');
UPDATE contracts SET status = 'reviewed' WHERE id = 109;
DELETE FROM reviews WHERE id = 1061;
```

- With INSERT, **always write the column names**; don't rely on the order of the columns in the table. Columns you leave out get their DEFAULT, or NULL if there is no default. Several rows at once: `VALUES (...), (...)`; you can also insert from a query: `INSERT INTO table (columns) SELECT ...`
- The most dangerous mistake with UPDATE / DELETE is **forgetting the WHERE**: the whole table gets changed or deleted
- A good habit: first write `SELECT * FROM contracts WHERE id = 109`, look closely at which rows it selects, then replace the first half with `UPDATE ... SET ...` or `DELETE`
- Add `RETURNING columns` at the end to get the changed rows straight back so you can look at them (Postgres and SQLite both support it)

Clause 8.1 of contract 109 later succeeded on a retry (review 1065), so below we change the contract's status from failed back to reviewed. Every run on this page starts from a fresh copy of the sample data, so change whatever you like: try removing the WHERE line and see how many rows RETURNING gives back.
--- code
UPDATE contracts
SET status = 'reviewed'
WHERE id = 109
RETURNING id, title, status;

title: UPSERT: safe to run again
lang: sql
dataset: clausecheck
--- body
After a worker crashes, it reruns a contract (Day 17's idempotency): the result for the same clause is written a second time. The table `latest_verdicts` has `(contract_id, clause_id)` as its primary key, so a plain INSERT runs into `UNIQUE constraint failed` the second time.

**UPSERT**: insert if the row doesn't exist, update it if it already does.

```sql
INSERT INTO table (columns...) VALUES (...)
ON CONFLICT (primary key or UNIQUE columns) DO UPDATE SET column = excluded.column;
```

- `excluded.verdict` means the value from "the row you tried to insert this time, the one that collided"
- The columns in `ON CONFLICT (...)` must be exactly one PRIMARY KEY or UNIQUE constraint, or you get an error
- `ON CONFLICT (...) DO NOTHING`: skip the row if it's already there
- This is Postgres syntax; SQLite copied it, so it works in both; in BigQuery the equivalent is `MERGE`

The table already has `(103, '8.1', 'redline', 1022)`; below, we update it with the result of re-review 1064. Change `'8.1'` to `'8.2'` and run again: this time it inserts a new row.
--- schema
CREATE TABLE latest_verdicts (
  contract_id INTEGER NOT NULL,
  clause_id TEXT NOT NULL,
  verdict TEXT NOT NULL,
  review_id INTEGER NOT NULL,
  PRIMARY KEY (contract_id, clause_id)
);
INSERT INTO latest_verdicts VALUES (103, '8.1', 'redline', 1022);
--- code
INSERT INTO latest_verdicts (contract_id, clause_id, verdict, review_id)
VALUES (103, '8.1', 'flag', 1064)
ON CONFLICT (contract_id, clause_id) DO UPDATE SET
  verdict = excluded.verdict,
  review_id = excluded.review_id
RETURNING *;

title: sqlite3: a database from Python
dataset: clausecheck
--- body
Python comes with `sqlite3`; there is nothing to install.

- `conn = sqlite3.connect("app.db")` opens a database file (and creates it if it doesn't exist); `":memory:"` is a database that lives only in memory
- `conn.execute(sql)` returns a cursor: `.fetchall()` gets all the rows (a list of tuples), `.fetchone()` gets one row, or `None` when there are no rows
- After `conn.row_factory = sqlite3.Row`, you can get a row's values by column name: `row["verdict"]`, and `dict(row)` turns the row into a dictionary. Set it right after you open the connection
- After you change data (INSERT / UPDATE / DELETE) you need `conn.commit()`: only then are the changes really written to the file, and only then can other connections (other programs) see them. Exit without committing and the changes are lost

On this page, `fresh_db()` gives you a new in-memory database with the sample data loaded, every time. Every function you write today takes `conn` as a parameter (dependency injection), so the tests can pass in a fresh database and production code passes in the real one.

The last part below opens the same file with two connections, so you can see the difference before and after commit.
--- code
import sqlite3
from pathlib import Path

conn = fresh_db()
rows = conn.execute("SELECT id, clause_id, verdict FROM reviews WHERE contract_id = 108").fetchall()
print(rows)
print(conn.execute("SELECT MAX(latency_ms) FROM reviews").fetchone())

conn.row_factory = sqlite3.Row
row = conn.execute("SELECT id, heading, risk FROM reviews WHERE id = 1022").fetchone()
print(row["heading"], row[0], dict(row))

Path("work/d24").mkdir(parents=True, exist_ok=True)
a = sqlite3.connect("work/d24/app.db")
a.execute("CREATE TABLE IF NOT EXISTS notes (text TEXT)")
a.execute("DELETE FROM notes")
a.commit()
a.execute("INSERT INTO notes VALUES ('8.1 needs a lawyer')")
b = sqlite3.connect("work/d24/app.db")
print("before commit:", b.execute("SELECT COUNT(*) FROM notes").fetchone())
a.commit()
print("after commit: ", b.execute("SELECT COUNT(*) FROM notes").fetchone())

@@ concept
title: Parameterized queries and SQL injection
dataset: clausecheck
--- body
Customer names, topics, filters: they all come from users or from the model. Day 12's prompt injection tricks the model; **SQL injection** tricks the database.

If you paste a value into SQL with an f-string, a `'` inside the value becomes part of the SQL: `O'Brien Legal` turns the statement into a syntax error; `x' OR '1'='1` makes the WHERE always true and returns every customer. Some drivers let you run several statements at once (for example psycopg for Postgres), and then even a "drop the table" like `'; DROP TABLE customers; --` can sneak in. The `execute` of Python's `sqlite3` runs only one statement at a time, which blocks the table drop, but the two attacks above still work.

**Parameterized**: the SQL contains only placeholders, and the values are handed to the database separately. The database always treats the values as data and never runs them as SQL:

- `?` with a tuple: `conn.execute("... WHERE name = ?", (name,))`. Even a single value must be written `(name,)`; `(name)` is just a string
- `:name` with a dictionary: `conn.execute("... WHERE contract_id = :cid", {"cid": 103})`
- Placeholders can only stand for **values**. Table names, column names and `ASC` / `DESC` can't be parameters: first check that the name is on an allowlist, then paste it into the SQL
- In Postgres, psycopg writes placeholders as `%s`; BigQuery writes `@name`. The idea is exactly the same
--- code
conn = fresh_db()

def find_unsafe(name):
    sql = f"SELECT id, name FROM customers WHERE name = '{name}'"
    return conn.execute(sql).fetchall()

def find(name):
    return conn.execute("SELECT id, name FROM customers WHERE name = ?", (name,)).fetchall()

print(find_unsafe("Nordlys AB"))
print(len(find_unsafe("x' OR '1'='1")), "rows: injected!")
try:
    find_unsafe("O'Brien Legal")
except Exception as e:
    print(type(e).__name__, e)

print(find("x' OR '1'='1"))
conn.execute("INSERT INTO customers (name, country, plan, signed_up) VALUES (?, ?, ?, ?)", ("O'Brien Legal", "IE", "pro", "2026-09-22"))
print(find("O'Brien Legal"))
print(conn.execute("SELECT id FROM reviews WHERE contract_id = :cid AND risk = :risk", {"cid": 101, "risk": "high"}).fetchall())

@@ concept
title: Transactions: all or nothing
dataset: clausecheck
--- body
A contract has 12 review results, and writing fails at the 7th: the database is left with 6 rows, "half a report". That is worse than writing none at all, because it looks as if the review is finished.

A **transaction** ties a group of changes together: either they all take effect, or they are all undone.

- Everything in a `with conn:` block succeeds → automatic `commit`; an exception is raised → automatic `rollback`, and the exception keeps going up
- `with conn:` **does not close the connection**. That is different from `with open(...)`, and it is the most common misunderstanding
- You can do it without `with` too: `conn.commit()` on success, `conn.rollback()` on error
- `executemany(sql, many sets of parameters)` inserts many rows with the same SQL. If it fails partway, the earlier rows have actually already run; they just aren't committed yet: without a rollback, the same connection can still see them, and the next commit writes them in along with everything else

The first batch below has one bad row (`maybe` is not one of the values the CHECK allows), so the whole batch is undone; the second batch has only good rows and is written successfully.
--- code
import sqlite3

conn = fresh_db()
conn.execute("CREATE TABLE feedback (review_id INTEGER NOT NULL, reviewer TEXT NOT NULL, verdict TEXT NOT NULL CHECK (verdict IN ('accept', 'flag', 'redline')))")
rows = [
    (1062, "anna", "accept"),
    (1063, "anna", "flag"),
    (1064, "anna", "maybe"),
]

try:
    with conn:
        conn.executemany("INSERT INTO feedback VALUES (?, ?, ?)", rows)
except sqlite3.IntegrityError as e:
    print("rolled back:", e)
print("rows:", conn.execute("SELECT COUNT(*) FROM feedback").fetchone()[0])

with conn:
    conn.executemany("INSERT INTO feedback VALUES (?, ?, ?)", rows[:2])
print("rows:", conn.execute("SELECT COUNT(*) FROM feedback").fetchone()[0])

title: JSON columns: json_extract and json_each
lang: sql
dataset: clausecheck
--- body
Two columns in the sample data hold JSON text: `reviews.rule_ids` looks like `'["PB-01", "PB-02"]'`, and `tool_calls.args` looks like `'{"topic": "payment"}'`. SQLite can read them directly:

- `json_extract(args, '$.topic')` (or `args ->> '$.topic'`) gets one field
- `json_array_length(rule_ids)`: how many elements the array has
- `json_each(rule_ids)` "explodes" an array into rows, one row per element, with the element in the `value` column. It goes in FROM and works like JOINing another table: `FROM reviews AS r, json_each(r.rule_ids) AS j`. In BigQuery the same thing is called `UNNEST`

When should you not use a JSON column, and split the data into a separate table instead (for example `review_rules(review_id, rule_id)`, one row per citation)? When you need to **filter, count or JOIN** on it, add **constraints** (every rule_id must really exist), or add an **index**. For things you only store as a whole and read as a whole (the model's full reply, tool arguments), a JSON column is a good fit.

Below, we expand the rules cited by each review of contract 101: review 1005 cites two rules, so it appears twice.
--- code
SELECT r.id, r.clause_id, j.value AS rule_id
FROM reviews AS r, json_each(r.rule_ids) AS j
WHERE r.contract_id = 101
ORDER BY r.id;

@@ concept
title: Production: Postgres, pgvector, and indexes
dataset: clausecheck
--- body
SQLite is a single file, good for one machine, tests and small tools (the project's checkpoints use it). The database behind a production app is usually **Postgres**: many services read and write at the same time, and it has permissions and backups. Today's SQL runs in Postgres almost unchanged. The differences: types are strict, foreign keys are always checked, auto-increment primary keys are written `GENERATED ALWAYS AS IDENTITY`, `LIKE` is case-sensitive, JSON uses `JSONB`, and times with a time zone use `TIMESTAMPTZ`. In Python you use psycopg (placeholder `%s`) or SQLAlchemy; in TypeScript, Prisma, Drizzle or node-postgres (placeholder `$1`).

**pgvector** is a Postgres extension that can store embeddings, which moves Day 11's RAG into the database:

```sql
CREATE EXTENSION vector;
CREATE TABLE chunks (id BIGSERIAL PRIMARY KEY, text TEXT, embedding vector(1536));
CREATE INDEX ON chunks USING hnsw (embedding vector_cosine_ops);
SELECT id, text FROM chunks ORDER BY embedding <=> %s LIMIT 5;
```

`<=>` is the **cosine distance** (1 − cosine similarity; the smaller, the more similar); 1536 is the length of a `text-embedding-3-small` vector. What goes into `%s` is the embedding of the question: in Python, first install the `pgvector` package and call `register_vector(conn)` once on the connection (`from pgvector.psycopg import register_vector`), so that psycopg understands the vector type (the pgvector docs are what counts).

An **index** works like the index at the back of a book: without one, finding rows by `contract_id` means scanning the whole table (SCAN); with one, the database jumps straight to them (SEARCH ... USING INDEX). The cost: writes get a little slower and it takes more space. `EXPLAIN QUERY PLAN` (`EXPLAIN` in Postgres) tells you how the database plans to run a query.
--- code
conn = fresh_db()
q = "SELECT id, verdict FROM reviews WHERE contract_id = ?"

def plan():
    return [row[3] for row in conn.execute("EXPLAIN QUERY PLAN " + q, (103,))]

print(plan())
conn.execute("CREATE INDEX idx_reviews_contract ON reviews (contract_id)")
print(plan())
print(conn.execute(q, (103,)).fetchall()[:3])

--- context
Today you start writing data into the database, so first warm up with the queries from the last two days. Contracts with many redlines are the hardest to negotiate, so the lawyers need to put people on them first.
--- prompt
Review Days 22 and 23: find the contracts with **at least 2** redlines. Return four columns: `contract_id`, `title`, `customer` (the customer's name) and `redlines` (the number of redlines), sorted by redlines from most to fewest, ties by contract_id from smallest to largest.
--- solution
SELECT c.id AS contract_id, c.title, cu.name AS customer, COUNT(*) AS redlines
FROM reviews AS r
JOIN contracts AS c ON c.id = r.contract_id
JOIN customers AS cu ON cu.id = c.customer_id
WHERE r.verdict = 'redline'
GROUP BY c.id, c.title, cu.name
HAVING COUNT(*) >= 2
ORDER BY redlines DESC, contract_id;
--- hints
- Two JOINs: reviews → contracts → customers; first use WHERE to keep only the redline rows.
- Group by contract (every non-aggregate column in SELECT goes into GROUP BY); "at least 2" is a condition on the groups, so it goes in HAVING.
- Finally `ORDER BY redlines DESC, contract_id`.

type: code
title: Constraints stop bad data
level: 2
dataset: clausecheck
cards: CREATE TABLE: rules for your data
--- context
Day 18's workflow stops before exporting the rewrites and waits for a lawyer to approve or reject them. That decision has to be stored reliably: the later steps use it to decide whether to really change the contract.
--- prompt
In Day 18's workflow, a lawyer has to approve or reject each redline. Store the decisions in the table `approvals`: write the CREATE TABLE statement in the string `SCHEMA`. Requirements:

- `id`: INTEGER, primary key
- `review_id`: INTEGER, required, a foreign key to `reviews(id)`; **each review can have only one decision** (UNIQUE)
- `decision`: TEXT, required, only `'approved'` or `'rejected'`
- `approver`: TEXT, required
- `decided_at`: TEXT, required, default `CURRENT_TIMESTAMP`

The tests take a fresh database with the sample data, first run `PRAGMA foreign_keys = ON`, then run your `SCHEMA`, and then insert one good row and all kinds of bad rows: the database must reject every bad row (raise `sqlite3.IntegrityError`). The starter code's table can be created, but it stops nothing.
--- starter
SCHEMA = """
CREATE TABLE approvals (
  id INTEGER PRIMARY KEY,
  review_id INTEGER,
  decision TEXT,
  approver TEXT,
  decided_at TEXT
);
"""
--- solution
SCHEMA = """
CREATE TABLE approvals (
  id INTEGER PRIMARY KEY,
  review_id INTEGER NOT NULL UNIQUE REFERENCES reviews(id),
  decision TEXT NOT NULL CHECK (decision IN ('approved', 'rejected')),
  approver TEXT NOT NULL,
  decided_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP
);
"""
--- tests
import sqlite3
def _db():
    conn = fresh_db()
    conn.execute("PRAGMA foreign_keys = ON")
    conn.executescript(SCHEMA)
    return conn
def _ins(conn, review_id, decision, approver):
    conn.execute("INSERT INTO approvals (review_id, decision, approver) VALUES (?, ?, ?)", (review_id, decision, approver))
def _try(review_id, decision, approver, first=None):
    conn = _db()
    if first:
        _ins(conn, *first)
    try:
        _ins(conn, review_id, decision, approver)
    except sqlite3.IntegrityError:
        return "rejected"
    return "accepted"
def _good():
    conn = _db()
    _ins(conn, 1005, "approved", "anna")
    return conn.execute("SELECT review_id, decision, approver, decided_at IS NOT NULL FROM approvals").fetchall()
expect("good data goes in, decided_at is filled in automatically", _good, [(1005, "approved", "anna", 1)])
expect("decision is not an allowed value", lambda: _try(1005, "maybe", "anna"), "rejected")
expect("decision is NULL (CHECK lets NULL through; only NOT NULL stops it)", lambda: _try(1005, None, "anna"), "rejected")
expect("approver is NULL", lambda: _try(1005, "approved", None), "rejected")
expect("review_id is NULL (the foreign key and UNIQUE both let NULL through)", lambda: _try(None, "approved", "anna"), "rejected")
expect("a second decision for the same review", lambda: _try(1005, "rejected", "ben", first=(1005, "approved", "anna")), "rejected")
expect("review_id does not exist in reviews (foreign key)", lambda: _try(9999, "approved", "anna"), "rejected")
expect("a decision for another review can be inserted", lambda: _try(1022, "rejected", "ben", first=(1005, "approved", "anna")), "accepted")
--- hints
- One column can have several constraints, written one after another: `review_id INTEGER NOT NULL UNIQUE REFERENCES reviews(id)`.
- Limit the values with `CHECK (decision IN ('approved', 'rejected'))`; set the default with `DEFAULT CURRENT_TIMESTAMP`.
- Foreign keys are only checked when `PRAGMA foreign_keys = ON`; the tests already turned it on for you. Watch out for NULL: `CHECK`, `UNIQUE` and foreign keys all ignore NULL, so only `NOT NULL` can make a column required.

SQL = (
    "INSERT INTO latest_verdicts (contract_id, clause_id, verdict, risk, review_id) "
    "VALUES (:contract_id, :clause_id, :verdict, :risk, :review_id) "
    "ON CONFLICT (contract_id, clause_id) DO UPDATE SET "
    "verdict = excluded.verdict, risk = excluded.risk, review_id = excluded.review_id"
)

def save_reviews(conn, reviews):
    with conn:
        conn.executemany(SQL, reviews)
    return len(reviews)

--- solution
def search_reviews(conn, topic=None, risk=None, limit=20):
    if not isinstance(limit, int) or limit < 1:
        raise ValueError("limit must be a positive integer")
    where = []
    params = []
    if topic is not None:
        where.append("topic = ?")
        params.append(topic)
    if risk is not None:
        where.append("risk = ?")
        params.append(risk)
    sql = "SELECT id FROM reviews"
    if where:
        sql += " WHERE " + " AND ".join(where)
    sql += " ORDER BY id LIMIT ?"
    params.append(limit)
    return [row[0] for row in conn.execute(sql, params).fetchall()]
