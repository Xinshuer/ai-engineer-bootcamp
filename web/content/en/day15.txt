@@ concept
title: interface and type
--- body
On Day 5 you used `type` to give an object a name. `interface` is another way to write it; for describing the shape of an object, the two are almost the same:

```ts
interface Clause { id: string; text: string }
type Verdict = "accept" | "flag" | "redline";
```

You only need to remember two differences:

- **Union types can only be written with `type`**
- An `interface` can use `extends` to build on another interface and add fields to it

TypeScript only looks at the **shape**: an object fits a type as long as its fields match, no matter where it came from. Pick one style per project and stay consistent. The convention in this course: `interface` for objects, `type` for unions.
--- code
type Verdict = "accept" | "flag" | "redline";

interface Clause {
  id: string;
  text: string;
}
interface ReviewedClause extends Clause {
  verdict: Verdict;
}

const c: ReviewedClause = { id: "8.1", text: "Liability is unlimited.", verdict: "redline" };
const plain: Clause = c; // an extra verdict field is fine: the shape matches
console.log(c.id, c.verdict);
console.log(plain.text);

@@ concept
title: Optional, read-only, and optional chaining
--- body
- `heading?: string`: this field may be missing; reading it gives the type `string | undefined`
- `readonly id: string`: can't be changed after the object is created (to make a whole object read-only, write `Readonly<Clause>`)
- `c.source?.page`: **optional chaining**. When the left side of `?.` is `null` / `undefined`, the whole expression simply gives `undefined` instead of throwing an error
- Combine it with `??` from Day 5 to give a default value: `c.source?.page ?? "?"`

The classic mistake: writing `c.heading.toUpperCase()` directly, and TypeScript reports `TS18048: 'c.heading' is possibly 'undefined'`. TypeScript isn't being fussy: fields really do go missing in model output and JSON files. An array's `find` is the same: when nothing matches, it returns `undefined`.
--- code
interface Clause {
  readonly id: string;
  heading?: string;
  source?: { file: string; page?: number };
}

const a: Clause = { id: "8.1", heading: "Cap on Liability", source: { file: "msa.pdf", page: 3 } };
const b: Clause = { id: "12" };

for (const c of [a, b]) {
  const heading = c.heading ?? "(no heading)";
  console.log(c.id, heading, c.source?.page ?? "?", c.source?.file.toUpperCase());
}
// a.id = "9.9"; // uncomment this line to try it: Cannot assign to 'id' because it is a read-only property

@@ concept
title: Union types and narrowing
--- body
`string | null` means "maybe a string, maybe null". **Check** it before you use it, and TypeScript follows your if checks and "narrows" the type:

- `x === null`, `x === undefined`
- `typeof x === "string"` (also `"number"`, `"boolean"`, `"object"`)
- `Array.isArray(x)`
- `"verdict" in obj`: does the object have this key?

Inside the if, TypeScript knows exactly what x is; once you leave the if, it's back to the union type. In VS Code on your own computer, hover the mouse over a variable to see its type on each line.

The classic trap: `typeof null` and `typeof []` both give `"object"` (old JavaScript baggage). So check for arrays with `Array.isArray`, and when checking for an object, rule out `null` as well.
--- code
function show(x: string | number | string[] | null): string {
  if (x === null) {
    return "nothing";
  }
  if (typeof x === "string") {
    return `text: ${x.toUpperCase()}`;
  }
  if (Array.isArray(x)) {
    return `list of ${x.length}`;
  }
  return `number: ${x.toFixed(1)}`; // by this point, x can only be a number
}
console.log(show("flag"));
console.log(show(["8.1", "12"]));
console.log(show(0.5));
console.log(show(null));
console.log(typeof null, typeof ["8.1"]);

@@ concept
title: Discriminated unions and exhaustiveness checks
--- body
One reply from the model can be a "final answer", a "please call a tool", or an "error", and each case carries different fields. In Clause Check's `review.py`, `Step` tells them apart with a string field `stop` (`"end"`, `"tool_use"`, `"error"` …).

TypeScript writes this as a **discriminated union**: every case has the same field (often called `kind`, `type` or `stop`), each with a different literal value. In each case of `switch (s.stop)`, TypeScript knows which kind s is, and only the `"tool_use"` branch can read `s.tool`.

**Exhaustiveness check**: in `default`, write

```ts
const unreachable: never = s;
```

`never` is the type that "can never have a value". When every case is handled, the s that reaches default is never, so there's no error. If someone later adds a fourth case but forgets to handle it, this line immediately gives a type error, and the bug is caught before the code runs.
--- code
type Step =
  | { stop: "end"; text: string }
  | { stop: "tool_use"; tool: string; args: string }
  | { stop: "error"; error: string };

function nextAction(s: Step): string {
  switch (s.stop) {
    case "end":
      return `answer: ${s.text}`;
    case "tool_use":
      return `run ${s.tool}(${s.args})`;
    case "error":
      return `give up: ${s.error}`;
    default: {
      const unreachable: never = s;
      return unreachable;
    }
  }
}

const steps: Step[] = [
  { stop: "tool_use", tool: "lookup_playbook", args: '{"topic": "payment"}' },
  { stop: "end", text: "flag: payment term unclear" },
  { stop: "error", error: "http 429" },
];
for (const s of steps) {
  console.log(nextAction(s));
}

@@ concept
title: Generics: parameters for types
--- body
Say you write a function that gets the first element: used on a `string[]` it should return a string, used on a `Clause[]` it should return a Clause. Writing `any` throws the type away. **Generics** are "parameters for types":

```ts
function first<T>(xs: T[]): T | undefined {
  return xs[0];
}
```

Read `<T>` as "for some type T". When you call it you usually don't write `first<string>(...)`: TypeScript infers T from the arguments. You've actually been using generics for a while: `Promise<string>`, `Record<string, number>`, `Array<string>`; what's inside the angle brackets is the type parameter. A type can take parameters too: `type ApiResult<T> = { ok: true; data: T } | { ok: false; error: string }`.

The classic mistake: writing `const x: T = "8.1"` inside the function. The caller decides what T is; the function itself can't assume it's a string.
--- code
function first<T>(xs: T[]): T | undefined {
  return xs[0];
}

function countBy<T>(xs: T[], key: (x: T) => string): Record<string, number> {
  const counts: Record<string, number> = {};
  for (const x of xs) {
    const k = key(x);
    counts[k] = (counts[k] ?? 0) + 1;
  }
  return counts;
}

interface Review {
  id: string;
  verdict: string;
}
const reviews: Review[] = [
  { id: "3.1", verdict: "accept" },
  { id: "8.1", verdict: "flag" },
  { id: "10.1", verdict: "flag" },
];
const none: string[] = [];
console.log(first(reviews)?.id, first(none) ?? "empty");
console.log(countBy(reviews, (r) => r.verdict));
console.log(countBy(["low", "high", "low"], (r) => r));

@@ concept
title: Utility types: derive one type from another
--- body
You can "derive" a new type from an existing one without writing it all out again:

- `Partial<Review>`: every field becomes optional; good for a "patch" (changing only a few fields)
- `Pick<Review, "id" | "verdict">`: keep only these fields
- `Omit<Review, "cost_usd">`: remove these fields
- `Record<K, V>`: you already used it on Day 5
- `ReturnType<typeof fn>`: the return type of a function (you'll see it when you read other people's code)

The most important point: **these are only types; they don't exist at run time**. `Omit` won't remove a field for you; to really remove it, your code has to build a new object. The usual way is **destructuring with a rest element**:

```ts
const { cost_usd, ...rest } = review; // rest = every field except cost_usd
```
--- code
interface Review {
  id: string;
  verdict: "accept" | "flag" | "redline";
  risk: "low" | "medium" | "high";
  cost_usd: number;
}
type ReviewPatch = Partial<Review>;
type PublicReview = Omit<Review, "cost_usd">;

const r: Review = { id: "8.1", verdict: "flag", risk: "high", cost_usd: 0.0021 };
const patch: ReviewPatch = { verdict: "redline" };
const updated: Review = { ...r, ...patch };
console.log(updated.verdict, r.verdict);

const { cost_usd, ...rest } = r;
const pub: PublicReview = rest;
console.log(Object.keys(pub), cost_usd);

@@ concept
title: unknown and type guards
--- body
`JSON.parse` returns `any`: from there on TypeScript stops checking, a misspelled field name gives no error, and things only go wrong at run time. Model output, HTTP responses and file contents are all **external data** and should be treated as `unknown`: "I don't know what this is; check it before using it".

Write the check as a **type guard** function, whose return type is written `x is Verdict`:

```ts
function isVerdict(x: unknown): x is Verdict { ... }
```

After `if (isVerdict(data))`, data inside the if is a Verdict.

Two classic mistakes:

- `data as Verdict` only **tells** the compiler "trust me"; nothing is checked at run time
- If the guard forgets to check a field, the compiler can't notice either: the guard is your own promise. When there are many fields, use Zod from Day 6: one schema does both the checking and the type, so nothing gets missed
--- code
const VERDICTS = ["accept", "flag", "redline"];
interface Verdict {
  clause_id: string;
  verdict: "accept" | "flag" | "redline";
}

function isVerdict(x: unknown): x is Verdict {
  return (
    typeof x === "object" &&
    x !== null &&
    "clause_id" in x &&
    typeof x.clause_id === "string" &&
    "verdict" in x &&
    typeof x.verdict === "string" &&
    VERDICTS.includes(x.verdict)
  );
}

const inputs = ['{"clause_id": "8.1", "verdict": "flag"}', '{"clause_id": "8.1", "verdict": "maybe"}', "null"];
for (const raw of inputs) {
  const data: unknown = JSON.parse(raw);
  if (isVerdict(data)) {
    console.log("ok:", data.clause_id, data.verdict);
  } else {
    console.log("rejected:", raw);
  }
}

@@ concept
title: as const: one list, two uses
--- body
The same list is often needed twice: at run time you need an array (to loop over it, to check values against it), and at compile time you need a union type. Write them separately and sooner or later they'll disagree. `as const` gets both from one definition:

```ts
const RISKS = ["low", "medium", "high"] as const;
type Risk = (typeof RISKS)[number]; // "low" | "medium" | "high"
```

- `as const`: the array becomes read-only, and each element's type is its exact literal rather than string
- `typeof RISKS`: the type of this **value**; `[number]`: the type of "an element you get with a number index"

The classic trap: when x is a `string`, `RISKS.includes(x)` gives an error (TypeScript thinks RISKS can only contain those three words). To check any string, write `(RISKS as readonly string[]).includes(x)`. Zod's `z.enum(RISKS)` can use this same list directly.
--- code
const RISKS = ["low", "medium", "high"] as const;
type Risk = (typeof RISKS)[number];

function isRisk(x: string): x is Risk {
  return (RISKS as readonly string[]).includes(x);
}

function rank(r: Risk): number {
  return RISKS.indexOf(r);
}

for (const raw of ["high", "urgent", "low"]) {
  if (isRisk(raw)) {
    console.log(raw, "rank", rank(raw));
  } else {
    console.log(raw, "is not a risk level");
  }
}
console.log(RISKS.length, RISKS[2]);

interface Clause {
  id: string;
  heading?: string;
}

--- context

--- code
function kindOf(x: string | number | string[] | null | undefined): string {
  if (x === null || x === undefined) {
    return "empty";
  }
  if (typeof x === "number") {
    return x > 0.5 ? "high score" : "low score";
  }
  if (Array.isArray(x)) {
    return `${x.length} ids`;
  }
  return x.trim() === "" ? "blank" : `text ${x}`;
}
console.log(kindOf(0.8), kindOf(0));

console.log(kindOf("  "), kindOf("flag"));
console.log(kindOf(null), kindOf(undefined));
console.log(typeof null, typeof [], Array.isArray([]));
--- explain
Each if rules out one possibility, so by the last line x can only be a `string`, and you can call `x.trim()` directly. `typeof` returns `"object"` for both `null` and arrays, so check for arrays with `Array.isArray`, and when checking "is it an object", add `x !== null`.

--- solution
function normalizeIds(input: string | string[] | null): string[] {
  if (input === null) {
    return [];
  }
  const parts = typeof input === "string" ? input.split(",") : input;
  return parts.map((s) => s.trim()).filter((s) => s !== "");
}

--- solution
type ReviewEvent =
  | { type: "tool_call"; tool: string }
  | { type: "verdict"; clause_id: string; verdict: "accept" | "flag" | "redline" }
  | { type: "error"; message: string };

interface Summary {
  toolCalls: number;
  verdicts: Record<string, number>;
  errors: string[];
}

function summarize(events: ReviewEvent[]): Summary {
  const out: Summary = { toolCalls: 0, verdicts: {}, errors: [] };
  for (const e of events) {
    switch (e.type) {
      case "tool_call":
        out.toolCalls += 1;
        break;
      case "verdict":
        out.verdicts[e.verdict] = (out.verdicts[e.verdict] ?? 0) + 1;
        break;
      case "error":
        out.errors.push(e.message);
        break;
      default: {
        const unreachable: never = e;
        throw new Error(`unknown event: ${JSON.stringify(unreachable)}`);
      }
    }
  }
  return out;
}

The report page lists "the clauses to look at first". The score might be the risk or a retrieval score, and the function will be used on other data too, so it has to be a general function.
--- prompt
Write the generic function `topBy<T>(xs: T[], score: (x: T) => number, k: number): T[]`: return the top `k` elements by `score`, from highest to lowest.

- equal scores keep their original order
- **don't change** `xs`
- if `k` is larger than the length, return all of them; if `k <= 0`, return `[]`
--- solution
function topBy<T>(xs: T[], score: (x: T) => number, k: number): T[] {
  if (k <= 0) {
    return [];
  }
  return [...xs].sort((a, b) => score(b) - score(a)).slice(0, k);
}

--- context
The playbook is the customer's review rules, stored in a JSON file that people write and edit by hand, so some rules are bound to be wrong. When loading, the bad rules have to be picked out; they must not slip quietly into the review.
--- prompt
Load playbook rules from JSON text, checking them by hand without Zod:

- `interface Rule { id: string; topic: string; severity: "low" | "medium" | "high"; keywords?: string[] }`
- `isRule(x: unknown): x is Rule`: `id` and `topic` are strings, and `severity` is one of the three levels; `keywords` may be missing, but if it's there it must be an array of strings
- `loadRules(raw: string): { rules: Rule[]; rejected: number }`: `raw` should be JSON like `{"rules": [...]}`. Valid rules go into `rules` (in order), and the number of invalid ones goes into `rejected`. If `raw` isn't valid JSON, or has no `rules` array, return `{ rules: [], rejected: 0 }`
--- solution
const SEVERITIES = ["low", "medium", "high"];

interface Rule {
  id: string;
  topic: string;
  severity: "low" | "medium" | "high";
  keywords?: string[];
}

function isRule(x: unknown): x is Rule {
  if (typeof x !== "object" || x === null) {
    return false;
  }
  if (!("id" in x) || typeof x.id !== "string") {
    return false;
  }
  if (!("topic" in x) || typeof x.topic !== "string") {
    return false;
  }
  if (!("severity" in x) || typeof x.severity !== "string" || !SEVERITIES.includes(x.severity)) {
    return false;
  }
  if ("keywords" in x) {
    const kw = x.keywords;
    if (!Array.isArray(kw) || !kw.every((k) => typeof k === "string")) {
      return false;
    }
  }
  return true;
}

function loadRules(raw: string): { rules: Rule[]; rejected: number } {
  let data: unknown;
  try {
    data = JSON.parse(raw);
  } catch {
    return { rules: [], rejected: 0 };
  }
  if (typeof data !== "object" || data === null || !("rules" in data) || !Array.isArray(data.rules)) {
    return { rules: [], rejected: 0 };
  }
  const items: unknown[] = data.rules;
  const rules = items.filter(isRule);
  return { rules, rejected: items.length - rules.length };
}
