@@ concept
title: SELECT, AS, LIMIT, DISTINCT
--- body
A query starts with `SELECT`: **which columns** you want, `FROM` **which table**.

- Separate column names with commas; `AS` gives a result column a name (an alias)
- A column can be computed: `prompt_tokens + completion_tokens AS total_tokens`, just like Python's `r["prompt_tokens"] + r["completion_tokens"]`
- `LIMIT 5`: return at most 5 rows
- `SELECT DISTINCT model`: remove duplicate rows, like the `set` from Day 8. With two columns, it removes duplicate "combinations"
- `SELECT *` takes every column; use it only while exploring data. Real queries list the columns they need (on Day 25 you'll see that in BigQuery `SELECT *` also costs more money)

SQL keywords are not case-sensitive; by convention they are written in capitals. The semicolon at the end is optional.
--- code
SELECT id,
       clause_id,
       prompt_tokens + completion_tokens AS total_tokens,
       latency_ms / 1000.0 AS latency_s
FROM reviews
LIMIT 5;
-- Then try this one (replace the whole query above): SELECT DISTINCT model, prompt_version FROM reviews;

@@ concept
title: WHERE: pick the rows you need
--- body
After `WHERE` comes a condition; only the rows where it is **true** stay. It is the `if` of a list comprehension:

- Comparison: `=` (just one equals sign), `<>` (not equal; `!=` works too), `<`, `>=`
- Combining: `AND`, `OR`, `NOT`. **`AND` is evaluated before `OR`**, so always add parentheses when you mix them
- `topic IN ('payment', 'termination')`: equal to any one of them
- `pages BETWEEN 5 AND 12`: includes both ends, 5 and 12
- `heading LIKE '%Renewal%'`: `%` stands for any number of characters, `_` for exactly one character
- Text goes in **single quotes**. In Postgres, double quotes mean a column name, so don't mix them up

Dialect differences: in SQLite, `LIKE` ignores the case of English letters; in Postgres and BigQuery, `LIKE` is case-sensitive (Postgres also has `ILIKE`). Times in this database are text like `'2026-09-05 13:17:04'`, and comparing that text happens to put them in time order.
--- code
SELECT id, contract_id, clause_id, heading, risk
FROM reviews
WHERE (topic = 'payment' OR topic = 'termination')
  AND risk <> 'low';

@@ concept
title: NULL: unknown
--- body
The two failed reviews (`id` 1047 and 1061) have **NULL** in `verdict`, `risk` and `rule_ids`: not an empty string, not 0, but "no value / unknown".

- Comparing any value with NULL gives "unknown" again, and WHERE keeps only the rows where the condition is **true**. So `verdict = NULL` never finds a single row; write `verdict IS NULL` or `IS NOT NULL`
- In the same way, `verdict <> 'accept'` does **not** return the two failed rows either; the same goes for `NOT IN (...)`
- `COALESCE(verdict, 'failed')` returns the first value that is not NULL; use it to give a default. SQLite and BigQuery also have `IFNULL`, Postgres doesn't; `COALESCE` works everywhere

In Python, `None == None` is True, but in SQL, `NULL = NULL` is not true. This is interviewers' favorite point.
--- code
SELECT id,
       clause_id,
       verdict,
       COALESCE(verdict, 'failed') AS verdict_or_failed,
       error
FROM reviews
WHERE verdict IS NULL;

@@ concept
title: ORDER BY: sorting and top N
--- body
- `ORDER BY cost_usd DESC`: largest first; leave it out or write `ASC` for smallest first
- Several columns: `ORDER BY contract_id, cost_usd DESC`: sort by the first column first; rows with the same first column are then sorted by the second
- Top N = `ORDER BY ... LIMIT N`. **Without ORDER BY, the order of the result is not guaranteed at all**, so don't rely on it
- Where NULL goes differs between databases (SQLite and BigQuery put NULL first when sorting smallest first; Postgres puts it last)

The classic trap: `clause_id` is **text**, and text is compared one character at a time, so `'10.1' < '8.1'` (because `'1' < '8'`), the same as Python's `sorted(["8.1", "10.1"])`. To sort by number, convert to a number first: `CAST(clause_id AS REAL)` turns `'10.1'` into 10.1. This only works when every number has a single digit after the dot (`'8.10'` would become 8.1 and sort before `'8.9'`). The safer way is to split it into two integers and sort by each one (`substr` and `instr` are SQLite string functions; in Postgres you can use `split_part`):

```sql
ORDER BY CAST(substr(clause_id, 1, instr(clause_id, '.') - 1) AS INTEGER),
         CAST(substr(clause_id, instr(clause_id, '.') + 1) AS INTEGER)
```
--- code
SELECT clause_id,
       heading,
       CAST(clause_id AS REAL) AS as_number
FROM reviews
WHERE contract_id = 101
ORDER BY clause_id;
-- Change ORDER BY clause_id to ORDER BY as_number, run it again and compare the two orders

@@ concept
title: Aggregates: turn many rows into one number
--- body
An aggregate function "folds" many rows into one value, like Python's `len`, `sum` and `max`:

- `COUNT(*)` counts **rows**; `COUNT(verdict)` counts only the rows where verdict is **not NULL**; `COUNT(DISTINCT topic)` counts how many different values there are
- `SUM`, `AVG`, `MIN` and `MAX` all **skip NULL**
- `ROUND(x, 2)` keeps 2 decimal places. Do this with averages and money, so the results are easy to read and to compare (in Postgres, `ROUND(x, 2)` only accepts the `numeric` type, and money is usually stored as `NUMERIC` anyway; a floating-point number needs `x::numeric` first)

Trap: **an integer divided by an integer is still an integer**. In SQLite and Postgres, `1 / 2` is 0, so dividing one SUM by another easily gives 0. Multiply by `1.0` first to turn it into a decimal: `ROUND(1.0 * a / b, 3)`. BigQuery is different: its `/` always returns a decimal (`5 / 2 = 2.5`), and for integer division you write `DIV(5, 2)`.
--- code
SELECT COUNT(*) AS all_rows,
       COUNT(verdict) AS with_verdict,
       COUNT(DISTINCT topic) AS topics,
       ROUND(AVG(latency_ms), 1) AS avg_latency_ms,
       MAX(latency_ms) AS max_latency_ms,
       ROUND(SUM(cost_usd), 4) AS total_cost_usd,
       SUM(completion_tokens) / SUM(prompt_tokens) AS wrong_ratio,
       ROUND(1.0 * SUM(completion_tokens) / SUM(prompt_tokens), 3) AS output_input_ratio
FROM reviews;

@@ concept
title: GROUP BY and HAVING
--- body
`GROUP BY topic`: split the rows into groups by topic, **output one row per group**, and compute the aggregate functions inside each group separately. It is like counting with a dictionary on Day 2: `counts[topic] = counts.get(topic, 0) + 1`.

- Every column in SELECT must either be in GROUP BY or be wrapped in an aggregate function. SQLite lets you write a column that is neither (it quietly takes the value from any one row of the group); Postgres and BigQuery raise an error. **Don't write it that way**
- `WHERE` filters **rows** **before** grouping; `HAVING` filters **groups** **after** grouping. So `COUNT(*) >= 6` can only go in HAVING

The logical order in which the database runs a query is not the order you write it in:

FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT

So the alias `n` you define in SELECT can be used in ORDER BY (it comes after SELECT) but not in WHERE (it comes before). HAVING also comes before SELECT: in Postgres, HAVING doesn't know aliases, so you write `COUNT(*)` again, and written that way it runs in every database. SQLite is lenient and often accepts aliases in WHERE and HAVING too; don't let it spoil you.
--- code
SELECT topic,
       COUNT(*) AS n,
       ROUND(AVG(latency_ms)) AS avg_latency_ms
FROM reviews
WHERE verdict IS NOT NULL
GROUP BY topic
HAVING COUNT(*) >= 6
ORDER BY n DESC, topic;

@@ concept
title: CASE WHEN: labels and conditional counts
--- body
`CASE` is SQL's if / elif / else: going from top to bottom, the first WHEN that is true wins; if none is true, ELSE is used, and without an ELSE the result is NULL.

```sql
CASE WHEN latency_ms >= 5000 THEN 'slow'
     WHEN latency_ms >= 2500 THEN 'ok'
     ELSE 'fast' END
```

Two ways to use it:

- **Labels**: put it in SELECT to create a new column; you can even group by it
- **Conditional counts**: `SUM(CASE WHEN verdict = 'redline' THEN 1 ELSE 0 END)` counts how many redlines each group has. One query can compute several counts at once, instead of running several queries

Postgres and SQLite also have the shorter `COUNT(*) FILTER (WHERE verdict = 'redline')`; in BigQuery you write `COUNTIF(verdict = 'redline')` (Day 25). `SUM(CASE ...)` works everywhere, so it is the safest thing to write in an interview.
--- code
SELECT CASE WHEN latency_ms >= 5000 THEN 'slow'
            WHEN latency_ms >= 2500 THEN 'ok'
            ELSE 'fast' END AS speed,
       COUNT(*) AS n,
       SUM(CASE WHEN model = 'deepseek-v4-pro' THEN 1 ELSE 0 END) AS v4_pro,
       COUNT(*) FILTER (WHERE verdict = 'redline') AS redlines
FROM reviews
GROUP BY speed
ORDER BY MIN(latency_ms);

@@ item d22-04
type: choice
title: BETWEEN and times
level: 2
cards: WHERE: pick the rows you need
--- context
Operations often asks "which reviews were done in these few days?". Filtering by a time range is one of the most common queries on a dashboard (a page of statistics for managers).
--- prompt
There are 3 reviews on September 2 and 8 on September 5, and none on September 3 and 4. `created_at` is text like `'2026-09-05 13:17:04'`. How many rows does this query return?
--- code
SELECT id, created_at
FROM reviews
WHERE created_at BETWEEN '2026-09-02' AND '2026-09-05';
--- options
- 11 rows
- 3 rows
- 8 rows
- 0 rows: a date can't be compared with text that includes a time
answer: 2
--- explain
`BETWEEN a AND b` means `>= a AND <= b`. `'2026-09-05 13:17:04'` has the same first 10 characters as `'2026-09-05'`, but it is longer, so it is larger: all 8 reviews from September 5 are left out, and only the 3 from September 2 remain. The safe way to ask for "from one day to another, including the last day" is a **half-open range** (include the start, exclude the end): `created_at >= '2026-09-02' AND created_at < '2026-09-06'`. The real time types in Postgres and BigQuery have the same trap: `'2026-09-05'` is read as midnight at the start of September 5.

type: sql
title: Fix the bug: the hit ratio is 0
level: 2
ordered: yes
cards: Aggregates: turn many rows into one number; GROUP BY and HAVING
--- context
Day 12 covered the prefix cache: input tokens that hit the cache are cheaper (the model bills by token). To decide whether prompt v1 or v2 saves more money, the cache hit ratio is the key number; get it wrong and you can't compare them.
--- prompt
You want to compare the **cache hit ratio** of the two prompt versions: input tokens that hit the cache ÷ all input tokens, that is, `SUM(cache_hit_tokens) / SUM(prompt_tokens)`. The query below gives 0 for both versions.

Run it and fix it: two columns, `prompt_version` and `hit_ratio`, with `hit_ratio` rounded to 3 decimal places, sorted by `prompt_version`.
--- starter
SELECT prompt_version,
       SUM(cache_hit_tokens) / SUM(prompt_tokens) AS hit_ratio
FROM reviews
GROUP BY prompt_version
ORDER BY prompt_version;
--- solution
SELECT prompt_version,
       ROUND(1.0 * SUM(cache_hit_tokens) / SUM(prompt_tokens), 3) AS hit_ratio
FROM reviews
GROUP BY prompt_version
ORDER BY prompt_version;
--- hints
- When an integer is divided by an integer, SQLite and Postgres simply throw away the decimal part: 37070 / 63146 = 0.

--- context
Legal wants to know which topics (payment, liability cap…) the high-risk reviews are concentrated in, leaving out topics that showed up only once here and there. This kind of statistic is common both on dashboards and in interview questions.
--- prompt
You want "the number of high-risk reviews in each topic, listing only topics with at least 2". Which query is correct and also works in SQLite, Postgres and BigQuery?
--- options
- `SELECT topic, COUNT(*) AS n FROM reviews WHERE risk = 'high' GROUP BY topic HAVING COUNT(*) >= 2`
- `SELECT topic, COUNT(*) AS n FROM reviews WHERE risk = 'high' AND COUNT(*) >= 2 GROUP BY topic`
- `SELECT topic, COUNT(*) AS n FROM reviews GROUP BY topic HAVING risk = 'high' AND COUNT(*) >= 2`
- `SELECT topic, COUNT(*) AS n FROM reviews WHERE n >= 2 AND risk = 'high' GROUP BY topic`
answer: 1
--- explain
The execution order is FROM → WHERE → GROUP BY → HAVING → SELECT. `risk = 'high'` is a condition on **rows**: put it in WHERE to filter out rows first. `COUNT(*) >= 2` is a condition on **groups**, known only after grouping, so it can only go in HAVING. The correct result is liability_cap with 7 and data_processing with 2.

Options 2 and 4: when WHERE runs, there are no groups yet, so it can't use an aggregate function, and the alias `n` doesn't exist yet either: error. Option 3 is the most dangerous: `risk` is neither grouped nor aggregated. Postgres and BigQuery raise an error, but SQLite quietly takes the risk of any one row in the group to decide, returns liability_cap with 12 (every review of that topic), and raises no error.

--- prompt
One row per contract, four columns:

- `contract_id`
- `reviews`: the number of reviews (including failed ones)
- `redlines`: how many of them are redline
- `redline_share`: redlines ÷ reviews, rounded to 2 decimal places

Sort by `redline_share` from highest to lowest, and ties by `contract_id` from smallest to largest.

SELECT contract_id,
       COUNT(*) AS reviews,
       SUM(CASE WHEN verdict = 'redline' THEN 1 ELSE 0 END) AS redlines,
       ROUND(1.0 * SUM(CASE WHEN verdict = 'redline' THEN 1 ELSE 0 END) / COUNT(*), 2) AS redline_share
FROM reviews
GROUP BY contract_id
ORDER BY redline_share DESC, contract_id;

- Don't forget integer division: `ROUND(1.0 * (number of redlines) / COUNT(*), 2)`; at the end, `ORDER BY redline_share DESC, contract_id`.
