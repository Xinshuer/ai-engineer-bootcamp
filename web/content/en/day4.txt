@@ concept
title: Pydantic: rules for your data
--- body
Yesterday's hand-written `validate_verdict` was tedious. Pydantic lets you **describe your data with type hints**, and it does the checking for you:

```python
from typing import Literal
from pydantic import BaseModel

class Verdict(BaseModel):
    clause_id: str
    verdict: Literal["accept", "flag", "redline"]
    confidence: float = 0.5
```

- `Literal[...]` means "must be one of these values"
- A field with a default value can be left out
- The object is validated automatically when you create it; values that can be converted safely are converted (the string `"0.9"` → `0.9`), and anything invalid raises `ValidationError`
- `v.model_dump()` turns it back into a dictionary
--- code
from typing import Literal
from pydantic import BaseModel

class Verdict(BaseModel):
    clause_id: str
    verdict: Literal["accept", "flag", "redline"]
    confidence: float = 0.5

v = Verdict(clause_id="8.1", verdict="flag")
print(v.verdict, v.confidence)
print(v.model_dump())
w = Verdict(clause_id="12", verdict="accept", confidence="0.9")
print(w.confidence, type(w.confidence))

@@ concept
title: Failed validation: ValidationError
--- body
JSON text from the model can be parsed and validated in one step:

```python
v = Verdict.model_validate_json(raw)
```

Broken JSON, a missing field, an invalid value: each of them raises `ValidationError`. `e.errors()` is the list of problems; each item has `loc` (which field) and `msg` (the reason).

In Clause Check, a failed validation does not crash the program. Instead, the error message is **sent back to the model** so it can correct its answer. This is called "validation feedback".
--- code
from typing import Literal
from pydantic import BaseModel, ValidationError

class Verdict(BaseModel):
    clause_id: str
    verdict: Literal["accept", "flag", "redline"]

for raw in ['{"clause_id": "8.1", "verdict": "flag"}', '{"clause_id": "8.1", "verdict": "HIGH"}', "not json"]:
    try:
        print("ok:", Verdict.model_validate_json(raw))
    except ValidationError as e:
        err = e.errors()[0]
        print("invalid:", err["loc"], err["msg"])

@@ concept
title: What a Chat API request and response look like
--- body
Almost every model API (DeepSeek, OpenAI, LM Studio) uses the same format. DeepSeek's current model names are `deepseek-flash` (fast and cheap; this course uses it throughout) and `deepseek-v4-pro` (bigger, slower, more expensive). DeepSeek has officially announced that the old model names `deepseek-chat` / `deepseek-reasoner` are retired as of 2026-07-24: tested in 2026-09, they can still be called (and `deepseek-flash` answers), but they are no longer in the model list and may stop working at any time. Many tutorials online still use them; when you copy from one, change the name to `deepseek-flash`.

**Request**: POST to `.../chat/completions` with the header `Authorization: Bearer <API key>`, and this request body:

```python
{
    "model": "deepseek-flash",
    "messages": [
        {"role": "system", "content": "You are a contract review assistant..."},
        {"role": "user", "content": "Please review this clause: ..."},
    ],
    "thinking": {"type": "disabled"},
    "temperature": 0.3,
}
```

**Thinking mode**: by default, DeepSeek "thinks it over" before it answers. The answer is still in `content`, and the thinking is in `reasoning_content`; the tokens spent on thinking are billed as **output**, and `temperature` has no effect in this mode. For calls like reviewing a clause, add `"thinking": {"type": "disabled"}` to turn it off: it is faster and cheaper, `temperature` works again, and judging one clause doesn't need long reasoning anyway.

The three places in the **response** you will use most:

- `data["choices"][0]["message"]["content"]` what the model said
- `data["choices"][0]["finish_reason"]` why it stopped: `"stop"` means it finished, `"tool_calls"` means it wants to call a tool
- `data["usage"]["total_tokens"]` how many tokens it used (this is what you pay for)
--- code
import json

messages = [
    {"role": "system", "content": "You review contract clauses."},
    {"role": "user", "content": "Review clause 8.1: liability is unlimited."},
]
body = {"model": "deepseek-flash", "messages": messages, "thinking": {"type": "disabled"}, "temperature": 0.3}
print(json.dumps(body, indent=2))

@@ concept
title: Status codes and retries
mock: yes
--- body
- `200` success
- `400` the request is wrong (a missing field, a wrong model name): **don't retry**, fix the code
- `401` the API key is wrong or `Bearer` is missing: **don't retry**
- `429` too many requests, `500` / `503` a server problem: **you can retry**; wait a moment and try again

Retries need a **limit** (for example 3 attempts); otherwise, if the service stays down, you stay stuck in the loop. In production you also wait longer and longer between retries (exponential backoff).

On this page, `MOCK.fail_next(429, 2)` makes the mock server return 429 for the next two requests, so you can practice retrying.
--- code
import os
import requests

URL = "https://api.deepseek.com/v1/chat/completions"
HEADERS = {"Authorization": f"Bearer {os.getenv('DEEPSEEK_API_KEY')}"}
body = {"model": "deepseek-flash", "messages": [{"role": "user", "content": "hi"}]}

MOCK.fail_next(429, 2)
for attempt in range(1, 4):
    resp = requests.post(URL, headers=HEADERS, json=body)
    print("attempt", attempt, "status", resp.status_code)
    if resp.status_code == 200:
        break

print(requests.post(URL, headers={"Authorization": "wrong"}, json=body).json())

@@ concept
title: Tool calls: the model asks you to look something up
mock: yes
--- body
Put the tool descriptions (name, description, parameters) in the request's `tools`. When the model decides it needs a tool, it doesn't answer directly; instead it returns:

```python
finish_reason == "tool_calls"
message["tool_calls"] = [{"id": "call_1", "function": {"name": "lookup_playbook", "arguments": '{"topic": "liability_cap"}'}}]
```

Your code has to:

1. Find the Python function with that name
2. Get the arguments with `json.loads(arguments)` and call the function
3. Add the model's message and a message `{"role": "tool", "tool_call_id": ..., "content": result}` to messages, then **send the request again**

Once the model sees the tool result, it gives its final answer. This "request → call the tool → request again" loop is what an agent is. The example turns thinking mode off here too: an agent sends several requests back and forth, so speed and cost matter more. Also, with thinking mode on, DeepSeek's docs require the model message you add back in step 3 to keep its `reasoning_content`, and leaving it out returns 400 (the mock server on the practice page follows this rule; in tests in 2026-09 the real API did not reject it yet, but the docs say so, so follow them).
--- code
import json
import os
import requests

URL = "https://api.deepseek.com/v1/chat/completions"
HEADERS = {"Authorization": f"Bearer {os.getenv('DEEPSEEK_API_KEY')}"}
TOOLS = [{"type": "function", "function": {"name": "lookup_playbook", "description": "Return the customer's rule for a topic", "parameters": {"type": "object", "properties": {"topic": {"type": "string"}}, "required": ["topic"]}}}]

messages = [{"role": "user", "content": "Is unlimited liability acceptable?"}]
data = requests.post(URL, headers=HEADERS, json={"model": "deepseek-flash", "messages": messages, "tools": TOOLS, "thinking": {"type": "disabled"}}).json()
choice = data["choices"][0]
print("finish_reason:", choice["finish_reason"])
call = choice["message"]["tool_calls"][0]
print("tool:", call["function"]["name"], json.loads(call["function"]["arguments"]))

@@ concept
title: Randomness: one run is not enough
mock: yes
--- body
Given the same input, the model may answer differently from one time to the next. So when you evaluate a function that uses a model, **run it N times and look at the pass rate**, instead of running it once and checking whether it is right.

The mock server on this page deliberately wavers on clauses like an "AS IS" disclaimer (in the long run it says accept about 60% of the time), just like a real model. The example below counts how many of 10 runs say accept: with only 10 runs, a result far from 60% is perfectly normal, and that is exactly why you run many times and look at the pass rate.

This is the core idea of Clause Check's `evals/run_evals.py`.
--- code
import json
import os
import requests

URL = "https://api.deepseek.com/v1/chat/completions"
HEADERS = {"Authorization": f"Bearer {os.getenv('DEEPSEEK_API_KEY')}"}
clause = 'Review clause 7.2: THE SERVICE IS PROVIDED "AS IS".'
results = []
for _ in range(10):
    body = {"model": "deepseek-flash", "messages": [{"role": "user", "content": clause}], "response_format": {"type": "json_object"}, "thinking": {"type": "disabled"}}
    content = requests.post(URL, headers=HEADERS, json=body).json()["choices"][0]["message"]["content"]
    results.append(json.loads(content)["verdict"])
print(results)
print("accept rate:", results.count("accept") / len(results))

from pydantic import BaseModel, ValidationError

class Verdict(BaseModel):
    clause_id: str

import os
import requests

API_URL = "https://api.deepseek.com/v1/chat/completions"
HEADERS = {"Authorization": f"Bearer {os.getenv('DEEPSEEK_API_KEY')}"}
RETRYABLE = (429, 500, 503)

def ask_with_retry(prompt, max_attempts=3):
    body = {"model": "deepseek-flash", "messages": [{"role": "user", "content": prompt}]}
    for attempt in range(max_attempts):

    raise RuntimeError(f"gave up after {max_attempts} attempts")

import json

def extract_json(text):
    start = text.find("{")
    end = text.rfind("}")
    if start == -1 or end == -1:

    return json.loads(text[start:end + 1])

import json

def run_tool_call(call, tools):
    name = call["function"]["name"]
    if name not in tools:
        return f"UNKNOWN_TOOL: {name}"
    args = json.loads(call["function"]["arguments"])
    return tools[name](**args)

import json
import os
import requests

API_URL = "https://api.deepseek.com/v1/chat/completions"
HEADERS = {"Authorization": f"Bearer {os.getenv('DEEPSEEK_API_KEY')}"}
TOOLS = [{"type": "function", "function": {"name": "lookup_playbook", "description": "Return the customer's rule for a topic", "parameters": {"type": "object", "properties": {"topic": {"type": "string"}}, "required": ["topic"]}}}]

def lookup_playbook(topic):
    return f"rule for {topic}: cap at 100% of annual fees"

def run_tool_call(call, tools):
    return tools[call["function"]["name"]](**json.loads(call["function"]["arguments"]))

def mini_agent(question, max_steps=3):
    messages = [{"role": "user", "content": question}]
    for _ in range(max_steps):
        body = {"model": "deepseek-flash", "messages": messages, "tools": TOOLS, "thinking": {"type": "disabled"}}
        choice = requests.post(API_URL, headers=HEADERS, json=body).json()["choices"][0]
        message = choice["message"]
        if choice["finish_reason"] != "tool_calls":
            return message["content"]
        call = message["tool_calls"][0]
        result = run_tool_call(call, {"lookup_playbook": lookup_playbook})
        messages.append(message)
        messages.append({"role": "tool", "tool_call_id": call["id"], "content": result})
    return "STOPPED"

type: choice
title: Is temperature 0 deterministic?
level: 2
cards: Randomness: one run is not enough
--- context
Some people think that if you turn the randomness of the answers down to the minimum, tests only need to run once, which saves time and money. Whether that idea is right decides whether your evaluation results can be trusted.
--- prompt
After you turn thinking mode off (`"thinking": {"type": "disabled"}`) and set `temperature` to 0 in the request:
--- options
- The output is always exactly the same, so running the test once is enough
- It is usually more stable, but not guaranteed to be the same every time; evaluation still needs several runs and a pass rate
- The model refuses to answer
- The output becomes more creative
answer: 2
--- explain
The lower the temperature, the more focused the output, but batching on the server, the order of floating-point operations and the provider updating the model all make results change. Also, tests should use the same parameters as production. So "run once, check whether it is right" is unreliable; you need "run N times, look at the pass rate". And remember: with thinking mode on, DeepSeek ignores temperature completely, which is why the question turns thinking mode off first.

--- context
Reviewing one contract calls the model many times, and every call is billed by the token (a token is the unit a model uses to measure the text it reads and writes). Add up what each call used, and you know how many tokens the whole batch of requests used.
--- prompt
Write `total_tokens(prompts)`: call the API once for each prompt in the list (model `deepseek-flash`) and return the sum of `total_tokens` over all the calls. An empty list returns 0.
--- solution
import os
import requests

def total_tokens(prompts):
    headers = {"Authorization": f"Bearer {os.getenv('DEEPSEEK_API_KEY')}"}
    total = 0
    for p in prompts:
        body = {"model": "deepseek-flash", "messages": [{"role": "user", "content": p}]}
        data = requests.post("https://api.deepseek.com/v1/chat/completions", headers=headers, json=body).json()
        total += data["usage"]["total_tokens"]
    return total
