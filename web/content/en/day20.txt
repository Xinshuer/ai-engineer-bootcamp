@@ concept
title: Five kinds of interview questions
--- body
Technical interviews for AI Engineer roles usually have five kinds of questions, and each one tests something different:

1. **Predict the output**: read some code and say what it prints. Tests whether you can "run" code in your head
2. **Find the bug**: code that sometimes goes wrong, very often an agent loop. Tests the order in which you track the problem down
3. **Refactor**: the code works but is messy, and there's a small new requirement. Tests whether you can tidy it up **without changing behavior**
4. **Implement**: write a small function in 15–20 minutes. Tests edge cases and whether you think about testing
5. **Design**: "What do you do with a 300-page contract?" There's no single right answer; it tests whether your thinking is organized

For every kind, **talk while you work**: restate the question with its inputs and outputs, say what you plan to do, and when you're done, check it with an example before anyone asks. Writing in silence for ten minutes is the worst thing you can do.
--- code
forms = {

@@ concept
title: Reading code in the right order
--- body
When you get code you don't know, don't force your way from the first line to the last. Ask four questions, in this order:

1. **Input**: what types are the parameters? Can they be empty?
2. **Output**: what does it return? Does every path have a return?
3. **Loops**: how many times does it loop? When does it stop? Could it never stop?
4. **Side effects**: does it change a list or dictionary that was passed in? Does it write files or send requests?

These four questions match the four most common kinds of bug: empty input, a missing return, a loop that never stops, and quietly changing someone else's data. The example below "looks like it only picks out clauses". Run it and look at the last line.
--- code
def needs_review(reviews, limit=2):
    # 1 input: reviews is a list of dicts, may be empty
    picked = []
    for r in reviews:                 # 3 loop: looks at each one once, always stops
        if r["verdict"] != "accept":
            r["seen"] = True          # 4 side effect: changes the caller's dict!
            picked.append(r["id"])
    return picked[:limit]             # 2 output: at most limit clause numbers

reviews = [{"id": "8.1", "verdict": "redline"}, {"id": "3.1", "verdict": "accept"}, {"id": "9.1", "verdict": "flag"}]
print(needs_review(reviews))
print(needs_review([]))
print(reviews[0])

@@ concept
title: A bug-hunting checklist
lang: ts
--- body
When an interviewer gives you code that "is sometimes wrong", going through a checklist one item at a time works much better than staring at it:

- **Off by one**: `range(n)` vs `range(n + 1)`, `<` vs `<=`, the slice `[:k]`
- **Changing a list while looping over it**: `remove` from the same list inside a `for`
- **Forgetting await** (TS): `forEach(async ...)` doesn't wait at all
- **Forgetting return**: some path returns `None` / `undefined`
- **A misspelled key**: `risk` vs `risk_level`; `.get()` quietly returns None
- **A loop with no limit**: the agent has no `max_steps`, or the counter never goes up
- **Swallowed errors**: `except Exception: pass`, and on failure it even defaults to `accept`

The three most common in agent loops: the tool result isn't put back into messages, the assistant and tool messages are in the wrong order, and the step count never goes up. Below is a demo of "forgetting await": `forEach` starts the callbacks and moves on, so when it prints, the results haven't come back yet.
--- code
async function review(id: string): Promise<string> {
  await Promise.resolve(); // pretend to wait for the model
  return `${id}:ok`;
}
async function main() {
  const ids = ["8.1", "4.2"];
  const bad: string[] = [];
  ids.forEach(async (id) => {
    bad.push(await review(id));
  });
  console.log("forEach, right after:", bad);
  const good: string[] = [];
  for (const id of ids) {
    good.push(await review(id));
  }
  console.log("for...of:", good);
  console.log("forEach, later:", bad);
}
main();

@@ concept
title: Refactoring principles
--- body
Refactoring = **the same behavior**, a better structure. Refactoring questions in interviews usually add a small new requirement too: they test whether you tidy up first and then add, instead of piling one more layer of if onto messy code.

1. **Tests first**: lock in the current behavior with a few examples
2. **Change in small steps, and run the tests after each one**: rename (`x` → `verdict`), extract a function, return early to cut nesting, remove duplication (three nearly identical blocks → one loop or one table)
3. **Add the new requirement last**, ideally changing only one place

Say it out loud: "I won't change the behavior yet. I'll fold these three repeated checks into one table, and then the new requirement is just one more line." The old and new versions below give the same result for every input.
--- code
def label_old(v):
    if v["verdict"] == "redline":
        if v["risk"] == "high":
            return "URGENT"
        else:
            return "REVIEW"
    else:
        if v["verdict"] == "flag":
            return "REVIEW"
        else:
            return "OK"

def label_new(v):
    if v["verdict"] == "redline" and v["risk"] == "high":
        return "URGENT"
    if v["verdict"] in ("redline", "flag"):
        return "REVIEW"
    return "OK"

cases = [{"verdict": a, "risk": b} for a in ["accept", "flag", "redline"] for b in ["low", "high"]]
print(all(label_old(c) == label_new(c) for c in cases))
print([label_new(c) for c in cases])

@@ concept
title: A feel for complexity
--- body
When the interviewer asks "what is the complexity of this code?", you should be able to give your intuition:

- One loop over n elements: **O(n)**
- A loop inside a loop, or `in` on a **list** inside a loop: **O(n²)**. `x in some_list` compares one element at a time; `x in some_set` / `x in some_dict` gets there almost in one step
- Sorting: O(n log n)

A contract has 300 clauses, and n² is only 90,000 comparisons, which a computer does in the blink of an eye. **What's really slow is 300 model calls** (a few seconds each). So say it clearly: "O(n²) is fine here. The bottleneck is the network calls, so I'd start with bounded concurrency and caching." Only when the data grows to hundreds of thousands (for example, deduplicating across all contracts) do you need to swap the list for a set or a dictionary.
--- code
ids = [f"{i}.1" for i in range(300)]
cited = ids[::2]             # 150 of them were cited

comparisons = 0
for i in ids:
    for c in cited:           # list: compare one at a time
        comparisons += 1
print("comparisons with two loops:", comparisons)

cited_set = set(cited)       # set: look it up directly
missing = [i for i in ids if i not in cited_set]
print("with a set:", len(ids), "lookups,", len(missing), "not cited")

@@ concept
title: A framework for answering design questions
lang: ts
--- body
Answer a design question ("You need to review 1,000 contracts a day. How would you do it?") in six steps, one or two sentences each, using Clause Check as the example:

1. **Requirements**: who uses it? How fast must it be? How costly is a mistake? (For lawyers, missing a risky clause is worse than flagging one extra)
2. **Data flow**: upload → parse → split into clauses → review each clause (model + playbook retrieval) → summarize → a person approves → export
3. **Failure modes**: parsing errors, a broken output format, 429, prompt injection, the model missing a risk
4. **Evals**: run the test cases N times and look at the pass rate; keep a close eye on recall for high-risk clauses
5. **Cost and latency**: turn off thinking mode for per-clause classification, prefix cache, bounded concurrency, review duplicate clauses only once
6. **First step**: "I'd first add tracing to measure how long each step takes, then decide what to optimize"

Step 6 matters most: the interviewer wants to hear that you **measure first, then act**.
--- code
const answer: [string, string][] = [
  ["requirements", "lawyers; a missed risky clause costs most"],
  ["data flow", "parse -> split -> review -> summarize -> approve"],
  ["failure modes", "bad JSON, 429, injection, missed risk"],
  ["evals", "cases x N runs, high-risk recall"],
  ["cost/latency", "thinking off, prefix cache, bounded concurrency, dedupe"],
  ["first step", "add tracing, measure, then optimize"],
];
answer.forEach(([step, note], i) => console.log(`${i + 1}. ${step.padEnd(14)} ${note}`));

title: Recap: default arguments
level: 1
cards: d9:Common bug patterns; d2:Functions: default arguments and early return; Reading code in the right order
--- context
During a review, the numbers of the clauses that need attention are collected into a list. This is a very natural way to write it, and a regular guest in Python interviews.
--- prompt
Recap of Days 8 and 9. Write the output. Interviewers love asking this one.
--- code
def add_flag(clause_id, flags=[]):
    flags.append(clause_id)
    return flags

a = add_flag("8.1")
b = add_flag("4.2")
c = add_flag("9.1", [])
print(a)
print(b is a, c)
--- explain
The default value `[]` is created only once, at the moment `def` runs. After that, every call that doesn't pass `flags` uses that same list, so a and b are the same object and both appends are in it; c, which was given a new list of its own, is not affected. The standard way is `flags=None`, and inside the function `if flags is None: flags = []`. In the interview, say the key sentence: default arguments are evaluated when the function is defined.

type: predict
title: Closures in a loop
level: 2
cards: d13:Functions are values: decorators; Reading code in the right order
--- context
The exercise wants a batch of check functions, one for each of several thresholds, all made in one loop. Interviewers often use this pattern to test how well you understand functions and variables.
--- prompt
Write the output. Is the `limit` used inside the `lambda` the value at the time it was created, or at the time it is called?
--- code
checks = []
for limit in [1, 2, 3]:
    checks.append(lambda n: n > limit)
print([check(2) for check in checks])

fixed = []
for limit in [1, 2, 3]:
    fixed.append(lambda n, limit=limit: n > limit)
print([check(2) for check in fixed])
--- explain
A lambda remembers the **variable**, not its value at that moment. By the time it is called, the loop has long finished and `limit` is 3, so all three are `2 > 3`: all False. The second block uses the default argument `limit=limit` to "snapshot" the current value when the lambda is created: the trap from the previous exercise turns out to be useful here. You'll run into this when you generate one check function for each playbook rule.

type: predict
title: Sort stability
level: 2
cards: d8:Sorting by several keys; d2:Sorting and while
--- context
The report puts high-risk clauses first, so the lawyer sees the most urgent ones first. Sorting looks simple, but interviews often test its details.
--- prompt
Write the output. Python's sort is **stable**: elements with the same key keep their original order, and that stays true with `reverse=True`.
--- code
reviews = [
    ("3.2", "medium"), ("8.1", "high"), ("4.2", "medium"),
    ("9.1", "high"), ("1.1", "low"),
]
RANK = {"low": 0, "medium": 1, "high": 2}
by_risk = sorted(reviews, key=lambda r: RANK[r[1]], reverse=True)
print([cid for cid, _ in by_risk])
by_id = sorted(reviews)
print([cid for cid, _ in by_id][:3])
print(sorted(["10.1", "9.1", "8.2"]))
--- explain
Sorted by risk in reverse, 8.1 and 9.1 (both high) and 3.2 and 4.2 (both medium) keep their original order, so "same risk keeps the original order" in `summarise` needs no extra work. Sorting tuples compares the first element first, which here is the clause number string. The last line is an old trap: strings are compared character by character, and "1" is less than "8", so "10.1" comes first. To sort by number, use the key `tuple(int(p) for p in cid.split("."))`.

@@ item d20-04
type: predict
title: var and let
level: 2
lang: ts
cards: d5:From Python to TypeScript; Reading code in the right order
--- context
You still often see `var` in old JavaScript code and in examples online. Interviewers like to use this code to test which value each function in a batch made in a loop remembers.
--- prompt
Write the output. `var` is the old-style declaration: the whole function shares **one** variable. With `let`, a for loop gets **a new copy every round**.
--- code
const withVar: (() => number)[] = [];
for (var i = 0; i < 3; i++) {
  withVar.push(() => i);
}
const withLet: (() => number)[] = [];
for (let j = 0; j < 3; j++) {
  withLet.push(() => j);
}
console.log(withVar.map((f) => f()).join(","));
console.log(withLet.map((f) => f()).join(","));
--- explain
All three arrow functions refer to the same `i`; by the time they are called, the loop has finished and `i` is 3. `let j` is a new copy every round, so each one remembers 0, 1 and 2. Python's loop variable behaves more like `var`, which is why the closure exercise earlier gave three Falses. In TypeScript, always use `let` / `const`.

@@ item d20-05
type: predict
title: The order async code runs in
level: 3
lang: ts
cards: d6:async / await: wait for the network without freezing
--- context
Review code is full of `await`: call the model, wait for the answer. Once you know the order they really run in, you won't be guessing when you debug problems like "why are the log lines out of order?".
--- prompt
Write the output, one line each. Three rules:

1. All the synchronous code runs first
2. The part after an `await`, and `.then` callbacks, go into the "microtask" queue; once the synchronous code has finished, they run in the order they were queued
3. `setTimeout`, even with 0 milliseconds, comes after all the microtasks
--- code
async function review(id: string): Promise<string> {
  console.log(`start ${id}`);
  await Promise.resolve();
  console.log(`end ${id}`);
  return id;
}
console.log("A");
setTimeout(() => console.log("timeout"), 0);
review("8.1").then((id) => console.log(`then ${id}`));
review("4.2");
console.log("B");
--- explain
The synchronous phase: A, the two starts (each review runs until its await and then hands back control), B. Then the microtasks: 8.1 was queued first, so it ends first, then 4.2 ends. Only after 8.1's Promise has completed is the `.then` callback queued, so it comes after both ends. The timeout line comes last. In an interview, explaining the three layers "synchronous → microtasks → timers" clearly is enough.

        body = {"model": "deepseek-flash", "messages": messages, "tools": TOOLS, "thinking": {"type": "disabled"}}

import json
import os
import requests

API_URL = "https://api.deepseek.com/v1/chat/completions"
HEADERS = {"Authorization": f"Bearer {os.getenv('DEEPSEEK_API_KEY')}"}
TOOLS = [{"type": "function", "function": {"name": "lookup_playbook", "description": "Return the customer's rule for a topic. Call it before deciding.", "parameters": {"type": "object", "properties": {"topic": {"type": "string"}}, "required": ["topic"]}}}]

def lookup_playbook(topic):
    return f"rule for {topic}: cap at 12 months of fees"

def agent(question, max_steps=4):
    messages = [{"role": "user", "content": question}]
    for step in range(max_steps):
        body = {"model": "deepseek-flash", "messages": messages, "tools": TOOLS, "thinking": {"type": "disabled"}}
        message = requests.post(API_URL, headers=HEADERS, json=body).json()["choices"][0]["message"]
        if not message.get("tool_calls"):
            return message["content"]
        call = message["tool_calls"][0]
        result = lookup_playbook(**json.loads(call["function"]["arguments"]))
        messages.append(message)
        messages.append({"role": "tool", "tool_call_id": call["id"], "content": result})
    return "STOPPED"

The approval screen in this exercise saves the state after every step, so the lawyer can look back and undo. The idea is the same as with checkpoints: old records must always stay exactly as they were.
--- prompt
`replay` should save a snapshot of the state after every step (like a checkpoint, so you can look back and undo). The tests find that every snapshot looks like the last step. --- starter
type State = { counts: Record<string, number>; seen: string[] };
type ReviewEvent = { clauseId: string; verdict: "accept" | "flag" | "redline" };

function apply(state: State, e: ReviewEvent): State {
  state.counts[e.verdict] = (state.counts[e.verdict] ?? 0) + 1;
  state.seen.push(e.clauseId);
  return state;
}

function replay(events: ReviewEvent[]): State[] {
  const history: State[] = [];
  let state: State = { counts: {}, seen: [] };
  for (const e of events) {
    state = apply(state, e);
    history.push(state);
  }
  return history;
}

import re

def normalize(text):
    text = re.sub(r"[^a-z0-9\s]", "", text.lower())
    return " ".join(text.split())

def dedupe_clauses(clauses):
    first = {}
    unique = []
    duplicates = {}
    for c in clauses:
        key = normalize(c["text"])
        if key in first:
            duplicates[c["id"]] = first[key]
        else:

function mergeSpans(spans: [number, number][]): [number, number][] {
  const sorted = [...spans].sort((a, b) => a[0] - b[0]);
  const out: [number, number][] = [];
  for (const [start, end] of sorted) {
    const last = out[out.length - 1];
    if (last && start <= last[1]) {
      last[1] = Math.max(last[1], end);
    } else {
      out.push([start, end]);
    }
  }
  return out;
}

def plan_batches(clauses, max_requests, max_tokens):
    batches = []
    current = []
    used = 0
    for c in clauses:
        if c["tokens"] > max_tokens:
            raise ValueError(f"clause {c['id']} needs {c['tokens']} tokens, limit is {max_tokens}")
        if current and (len(current) >= max_requests or used + c["tokens"] > max_tokens):
            batches.append(current)
            current, used = [], 0
        current.append(c["id"])
        used += c["tokens"]
    if current:
        batches.append(current)
    return batches

type Edit = { start: number; end: number; replacement: string };

function applyRedlines(text: string, edits: Edit[]): string {
  const sorted = [...edits].sort((a, b) => a.start - b.start);
  for (let i = 1; i < sorted.length; i++) {
    if (sorted[i].start < sorted[i - 1].end) {
      throw new Error(`overlapping edits at ${sorted[i].start}`);
    }
  }
  let out = text;
  for (const e of sorted.reverse()) {
    out = out.slice(0, e.start) + e.replacement + out.slice(e.end);
  }
  return out;
}

--- context
Calls to the model now and then run into network glitches or a 429 (too many requests, temporarily refused); the usual answer is to retry automatically a few times. Every request in the review flow may be wrapped in a layer like this.
--- prompt
The `withRetry` below has 3 bugs. Don't patch it: write a correct version from scratch in a blank editor.

```ts
async function withRetry<T>(fn: () => Promise<T>, tries: number): Promise<T | undefined> {
  for (let i = 0; i <= tries; i++) {
    try {
      return fn();
    } catch (e) {
      console.log("retrying");
    }
  }
}
```

The signature of the correct version: `withRetry<T>(fn: () => Promise<T>, tries: number): Promise<T>`

- call `fn` at most `tries` times in total; as soon as one call succeeds, return its result
- when `fn` fails (its Promise is rejected), try again
- when every call fails: throw the error from the **last** call; never return undefined
--- solution
async function withRetry<T>(fn: () => Promise<T>, tries: number): Promise<T> {
  let lastError: unknown = new Error("tries must be at least 1");
  for (let i = 0; i < tries; i++) {
    try {
      return await fn();
    } catch (e) {
      lastError = e;
    }
  }
  throw lastError;
}
--- tests
function flaky(failures: number) {
  let calls = 0;
  const fn = async (): Promise<string> => {
    calls += 1;
    if (calls <= failures) throw new Error(`fail ${calls}`);
    return "ok";
  };
  return { fn, count: () => calls };
}
expectAsync("succeeds after two failures, 3 calls in total", async () => {
  const f = flaky(2);
  const r = await withRetry(f.fn, 3);
  return [r, f.count()];
}, ["ok", 3]);
expectAsync("all fail: throws the last error, calls only tries times", async () => {
  const f = flaky(10);
  try {
    await withRetry(f.fn, 3);
    return "no error thrown";
  } catch (e) {
    return [e instanceof Error ? e.message : String(e), f.count()];
  }
}, ["fail 3", 3]);
expectAsync("succeeds the first time", async () => {
  const f = flaky(0);
  return [await withRetry(f.fn, 3), f.count()];
}, ["ok", 1]);
