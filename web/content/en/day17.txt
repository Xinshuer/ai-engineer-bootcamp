@@ concept
title: Agent = loop + limits
--- body
Day 7's `miniAgent` is already an agent: ask the model → if the model wants a tool, run it → put the result back into messages → ask again… until the model gives a text answer. Today you turn it into something that is ready to ship.

Before you ship, the first question is not "how do I make it smarter" but **"how do I make it stop"**: the model may keep calling tools forever (an infinite loop), and every step costs money. So limits are part of the design, and when the loop stops it must also say why:

```ts
type StopReason = "answer" | "max_steps" | "budget";
```

In Clause Check's `review.py`, `while trace.steps < settings.max_steps` is this limit (`config.py` defaults to 6 steps). This page's mock server has a switch: if the user message contains `[loop]`, the model keeps calling tools forever. It exists just for testing limits.

`thinking: { type: "disabled" }` in the request body turns off DeepSeek's thinking mode, which is on by default. An agent calls the model once per step; thinking tokens are billed as output and also slow every step down. Picking a tool or giving a verdict doesn't need long reasoning, so tool loops usually turn thinking off (once it is off, `temperature` works again). All of today's requests are written this way.
--- code
const API_URL = "https://api.deepseek.com/v1/chat/completions";
const HEADERS = { Authorization: `Bearer ${process.env.DEEPSEEK_API_KEY}` };
const TOOLS = [{ type: "function", function: { name: "lookup_playbook", description: "Return the customer's rule for a topic", parameters: { type: "object", properties: { topic: { type: "string" } }, required: ["topic"] } } }];

async function run(question: string, maxSteps: number): Promise<string> {
  const messages: any[] = [{ role: "user", content: question }];
  for (let step = 1; step <= maxSteps; step++) {
    const res = await fetch(API_URL, { method: "POST", headers: HEADERS, body: JSON.stringify({ model: "deepseek-flash", messages, tools: TOOLS, thinking: { type: "disabled" } }) });
    const choice = (await res.json()).choices[0];
    console.log(`  step ${step}: ${choice.finish_reason}`);
    if (choice.finish_reason !== "tool_calls") {
      return `answer: ${choice.message.content}`;
    }
    const call = choice.message.tool_calls[0];
    messages.push(choice.message);
    messages.push({ role: "tool", tool_call_id: call.id, content: `rule for ${JSON.parse(call.function.arguments).topic}` });
  }
  return "stopped: max_steps";
}

async function main() {
  console.log(await run("Is unlimited liability acceptable?", 3));
  console.log(await run("Is unlimited liability acceptable? [loop]", 3));
}
main();

@@ concept
title: Tool registry: one schema, two uses
--- body
A tool = a name + a description + a parameter schema + a function that runs it. The schema does two jobs at once:

1. `z.toJSONSchema(schema)` generates the `parameters` the model sees
2. When the model sends arguments back, `schema.safeParse(...)` checks them in code

With one definition, what the model sees and what the code checks always match. `tool_specs()` in `tools.py` does the same thing with Pydantic's `model_json_schema()`.

Tools go into a `Map<string, Tool>` by name (Day 16), and you look one up with `.get(name)`. The parameter of `run` is typed `any` because every tool's arguments have a different shape. `any` is safe here, because the arguments always pass `safeParse` before they reach `run`.

A small note: this page's Zod type declarations are a simplified version without `z.ZodType`, so the exercises already include `type AnySchema = ReturnType<typeof z.any>`, which simply means "any Zod schema". In a real project, write `z.ZodType` directly.
--- code
import { z } from "zod";

type AnySchema = ReturnType<typeof z.any>;
type Tool = { name: string; description: string; schema: AnySchema; run: (args: any) => string | Promise<string> };

const lookupPlaybook: Tool = {
  name: "lookup_playbook",
  description: "Return the customer's rule for one topic. Call this before deciding any verdict.",
  schema: z.object({ topic: z.enum(["liability_cap", "payment", "termination"]).describe("Topic of the clause") }),
  run: (args) => `rule for ${args.topic}`,
};
const registry = new Map<string, Tool>([[lookupPlaybook.name, lookupPlaybook]]);

console.log(JSON.stringify(z.toJSONSchema(lookupPlaybook.schema), null, 2));
console.log(registry.has("lookup_playbook"), registry.get("delete_all"));

@@ concept
title: Argument validation: errors are messages for the model
--- body
The `arguments` the model gives are **JSON text**. The text may be malformed, have the wrong fields, or name a tool that doesn't exist at all. In none of these three cases should you **throw and crash the whole loop**. Instead, write the error as the tool result and send it back to the model; it usually corrects itself on the next step:

```ts
messages.push({ role: "tool", tool_call_id: call.id, content: "INVALID_ARGS: topic: Invalid option ..." });
```

This is exactly what `execute` in `tools.py` does: `UNKNOWN_TOOL` and `INVALID_ARGS` come back as content, plus an `is_error` flag, and the comment says "Never raises for model mistakes".

A classic mistake: `JSON.parse` without a try/catch. The model writes bad arguments once, and the review of the whole contract crashes.
--- code
import { z } from "zod";

const TopicArgs = z.object({ topic: z.enum(["liability_cap", "payment"]) });

function check(argText: string): string {
  let raw: unknown;
  try {
    raw = JSON.parse(argText);
  } catch {
    return "INVALID_JSON: arguments are not valid JSON";
  }
  const r = TopicArgs.safeParse(raw);
  if (!r.success) {
    const issue = r.error.issues[0];
    return `INVALID_ARGS: ${issue.path.join(".")}: ${issue.message}`;
  }
  return `OK: ${r.data.topic}`;
}

console.log(check('{"topic": "payment"}'));
console.log(check('{"topic": '));
console.log(check('{"topic": "gdpr"}'));

@@ concept
title: Limits and stop reasons
--- body
Use two kinds of limits together:

- **Steps**: the most times to ask the model (`maxSteps`)
- **Budget**: add up `usage.total_tokens` from every response, and stop once the total reaches `maxTokens`. messages keeps growing, so every step costs more than the one before (run the example below to see the numbers). With thinking mode on, thinking tokens also count in `completion_tokens`, so the budget runs out faster

When the loop stops, it returns not just some text but an object that says why it stopped:

```ts
type RunResult = { reason: "answer" | "max_steps" | "budget"; answer: string | null; steps: number };
```

The caller looks at `reason` to decide what to do: `answer` is used normally; for `max_steps` / `budget`, fall back to "flag, needs a person" the way `review.py` does, instead of pretending the review is finished.
--- code
const API_URL = "https://api.deepseek.com/v1/chat/completions";
const HEADERS = { Authorization: `Bearer ${process.env.DEEPSEEK_API_KEY}` };
const TOOLS = [{ type: "function", function: { name: "lookup_playbook", description: "Return the customer's rule for a topic", parameters: { type: "object", properties: { topic: { type: "string" } }, required: ["topic"] } } }];

async function main() {
  const messages: any[] = [{ role: "user", content: "Is unlimited liability acceptable? [loop]" }];
  let used = 0;
  for (let step = 1; step <= 4; step++) {
    const res = await fetch(API_URL, { method: "POST", headers: HEADERS, body: JSON.stringify({ model: "deepseek-flash", messages, tools: TOOLS, thinking: { type: "disabled" } }) });
    const data = await res.json();
    used += data.usage.total_tokens;
    console.log(`step ${step}: +${data.usage.total_tokens} tokens, total ${used}`);
    const call = data.choices[0].message.tool_calls[0];
    messages.push(data.choices[0].message);
    messages.push({ role: "tool", tool_call_id: call.id, content: "rule for liability_cap: cap at 12 months of fees" });
  }
}
main();

@@ concept
title: Traces: record every step
--- body
A lawyer asks "why was 8.1 flagged?" You need to be able to open a record and see which tools the model called, with which arguments, whether each call succeeded, and what it got back. This is a **trace**, and it is what tools like Langfuse display.

Record one entry per tool call:

```ts
type TraceEntry = { step: number; tool: string; args: string; ok: boolean; result: string };
```

`args` records the model's **raw text** (record bad JSON too: it's what you need most when debugging). Clause Check's `ReviewTrace` records `steps`, token counts, `stop_reason`, and a list of `tool_calls` labels such as `lookup_playbook:liability_cap`, `get_clause:12`, `propose_redline:INVALID_ARGS`.

The debugging order is still the one from Day 7: first look at what the model received (the trace), then question the model's reasoning.
--- code
type TraceEntry = { step: number; tool: string; args: string; ok: boolean; result: string };

const trace: TraceEntry[] = [];
function record(step: number, tool: string, args: string, ok: boolean, result: string): void {
  trace.push({ step, tool, args, ok, result: result.slice(0, 40) });
}

record(1, "lookup_playbook", '{"topic":"liability_cap"}', true, "Cap at 12 months of fees; never accept unlimited liability.");
record(2, "get_clause", '{"clause_id":"12"}', true, "The limitations in Section 8 shall not apply to Customer.");
record(3, "propose_redline", '{"clause_id":', false, "INVALID_JSON: arguments are not valid JSON");

for (const e of trace) {
  console.log(`${e.step} ${e.ok ? "ok " : "ERR"} ${e.tool.padEnd(16)} ${e.args}`);
}
const errors = trace.filter((e) => !e.ok).length;
console.log(`${trace.length} tool calls, ${errors} error(s)`);

@@ concept
title: Human in the loop: risky tools need a person to approve
--- body
Looking up the playbook and reading clauses are **read-only**: a wrong call does no harm. Tools with consequences, like sending an email, changing a contract or making a payment, must ask a person first:

- Mark the tool with `needsApproval: true`
- Before the loop runs it, call an **injected** `approve(request)` function. In a real app it shows buttons and waits for a person to click; in tests you pass a fake one
- When it is rejected, don't run it: send `DENIED: ...` back to the model as the tool result, so it tries another approach
- **Approval must never come from the model**: don't give the tool an `approved` parameter for the model to fill in itself

Clause Check does the same: `propose_redline` only "records a proposal", and before the change is actually written into the exported file, the `approve` node in `graph.py` stops and waits for a person to decide (tomorrow you hand-write this "pause and resume").
--- code
type Call = { tool: string; args: Record<string, string> };
const NEEDS_APPROVAL = new Set(["send_redline_email"]);

async function execute(call: Call, approve: (c: Call) => Promise<boolean>): Promise<string> {
  if (NEEDS_APPROVAL.has(call.tool)) {
    const yes = await approve(call);
    if (!yes) {
      return `DENIED: the user rejected ${call.tool}`;
    }
  }
  return `ran ${call.tool} for ${call.args.clause_id}`;
}

async function main() {
  const alwaysNo = async (c: Call) => {
    console.log(`  (asking a human about ${c.tool})`);
    return false;
  };
  const alwaysYes = async (_c: Call) => true;
  console.log(await execute({ tool: "lookup_playbook", args: { clause_id: "8.1" } }, alwaysNo));
  console.log(await execute({ tool: "send_redline_email", args: { clause_id: "8.1" } }, alwaysNo));
  console.log(await execute({ tool: "send_redline_email", args: { clause_id: "8.1" } }, alwaysYes));
}
main();

@@ concept
title: Idempotency: a retry must not send two emails
--- body
The same tool call may run more than once: the model calls it again, the whole step is retried after a 429, or the program crashes and resumes from a checkpoint (tomorrow). For read-only tools that doesn't matter, but **an email gets sent twice**.

The fix is called **idempotency**: give every action a fixed key (for example `` `${clauseId}:${action}` ``), and after the action succeeds, record the key in a `Set`. The next time you see the same key, return "already done" right away instead of really doing it again.

Two key points:

- Record the key **after the action succeeds**. If sending fails, don't record it, so a retry can still send
- In a real system this Set has to live in a database, or the program forgets it the moment it restarts. Payment APIs like Stripe support an `Idempotency-Key` request header; it's the same idea
--- code
class Outbox {
  #done = new Set<string>();
  sent: string[] = [];

  send(clauseId: string, action: string): string {
    const key = `${clauseId}:${action}`;
    if (this.#done.has(key)) {
      return `ALREADY_DONE: ${key}`;
    }
    this.sent.push(key);
    this.#done.add(key);
    return `SENT: ${key}`;
  }
}

const outbox = new Outbox();
console.log(outbox.send("8.1", "redline_email"));
console.log(outbox.send("8.1", "redline_email"));
console.log(outbox.send("8.1", "reminder"));
console.log(outbox.sent);

--- code
type Step =
  | { kind: "tool"; name: string; ok: boolean }
  | { kind: "answer"; text: string }
  | { kind: "stopped"; reason: "max_steps" | "budget" };

function describe(s: Step): string {
  switch (s.kind) {
    case "tool":
      return s.ok ? `called ${s.name}` : `${s.name} failed`;
    case "answer":
      return `answer (${s.text.length} chars)`;
    case "stopped":
      return `stopped: ${s.reason}`;
  }
}

const steps: Step[] = [
  { kind: "tool", name: "lookup_playbook", ok: true },
  { kind: "tool", name: "get_clause", ok: false },
  { kind: "answer", text: "Flag it." },
];
for (const s of steps) {
  console.log(describe(s));
}
console.log(describe({ kind: "stopped", reason: "budget" }));
--- explain
Whichever case `switch (s.kind)` enters, TypeScript knows which kind `s` is, so inside `case "tool"` you can use `s.name`, and inside `case "answer"` you can use `s.text`. Today's stop reason `"answer" | "max_steps" | "budget"` is also a union of literals, and the caller handles each one in a switch.

title: Recap: arguments must be an object
level: 1
cards: Argument validation: errors are messages for the model; d16:Result: failure is a return value too
--- context
When the model wants to call a tool, the arguments are a piece of JSON text it wrote itself. The text may be broken, or not the shape the tool needs. This is the first check before a tool runs: a problem must turn into a one-line error message, not crash the whole review.
--- prompt
Review Day 16's `Result`. Tool arguments must be a JSON **object**. Write `parseJsonObject(text)`:

- parsing fails: `{ ok: false, error: "INVALID_JSON" }`
- the parsed value is not an object (an array, `null`, a string, a number): `{ ok: false, error: "NOT_AN_OBJECT" }`
- otherwise: `{ ok: true, value: <the parsed value> }`

Example: `parseJsonObject('["payment"]')` → `{ ok: false, error: "NOT_AN_OBJECT" }`. `review.py` has this check too: "arguments were not a JSON object".
--- starter
type Result<T> = { ok: true; value: T } | { ok: false; error: string };

function parseJsonObject(text: string): Result<object> {
  return { ok: false, error: "" };
}
--- solution
type Result<T> = { ok: true; value: T } | { ok: false; error: string };

function parseJsonObject(text: string): Result<object> {
  let data: unknown;
  try {
    data = JSON.parse(text);
  } catch {
    return { ok: false, error: "INVALID_JSON" };
  }
  if (typeof data !== "object" || data === null || Array.isArray(data)) {
    return { ok: false, error: "NOT_AN_OBJECT" };
  }
  return { ok: true, value: data };
}
--- tests
expect("a valid object", () => parseJsonObject('{"topic": "payment"}'), { ok: true, value: { topic: "payment" } });
expect("bad JSON", () => parseJsonObject('{"topic": '), { ok: false, error: "INVALID_JSON" });
expect("an array doesn't count", () => parseJsonObject('["payment"]'), { ok: false, error: "NOT_AN_OBJECT" });
expect("null doesn't count", () => parseJsonObject("null"), { ok: false, error: "NOT_AN_OBJECT" });
expect("a string doesn't count", () => parseJsonObject('"payment"'), { ok: false, error: "NOT_AN_OBJECT" });
--- hints
- First wrap `JSON.parse` in a try/catch and store the result in `let data: unknown`.
- `typeof null` is also `"object"`, and so is the typeof of an array, so you also need to check `data === null` and `Array.isArray(data)`.

import { z } from "zod";

type AnySchema = ReturnType<typeof z.any>;
type Tool = { name: string; description: string; schema: AnySchema; run: (args: any) => string | Promise<string> };
type ToolSpec = { type: "function"; function: { name: string; description: string; parameters: Record<string, any> } };

function toolSpec(tool: Tool): ToolSpec {
  const parameters = z.toJSONSchema(tool.schema);
  delete parameters.$schema;
  return { type: "function", function: { name: tool.name, description: tool.description, parameters } };
}

title: Where the restriction goes
level: 1
cards: Tool registry: one schema, two uses; Argument validation: errors are messages for the model
--- context
`lookup_playbook` looks up the customer's review rules by topic. Sometimes the model makes up a topic name that isn't in the playbook; then no rule is found, and the verdict it gives has nothing to rest on.
--- prompt
The `topic` argument of `lookup_playbook` must be one of the 11 topics in the playbook. Where is the best place to put this restriction?
--- options
- Only in the description: "topic must be one of liability_cap, payment, …"
- As `z.enum([...])`: it becomes an `enum` in the JSON Schema the model sees, and `safeParse` also really blocks invalid values in code
- No restriction needed: the tool returns an empty string when it finds nothing
- In the system prompt, so the model remembers it
answer: 2
--- explain
The description and the prompt are "suggestions" to the model, and it may ignore them; the schema is a "rule": it generates the `enum` the model sees and is also enforced in code. That's how `tools.py` does it: `topic: Topic` in `LookupPlaybookArgs` is a `Literal` with 11 values, and the generated schema has an `enum`. What the description should say is "when to use it, when not to, and what happens after the call" (the lesson of `mark_for_review` on Day 12). Returning an empty string is the worst choice: the model concludes the playbook has no requirement for that topic.

type: fill
title: Fill in: the registry
level: 1
cards: Tool registry: one schema, two uses; d16:Map and Set
--- context
A tool call the agent receives contains only a tool name. The registry is a "name → tool" table: it is built when the program starts, and the loop looks tools up in it by name every time. Now and then the model writes a tool name that doesn't exist.
--- prompt
Fill in the blanks to complete `buildRegistry` (throw on a duplicate name) and `findTool` (when the name isn't found, return an error text that lists the available tools, so the model knows which name to use).
--- template
import { z } from "zod";

type AnySchema = ReturnType<typeof z.any>;
type Tool = { name: string; description: string; schema: AnySchema; run: (args: any) => string };

function buildRegistry(tools: Tool[]): Map<string, Tool> {
  const registry = new [[Map]]<string, Tool>();
  for (const t of tools) {
    if (registry.[[has]](t.name)) {
      throw new Error(`duplicate tool: ${t.name}`);
    }
    registry.[[set]](t.name, t);
  }
  return registry;
}

function findTool(registry: Map<string, Tool>, name: string): Tool | string {
  return registry.[[get]](name) ?? `UNKNOWN_TOOL: ${name}. Available: ${[...registry.keys()].join(", ")}`;
}
--- tests
const mk = (name: string): Tool => ({ name, description: name, schema: z.object({}), run: () => name });
const REG = buildRegistry([mk("lookup_playbook"), mk("get_clause")]);
expect("two tools", () => REG.size, 2);
expect("found", () => {
  const t = findTool(REG, "get_clause");
  return typeof t === "string" ? t : t.name;
}, "get_clause");
expect("not found", () => findTool(REG, "delete_all"), "UNKNOWN_TOOL: delete_all. Available: lookup_playbook, get_clause");
expectThrows("duplicate name", () => buildRegistry([mk("get_clause"), mk("get_clause")]));
--- hints
- Four Map members you use all the time: `has`, `get`, `set`, `size` (the last one is a property).
- `registry.get(name)` is `undefined` when nothing is found, so the `??` after it supplies the error text.

  const tool = registry.get(call.function.name);

  const messages: any[] = [{ role: "user", content: question }];

    const res = await fetch(API_URL, {
      method: "POST",
      headers: HEADERS,

  const messages: any[] = [{ role: "user", content: question }];

    const data = await callModel(messages, registry);
    tokens += data.usage.total_tokens;
    const choice = data.choices[0];

    }

import { z } from "zod";

type AnySchema = ReturnType<typeof z.any>;
type Tool = { name: string; description: string; schema: AnySchema; run: (args: any) => string | Promise<string>; needsApproval?: boolean };
type ToolCall = { id: string; function: { name: string; arguments: string } };
type ToolResult = { ok: boolean; content: string };
type ApprovalRequest = { tool: string; args: any };
type Approve = (req: ApprovalRequest) => Promise<boolean>;
type Result<T> = { ok: true; value: T } | { ok: false; error: string };

function parseArgs(tool: Tool, text: string): Result<any> {
  let raw: unknown;
  try {
    raw = JSON.parse(text);
  } catch {
    return { ok: false, error: "INVALID_JSON: arguments are not valid JSON" };
  }
  const r = tool.schema.safeParse(raw);
  if (!r.success) {
    const issue = r.error.issues[0];
    return { ok: false, error: `INVALID_ARGS: ${issue.path.join(".")}: ${issue.message}` };
  }
  return { ok: true, value: r.data };
}

async function gatedDispatch(registry: Map<string, Tool>, call: ToolCall, approve: Approve): Promise<ToolResult> {
  const tool = registry.get(call.function.name);
  if (!tool) {
    return { ok: false, content: `UNKNOWN_TOOL: ${call.function.name}` };
  }
  const args = parseArgs(tool, call.function.arguments);
  if (!args.ok) {
    return { ok: false, content: args.error };
  }
  if (tool.needsApproval) {
    const yes = await approve({ tool: tool.name, args: args.value });
    if (!yes) {
      return { ok: false, content: `DENIED: the user rejected ${tool.name}` };
    }
  }
  return { ok: true, content: await tool.run(args.value) };
}

class Outbox {

  #mailer: (key: string) => void;

  constructor(mailer: (key: string) => void) {
    this.#mailer = mailer;
  }

- schema validation fails (take the first issue): `{ ok: false, content: "INVALID_ARGS: " + issue.path.join(".") + ": " + issue.message }`
- `run` throws: `{ ok: false, content: "TOOL_ERROR: " + <the error's message> }`

--- solution
import { z } from "zod";

type AnySchema = ReturnType<typeof z.any>;
type Tool = { name: string; description: string; schema: AnySchema; run: (args: any) => string | Promise<string> };
type ToolCall = { id: string; function: { name: string; arguments: string } };
type ToolResult = { ok: boolean; content: string };

async function dispatch(registry: Map<string, Tool>, call: ToolCall): Promise<ToolResult> {
  const tool = registry.get(call.function.name);
  if (!tool) {
    return { ok: false, content: `UNKNOWN_TOOL: ${call.function.name}` };
  }
  let raw: unknown;
  try {
    raw = JSON.parse(call.function.arguments);
  } catch {
    return { ok: false, content: "INVALID_JSON" };
  }
  const r = tool.schema.safeParse(raw);
  if (!r.success) {
    const issue = r.error.issues[0];
    return { ok: false, content: `INVALID_ARGS: ${issue.path.join(".")}: ${issue.message}` };
  }
  try {
    return { ok: true, content: await tool.run(r.data) };
  } catch (e) {
    return { ok: false, content: `TOOL_ERROR: ${e instanceof Error ? e.message : String(e)}` };
  }
}

--- solution
const TOOLS = [{ type: "function", function: { name: "lookup_playbook", description: "Return the customer's rule for a topic", parameters: { type: "object", properties: { topic: { type: "string" } }, required: ["topic"] } } }];

function runTool(argText: string): string {
  try {
    return `rule for ${JSON.parse(argText).topic}`;
  } catch {
    return "INVALID_JSON";
  }
}

async function agent(question: string, maxSteps: number): Promise<{ reason: "answer" | "max_steps"; answer: string | null; steps: number }> {
  const messages: any[] = [{ role: "user", content: question }];
  for (let step = 1; step <= maxSteps; step++) {
    const res = await fetch("https://api.deepseek.com/v1/chat/completions", {
      method: "POST",
      headers: { Authorization: `Bearer ${process.env.DEEPSEEK_API_KEY}` },
      body: JSON.stringify({ model: "deepseek-flash", messages, tools: TOOLS, thinking: { type: "disabled" } }),
    });
    const choice = (await res.json()).choices[0];
    if (choice.finish_reason !== "tool_calls") {
      return { reason: "answer", answer: choice.message.content, steps: step };
    }
    messages.push(choice.message);
    for (const call of choice.message.tool_calls) {
      messages.push({ role: "tool", tool_call_id: call.id, content: runTool(call.function.arguments) });
    }
  }
  return { reason: "max_steps", answer: null, steps: maxSteps };
}

  2. otherwise ask `approve(key)`; if it's rejected, return `"DENIED"` (don't record anything; you can ask again later)

class ActionRunner {
  #done = new Set<string>();
  #approve: (key: string) => boolean;
  #perform: (key: string) => void;

  constructor(approve: (key: string) => boolean, perform: (key: string) => void) {
    this.#approve = approve;
    this.#perform = perform;
  }

  run(clauseId: string, action: string): "DONE" | "DUPLICATE" | "DENIED" {
    const key = `${clauseId}:${action}`;
    if (this.#done.has(key)) {
      return "DUPLICATE";
    }
    if (!this.#approve(key)) {
      return "DENIED";
    }
    this.#perform(key);
    this.#done.add(key);
    return "DONE";
  }
}
