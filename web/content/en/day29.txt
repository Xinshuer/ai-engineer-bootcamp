@@ concept
title: Why use a framework (and when not to)
--- body
On Day 4 you wrote a call yourself: build the URL, add the `Authorization` request header, put together the JSON request body, and take the answer from `choices[0]["message"]["content"]`. LangChain wraps all of this in a **chat model object**:

```python
model = ChatDeepSeek(model="deepseek-flash")
reply = model.invoke("Review clause 3.1 ...")   # returns an AIMessage
```

The upside: switching providers mostly means changing just this line (`ChatOpenAI` and `ChatAnthropic` work the same way); messages, templates, retries, streaming, token counts, tools and structured output all have one common way of writing them. The cost: several extra layers, so tracebacks get long; and it changes fast: 1.0 came out in October 2025, and the `LLMChain` and `langchain.chains` from older tutorials are gone from the `langchain` package in 1.x (1.0 moved many old modules into `langchain-classic`).

Clause Check's choice (see the README): the review flow is linear, so plain Python is enough; LangGraph is used only for "pause and wait for a person to approve, then continue in another process".

The two pieces of code below send the same request (LangChain only adds one extra `"stream": False`). `MOCK.calls[-1]["body"]` is the JSON that LangChain really sent; you will look at it a lot this week.
--- code
import os
import requests
import langchain
import langchain_core
from langchain_deepseek import ChatDeepSeek

question = "Review clause 3.1: Fees are due in 30 days."

# Day 4: by hand
URL = "https://api.deepseek.com/v1/chat/completions"
headers = {"Authorization": f"Bearer {os.getenv('DEEPSEEK_API_KEY')}"}
body = {"model": "deepseek-flash", "messages": [{"role": "user", "content": question}]}
data = requests.post(URL, headers=headers, json=body).json()
print("requests: ", data["choices"][0]["message"]["content"])

# LangChain: the URL, the headers, the API key (read from the environment variable DEEPSEEK_API_KEY) and the parsing are all done for you
model = ChatDeepSeek(model="deepseek-flash")
reply = model.invoke(question)
print("LangChain:", reply.content)
print("request body it sent:", MOCK.calls[-1]["body"])
print("versions: langchain-core", langchain_core.__version__, "| langchain", langchain.__version__)

@@ concept
title: AIMessage and thinking mode
--- body
`invoke` returns an `AIMessage`. The parts you use most:

- `.content`: the answer text
- `.usage_metadata`: `input_tokens`, `output_tokens`, `total_tokens`, plus `input_token_details["cache_read"]` (input that hit the cache) and `"reasoning"` inside `output_token_details` (tokens used for thinking; without thinking this dictionary may be empty, so use `.get("reasoning", 0)`)
- `.response_metadata["finish_reason"]`: why it stopped

In DeepSeek V4, **thinking mode is on by default**: the model thinks before it answers, the thinking goes into `additional_kwargs["reasoning_content"]`, it is **billed as output tokens**, and while it is on, `temperature` has no effect. Short tasks like reviewing or classifying usually turn it off, which is faster and cheaper:

```python
ChatDeepSeek(model="deepseek-flash", extra_body={"thinking": {"type": "disabled"}})
```

Whatever is in `extra_body` goes into the request body as it is (langchain-deepseek 1.1, which this page uses, has no dedicated thinking parameter). `temperature=0` only means something once thinking is off.

Model names: use `deepseek-flash` (cheap, fast) or `deepseek-v4-pro` now. DeepSeek has officially announced that `deepseek-chat` and `deepseek-reasoner`, from older tutorials, are retired from 2026-07-24; tested in 2026-09 they could still be called (both answered by `deepseek-flash`), but they are no longer in the model list and may stop working at any time, so don't use them anymore. A wrong model name returns 400, with the error message `The supported API model names are deepseek-flash, deepseek-v4-pro, but you passed ...`. You can also pick the provider with a string: `init_chat_model("deepseek:deepseek-flash")` gives you a `ChatDeepSeek` as well.
--- code
from langchain_deepseek import ChatDeepSeek

QUESTION = "Review clause 8.1: Customer's liability shall be unlimited."
default = ChatDeepSeek(model="deepseek-flash")
fast = ChatDeepSeek(model="deepseek-flash", extra_body={"thinking": {"type": "disabled"}}, temperature=0)

msg = default.invoke(QUESTION)
print(type(msg).__name__, "|", msg.content)
print("finish_reason:", msg.response_metadata["finish_reason"])
print("thinking:", msg.additional_kwargs["reasoning_content"])
for name, model in [("thinking on ", default), ("thinking off", fast)]:
    u = model.invoke(QUESTION).usage_metadata
    print(f"{name}: output {u['output_tokens']} tokens, of which reasoning {u['output_token_details'].get('reasoning', 0)}")
print("sent:", {k: v for k, v in MOCK.calls[-1]["body"].items() if k != "messages"})

@@ concept
title: Messages
--- body
Day 4's `role` turns into classes: `SystemMessage` (system), `HumanMessage` (user), `AIMessage` (assistant), and tomorrow `ToolMessage` as well. `invoke` also accepts a shorthand: `[("system", "..."), ("user", "...")]`, or dictionaries like on Day 4.

**Multi-turn conversations**: the model remembers nothing by itself, so every turn has to send the **whole history**. How: append the `AIMessage` the model returned to the list as it is, then append the next `HumanMessage`. The longer the history, the more tokens each request uses (Day 33 covers how to trim it).

Every `AIMessage` the model returns carries a random `id` (`lc_run--...`) that is different on every run (messages you create yourself have `None` as their `id`). So in tests, compare `.content` and `type(m).__name__`, not whole messages.
--- code
from langchain_core.messages import HumanMessage, SystemMessage
from langchain_deepseek import ChatDeepSeek

model = ChatDeepSeek(model="deepseek-flash", extra_body={"thinking": {"type": "disabled"}})

history = [
    SystemMessage("You review contract clauses for the Customer."),
    HumanMessage("Review clause 8.1: liability is unlimited."),
]
first = model.invoke(history)
history.append(first)                                   # put the model's answer back as it is
history.append(HumanMessage("Now clause 9.2: fees are due in 30 days."))
second = model.invoke(history)

for m in history + [second]:
    print(f"{type(m).__name__:<14}{m.content}")
print("roles sent:", [m["role"] for m in MOCK.calls[-1]["body"]["messages"]])
print("shorthand:", model.invoke([("system", "You review contracts."), ("user", "Hi")]).content)
print("id:", first.id[:8] + "... (different on every run)")

@@ concept
title: ChatPromptTemplate
--- body
On Day 12 you wrote templates with `str.format`. A LangChain template is **a list of message templates**:

```python
prompt = ChatPromptTemplate.from_messages([("system", "You review clauses for the {party}."), ("user", "{text}")])
prompt.invoke({"party": "Customer", "text": "..."}).to_messages()
```

- `.invoke(dict)` returns a `ChatPromptValue`; `.to_messages()` takes out the list of messages
- `input_variables`: which variables it needs (sorted alphabetically). Leave one out → `KeyError`, and the message says which one is missing
- To write a JSON example in a template, double the braces `{{ }}`, just like on Day 12; braces inside a **variable's value** are fine, because values are not treated as templates again
- `MessagesPlaceholder("history")`: inserts a whole run of history messages at this position
- `.partial(party="Customer")`: fills in part of it now and returns a new template
--- code
from langchain_core.prompts import ChatPromptTemplate, MessagesPlaceholder

review = ChatPromptTemplate.from_messages([
    ("system", 'You review clauses for the {party}. Reply as JSON like {{"verdict": "accept"}}.'),
    ("user", "Review clause {clause_id}: {text}"),
])
print(review.input_variables)
value = review.invoke({"party": "Customer", "clause_id": "8.1", "text": "Pay {net 30}."})
print(type(value).__name__)
for m in value.to_messages():
    print(" ", type(m).__name__, "->", m.content)

try:
    review.invoke({"party": "Customer", "clause_id": "8.1"})
except KeyError as e:
    print("KeyError:", e.args[0].split(".")[0])

print(review.partial(party="Customer").input_variables)

chat = ChatPromptTemplate.from_messages([
    ("system", "You answer questions about one contract."),
    MessagesPlaceholder("history"),
    ("user", "{question}"),
])
msgs = chat.invoke({"history": [("user", "What is clause 8.1?"), ("assistant", "A liability cap.")], "question": "Is it mutual?"}).to_messages()
print([type(m).__name__ for m in msgs])

@@ concept
title: LCEL: chain steps with |
--- body
Almost every part in LangChain is a **Runnable**: they all have `invoke` (one input), `batch` (a batch of inputs) and `stream` (streaming). `|` joins them into a chain, and the output of one step is the input of the next:

```
dict --prompt--> ChatPromptValue --model--> AIMessage --StrOutputParser()--> str
```

Put a plain function in the pipe and it is wrapped into a `RunnableLambda` automatically. The whole chain is a Runnable too, so it can also batch, stream and take callbacks.

Run the example below and you'll see that the type name of `StrOutputParser`'s output is `TextAccessor`: it is a subclass of `str` (added in 1.0 to stay compatible with older code), so just use it like a normal string; `==`, `.strip()` and `isinstance(x, str)` all work as usual.

The classic mistake: the order is reversed, for example the parser goes before the model. It then receives a ChatPromptValue instead of an AIMessage and raises a hard-to-read `ValidationError`. **When debugging, look at the input and output type of each step**; the example below walks through it one step at a time.
--- code
from langchain_core.messages import AIMessage
from langchain_core.output_parsers import StrOutputParser
from langchain_core.prompts import ChatPromptTemplate
from langchain_deepseek import ChatDeepSeek

prompt = ChatPromptTemplate.from_messages([("system", "You summarise clauses in one sentence."), ("user", "{text}")])
model = ChatDeepSeek(model="deepseek-flash", extra_body={"thinking": {"type": "disabled"}})
chain = prompt | model | StrOutputParser() | (lambda s: s.upper())

print(type(chain).__name__, [type(s).__name__ for s in chain.steps])
value = {"text": "Fees are due in 30 days."}
for step in chain.steps:           # walk through the pipe by hand and see what type each step outputs
    value = step.invoke(value)
    print(f"  {type(step).__name__:<19}-> {type(value).__name__}")
print(chain.invoke({"text": "Fees are due in 30 days."}))

text = StrOutputParser().invoke(AIMessage("accept"))
print(type(text).__name__, isinstance(text, str), text == "accept")

@@ concept
title: stream and batch
--- body
- `chain.stream(input)`: hands you the answer one piece at a time; on screen this is the typewriter effect. When the chain ends with `StrOutputParser`, each piece is a string. Some pieces are **empty strings**: the first one (it only carries the role) and the last one (only the finish reason and the usage) are always there; with thinking mode on, a long run of them also comes first (the thinking is not part of the answer). Skip them when you display the answer
- `chain.batch([input1, input2, ...])`: the results come back in the same order as the inputs
- `return_exceptions=True`: the position that failed holds the exception object, and the others come back as usual (Day 28's "one failure doesn't take down the rest"). Without it, one failure makes the whole batch raise
- `config={"max_concurrency": 3}`: at most 3 requests at the same time. The browser on this page has no threads, so they run one after another; on your own computer they really run in parallel

A real web service usually uses the async versions: `await chain.ainvoke(...)`, `astream`, `abatch`. This page can't run asyncio, so they are only mentioned here.
--- code
from langchain_core.output_parsers import StrOutputParser
from langchain_core.prompts import ChatPromptTemplate
from langchain_deepseek import ChatDeepSeek

prompt = ChatPromptTemplate.from_messages([("user", "{text}")])
off = prompt | ChatDeepSeek(model="deepseek-flash", extra_body={"thinking": {"type": "disabled"}}) | StrOutputParser()
on = prompt | ChatDeepSeek(model="deepseek-flash") | StrOutputParser()

print(list(off.stream({"text": "Summarise clause 9.2 on fees"})))
pieces = list(on.stream({"text": "Summarise clause 9.2 on fees"}))
print(len(pieces), "pieces with thinking on,", pieces.count(""), "of them empty")

inputs = [{"text": "Fees are due in 30 days."}, {"text": "Liability is unlimited."}, {"wrong_key": "x"}]
print(off.batch(inputs[:2]))
results = off.batch(inputs, return_exceptions=True, config={"max_concurrency": 2})
print(["ok" if isinstance(r, str) else type(r).__name__ for r in results])

@@ concept
title: Small Runnable building blocks
--- body
- `RunnableLambda(fn)`: turns a function into a Runnable (plain functions in a pipe are wrapped automatically)
- `RunnableParallel(summary=chain1, risk=chain2)`, or simply a dictionary `{"summary": chain1, "risk": chain2}`: hands **the same input** to several chains at once and combines the results into one dictionary
- `RunnablePassthrough.assign(words=fn)`: keeps the input dictionary as it is and adds one key (the value can be a function or a chain)

Typical use: one clause needs both a summary and a risk level; the two requests don't depend on each other, so they can run in parallel.

A reminder: don't use them just for the sake of it. When a plain Python function says it clearly, wrapping it in three layers of Runnable only makes the traceback longer.
--- code
from langchain_core.output_parsers import StrOutputParser
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.runnables import RunnableLambda, RunnableParallel, RunnablePassthrough
from langchain_deepseek import ChatDeepSeek

model = ChatDeepSeek(model="deepseek-flash", extra_body={"thinking": {"type": "disabled"}})
summary = ChatPromptTemplate.from_messages([("user", "Summarise: {text}")]) | model | StrOutputParser()
risk = ChatPromptTemplate.from_messages([("user", "Risk level of: {text}")]) | model | StrOutputParser()

brief = RunnableParallel(summary=summary, risk=risk)
print(brief.invoke({"text": "Liability is unlimited."}))

count = RunnablePassthrough.assign(words=lambda d: len(d["text"].split()))
print(count.invoke({"text": "Liability is unlimited."}))

pipeline = count | RunnableLambda(lambda d: f"{d['words']} words: {d['text']}")
print(pipeline.invoke({"text": "Fees are due in 30 days."}))

@@ concept
title: Testing chains offline: fake models
--- body
On Day 19 you learned dependency injection: **pass the model in as a parameter** (`build_chain(model)`), and in tests pass in a fake one:

- `FakeListChatModel(responses=["a", "b"])`: returns them in order and starts again from the beginning when it runs out
- `GenericFakeChatModel(messages=iter([AIMessage(...)]))`: raises `StopIteration` when it runs out; when streaming, it splits the text into pieces at spaces
- Any Runnable can act as a model: `RunnableLambda(fn)`. `fn` receives the ChatPromptValue, so it can **decide the answer based on the input**, and check along the way that the prompt is right

Limitation: fake models don't support `bind_tools` (`NotImplementedError`); tomorrow, to test tools, you'll use the mock server.

What to test: **the logic you wrote yourself** in the chain (templates, parsing, cleanup). Whether the model answers well is a job for evals (Day 13).
--- code
from langchain_core.language_models.fake_chat_models import FakeListChatModel, GenericFakeChatModel
from langchain_core.messages import AIMessage
from langchain_core.output_parsers import StrOutputParser
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.runnables import RunnableLambda

def build_chain(model):
    prompt = ChatPromptTemplate.from_messages([("system", "Answer with one word: accept, flag or redline."), ("user", "{text}")])
    return prompt | model | StrOutputParser() | (lambda s: s.strip().lower())

chain = build_chain(FakeListChatModel(responses=[" Redline\n", "accept"]))
print([chain.invoke({"text": "x"}) for _ in range(3)])

def by_rule(prompt_value):
    text = prompt_value.to_messages()[-1].content
    return AIMessage("redline" if "unlimited" in text else "accept")

chain = build_chain(RunnableLambda(by_rule))
print(chain.batch([{"text": "Liability is unlimited."}, {"text": "Fees are due."}]))
print("requests to the server:", len(MOCK.calls))

g = GenericFakeChatModel(messages=iter([AIMessage("flag this clause")]))
print([chunk.content for chunk in g.stream("x")])
try:
    FakeListChatModel(responses=["x"]).bind_tools([])
except NotImplementedError:
    print("bind_tools: NotImplementedError")

@@ item d29-03
type: code
title: How many tokens thinking used
level: 2
cards: AIMessage and thinking mode
--- context
For every clause it reviews, Clause Check records how many tokens it used (the model bills by the token), and the cost statistics depend on these numbers. With LangChain, these numbers sit inside the message object that comes back, and you have to take them out yourself.
--- prompt
Write `token_report(model, question)`: answer `question` once with `model` and return a dictionary:

- `"answer"`: the answer text
- `"output"`: the total number of output tokens (`usage_metadata["output_tokens"]`)
- `"reasoning"`: how many of them went into thinking (`usage_metadata["output_token_details"]["reasoning"]`)
- `"thinking"`: whether the answer includes a thinking process (`True` when `additional_kwargs` has the key `"reasoning_content"`)

The numbers are not always there: with thinking off, the answer may not include a thinking token count (the mock server on this page leaves it out in that case), and `output_token_details` is an empty dictionary; some models don't report usage at all (for example the fake models used in tests), and then `usage_metadata` is `None`. Rules: when `usage_metadata` is `None`, `output` and `reasoning` are both 0; when there is no `output_token_details`, or it has no `"reasoning"`, `reasoning` is 0.

Example: with thinking mode on, `token_report(model, "Review clause 3.1: fees.")` → `{"answer": "Mock reply: Review clause 3.1: fees.", "output": 68, "reasoning": 54, "thinking": True}`
--- starter
def token_report(model, question):
    msg = model.invoke(question)
    return {}
--- solution
def token_report(model, question):
    msg = model.invoke(question)
    usage = msg.usage_metadata or {}
    details = usage.get("output_token_details") or {}
    return {
        "answer": msg.content,
        "output": usage.get("output_tokens", 0),
        "reasoning": details.get("reasoning", 0),
        "thinking": "reasoning_content" in msg.additional_kwargs,
    }
--- tests
from langchain_core.language_models.fake_chat_models import FakeListChatModel, GenericFakeChatModel
from langchain_core.messages import AIMessage
from langchain_deepseek import ChatDeepSeek
ON = ChatDeepSeek(model="deepseek-flash")
OFF = ChatDeepSeek(model="deepseek-flash", extra_body={"thinking": {"type": "disabled"}})
expect("thinking on: most of the output is thinking", lambda: token_report(ON, "Review clause 3.1: fees."), {"answer": "Mock reply: Review clause 3.1: fees.", "output": 68, "reasoning": 54, "thinking": True})
expect("thinking off: the same answer, much cheaper", lambda: token_report(OFF, "Review clause 3.1: fees."), {"answer": "Mock reply: Review clause 3.1: fees.", "output": 14, "reasoning": 0, "thinking": False})
expect("a fake model reports no usage: usage_metadata is None", lambda: token_report(FakeListChatModel(responses=["accept"]), "x"), {"answer": "accept", "output": 0, "reasoning": 0, "thinking": False})
USAGE = {"input_tokens": 5, "output_tokens": 7, "total_tokens": 12}
expect("usage but no output_token_details", lambda: token_report(GenericFakeChatModel(messages=iter([AIMessage("flag", usage_metadata=USAGE)])), "x"), {"answer": "flag", "output": 7, "reasoning": 0, "thinking": False})
--- hints
- Start with `usage = msg.usage_metadata or {}`: if it is None, it becomes an empty dictionary, and after that you can always use `.get(key, 0)`.
- `details = usage.get("output_token_details") or {}`, then `details.get("reasoning", 0)`.
- Whether a key is there: `"reasoning_content" in msg.additional_kwargs`.

title: What the template turns into
level: 2
cards: ChatPromptTemplate
--- context
In a review prompt, some parts never change and some change every time, such as the clause number and the clause text; this exercise also leaves "which party we review for" as a blank. LangChain separates these two kinds of parts with a template. First see clearly what the template turns into once it is filled in.
--- prompt
Write the output. `input_variables` is sorted alphabetically.
--- code
from langchain_core.prompts import ChatPromptTemplate

prompt = ChatPromptTemplate.from_messages([
    ("system", "You review contracts for the {party}."),
    ("user", "Clause {clause_id}: {text}"),
])
print(prompt.input_variables)
value = prompt.invoke({"party": "Customer", "clause_id": "8.1", "text": "Liability is unlimited."})
for m in value.to_messages():
    print(type(m).__name__, "->", m.content)
customer = prompt.partial(party="Customer")
print(customer.input_variables)
print(customer.invoke({"clause_id": "3.1", "text": "Net 30."}).to_messages()[1].content)

--- context
When an interviewer sees that your project uses LangGraph in only one file and calls the model by hand everywhere else, they will very likely ask why.
--- prompt
Clause Check's `review.py` calls DeepSeek directly with `requests`; only `graph.py` uses LangGraph. The interviewer asks: "Why not switch the whole project to LangChain?" Which answer is best?
--- options
- LangChain doesn't support DeepSeek, so the calls have to be written by hand
- Every LangChain call is much slower than requests, which hurts performance
- The review flow is a fixed series of linear steps; plain Python is enough, easy to debug, and has few dependencies. What really needs a framework is "pause and wait for a person to approve, then resume in another process", and only that part uses LangGraph. - The more frameworks, the more professional; everything should be switched, because interviewers like to see frameworks
answer: 3
--- explain
Option 1 is wrong: the `langchain-deepseek` used today is the official integration. Option 2 is wrong: the overhead of the framework's Python layers is negligible next to a model call that takes a few seconds; the real cost is the extra abstraction and dependencies (longer tracebacks, fast-changing versions). Adding things as you need them, and being able to say which specific problem each framework solves, is what the interviewer wants to hear. This is exactly the "Why LangGraph was not the first choice" section of the README.

All the clauses of a contract are sent for review in one batch, and the results are organized by clause number and handed on to report generation. With many clauses, the number of requests sent at the same time needs a cap too, so the model service doesn't rate-limit you.
--- prompt
Write `review_batch(chain, clauses)`:

- `clauses` is a list of dictionaries, each with `"clause_id"` and `"text"`; the input of `chain` is exactly one such dictionary, and it outputs a string
- call `chain.batch(...)` only **once**, with `return_exceptions=True` and `config={"max_concurrency": 4}`
- return a dictionary `{clause_id: result}`; for a clause that failed, the result is `"ERROR: " + the exception's class name`
- `clauses` is an empty list: return `{}` without calling the chain

Example: the second one raises ValueError → `{"3.1": "accept", "5.2": "ERROR: ValueError", "8.1": "redline"}`
--- solution
def review_batch(chain, clauses):
    if not clauses:
        return {}
    results = chain.batch(clauses, config={"max_concurrency": 4}, return_exceptions=True)
    out = {}
    for clause, result in zip(clauses, results):
        out[clause["clause_id"]] = f"ERROR: {type(result).__name__}" if isinstance(result, Exception) else result
    return out

--- context
This exercise's contract Q&A assistant has to hold an ongoing conversation, but the longer the history, the more tokens each request uses (the model bills by the token). The full conversation record should be kept, but what is sent to the model each time doesn't have to be all of it.
--- prompt
Write the class `ChatSession`:

- `ChatSession(model, max_history=4)`: `self.history` starts as an empty list
- The chain it uses: the prompt is system `"You answer questions about one contract for the Customer."` → `MessagesPlaceholder("history")` → user `"{question}"`, followed by `model` and `StrOutputParser()`
- `ask(question)`: put only the **last `max_history` messages** of `self.history` into the history slot (`max_history=0` means none at all), and call the chain to get the answer; then append `HumanMessage(question)` and `AIMessage(answer)` to `self.history` (this stores the full history, untrimmed); return the answer

Careful: `lst[-0:]` is the whole list, not an empty list.

Imports: `AIMessage` and `HumanMessage` from `langchain_core.messages`, `ChatPromptTemplate` and `MessagesPlaceholder` from `langchain_core.prompts`, `StrOutputParser` from `langchain_core.output_parsers`.
--- solution
from langchain_core.messages import AIMessage, HumanMessage
from langchain_core.output_parsers import StrOutputParser
from langchain_core.prompts import ChatPromptTemplate, MessagesPlaceholder

PROMPT = ChatPromptTemplate.from_messages([
    ("system", "You answer questions about one contract for the Customer."),
    MessagesPlaceholder("history"),
    ("user", "{question}"),
])

class ChatSession:
    def __init__(self, model, max_history=4):
        self.chain = PROMPT | model | StrOutputParser()
        self.max_history = max_history
        self.history = []

    def ask(self, question):
        recent = self.history[-self.max_history:] if self.max_history > 0 else []
        answer = self.chain.invoke({"history": recent, "question": question})
        self.history.append(HumanMessage(question))
        self.history.append(AIMessage(answer))
        return answer
