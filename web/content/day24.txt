title: CREATE TABLE：给数据立规矩
lang: sql
dataset: clausecheck
--- body
表不只是装数据的格子。建表时写下的**约束**，是坏数据进库前的最后一道关：模型偶尔会返回 `risk_level: "critical"`（样例数据里 1047 那条失败就是这样），这种值就不该进库。下面是律师反馈表 `feedback`，已经建好了：

```sql
CREATE TABLE feedback (
  id INTEGER PRIMARY KEY,
  review_id INTEGER NOT NULL REFERENCES reviews(id),
  reviewer TEXT NOT NULL,
  verdict TEXT NOT NULL CHECK (verdict IN ('accept', 'flag', 'redline')),
  note TEXT,
  created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
  UNIQUE (review_id, reviewer)
);
```

- 类型：`INTEGER`、`TEXT`、`REAL`（小数）
- `PRIMARY KEY`：每行的唯一编号。SQLite 里 `INTEGER PRIMARY KEY` 不给值时自动取下一个号（Postgres 不会，要写 `BIGINT GENERATED ALWAYS AS IDENTITY` 或 `BIGSERIAL`）
- `NOT NULL` 必须有值；`DEFAULT` 不给时用默认值；`UNIQUE` 不能重复（可以是几列的组合）；`CHECK (...)` 值必须满足条件
- `REFERENCES reviews(id)`：**外键**，必须指向 reviews 里真实存在的一行
- 一种东西一张表：客户、合同、审查、反馈各一张，用 id 连起来（昨天的 JOIN）

SQLite 的两个坑：外键默认**不检查**，要先执行 `PRAGMA foreign_keys = ON`；类型也很宽松，往 INTEGER 列里放 `'abc'` 也能存进去。Postgres 两样都严格。

运行下面的插入，再把 `'accept'` 改成 `'maybe'`，或者把 `reviewer` 这一列连同它的值 `'anna'` 一起删掉，再运行，读读报错。
--- schema
CREATE TABLE feedback (
  id INTEGER PRIMARY KEY,
  review_id INTEGER NOT NULL REFERENCES reviews(id),
  reviewer TEXT NOT NULL,
  verdict TEXT NOT NULL CHECK (verdict IN ('accept', 'flag', 'redline')),
  note TEXT,
  created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
  UNIQUE (review_id, reviewer)
);
--- code
INSERT INTO feedback (review_id, reviewer, verdict, note)
VALUES (1005, 'anna', 'accept', 'A 12-month cap is fine for this customer')
RETURNING *;

title: INSERT、UPDATE、DELETE：先 SELECT 再动手
lang: sql
dataset: clausecheck
--- body
三条改数据的语句：

```sql
INSERT INTO customers (name, country, plan, signed_up)
VALUES ('Oslo Maritime AS', 'NO', 'pro', '2026-09-20');
UPDATE contracts SET status = 'reviewed' WHERE id = 109;
DELETE FROM reviews WHERE id = 1061;
```

- INSERT **永远写出列名**，不要依赖表里列的顺序；没写的列取 DEFAULT，没有默认值就是 NULL。一次插多行：`VALUES (...), (...)`；也可以从查询插入：`INSERT INTO 表 (列) SELECT ...`
- UPDATE / DELETE 最危险的错误是**忘了写 WHERE**：整张表都被改掉、删掉
- 好习惯：先写 `SELECT * FROM contracts WHERE id = 109`，看清选中的是哪几行，再把前半句换成 `UPDATE ... SET ...` 或 `DELETE`
- 末尾加 `RETURNING 列`，把改过的行直接返回来看（Postgres 和 SQLite 都支持）

合同 109 的 8.1 条后来重试成功了（1065 那条），下面把合同状态从 failed 改回 reviewed。本页每次运行都从一份全新的样例数据开始，放心改：试试去掉 WHERE 那一行，看 RETURNING 返回几行。

SET status = 'reviewed'
WHERE id = 109
RETURNING id, title, status;

@@ concept
title: UPSERT：重跑也不怕
lang: sql
dataset: clausecheck
--- body
worker 崩溃后重跑一份合同（第 17 天的幂等）：同一个条款的结果会再写一次。表 `latest_verdicts` 以 `(contract_id, clause_id)` 为主键，普通 INSERT 第二次就会撞上 `UNIQUE constraint failed`。

**UPSERT**：不存在就插入，已经存在就更新。

```sql
INSERT INTO 表 (列...) VALUES (...)
ON CONFLICT (主键或 UNIQUE 的列) DO UPDATE SET 列 = excluded.列;
```

- `excluded.verdict` 指「这次想插入、但撞车了的那一行」的值
- `ON CONFLICT (...)` 里写的列，必须正好是一个 PRIMARY KEY 或 UNIQUE 约束，否则报错
- `ON CONFLICT (...) DO NOTHING`：已经有了就跳过
- 这是 Postgres 的写法，SQLite 照着学的，两边一样能用；BigQuery 里对应的是 `MERGE`

表里已经有 `(103, '8.1', 'redline', 1022)`，下面用 1064 那次重审的结果更新它。把 `'8.1'` 改成 `'8.2'` 再运行：这次是插入新行。
--- schema
CREATE TABLE latest_verdicts (
  contract_id INTEGER NOT NULL,
  clause_id TEXT NOT NULL,
  verdict TEXT NOT NULL,
  review_id INTEGER NOT NULL,
  PRIMARY KEY (contract_id, clause_id)
);
INSERT INTO latest_verdicts VALUES (103, '8.1', 'redline', 1022);
--- code
INSERT INTO latest_verdicts (contract_id, clause_id, verdict, review_id)
VALUES (103, '8.1', 'flag', 1064)
ON CONFLICT (contract_id, clause_id) DO UPDATE SET
  verdict = excluded.verdict,
  review_id = excluded.review_id
RETURNING *;

@@ concept
title: sqlite3：在 Python 里用数据库
dataset: clausecheck
--- body
Python 自带 `sqlite3`，不用安装。

- `conn = sqlite3.connect("app.db")` 打开一个数据库文件（没有就新建）；`":memory:"` 是只在内存里的库
- `conn.execute(sql)` 返回一个游标：`.fetchall()` 取出所有行（元组组成的列表），`.fetchone()` 取一行，没有行时是 `None`
- `conn.row_factory = sqlite3.Row` 以后，行可以按列名取值：`row["verdict"]`，`dict(row)` 变成字典。在建好连接后马上设
- 改了数据（INSERT / UPDATE / DELETE）要 `conn.commit()`，改动才真正写进文件，别的连接（别的程序）才看得到。没提交就退出，改动就丢了

本页的 `fresh_db()` 每次给你一个装好样例数据的新内存库。今天写的函数都把 `conn` 当参数传进来（依赖注入），测试就能传一个新库进去，生产代码传真正的库。

下面最后一段用两个连接打开同一个文件，看看 commit 前后的区别。
--- code
import sqlite3
from pathlib import Path

conn = fresh_db()
rows = conn.execute("SELECT id, clause_id, verdict FROM reviews WHERE contract_id = 108").fetchall()
print(rows)
print(conn.execute("SELECT MAX(latency_ms) FROM reviews").fetchone())

conn.row_factory = sqlite3.Row
row = conn.execute("SELECT id, heading, risk FROM reviews WHERE id = 1022").fetchone()
print(row["heading"], row[0], dict(row))

Path("work/d24").mkdir(parents=True, exist_ok=True)
a = sqlite3.connect("work/d24/app.db")
a.execute("CREATE TABLE IF NOT EXISTS notes (text TEXT)")
a.execute("DELETE FROM notes")
a.commit()
a.execute("INSERT INTO notes VALUES ('8.1 needs a lawyer')")
b = sqlite3.connect("work/d24/app.db")
print("before commit:", b.execute("SELECT COUNT(*) FROM notes").fetchone())
a.commit()
print("after commit: ", b.execute("SELECT COUNT(*) FROM notes").fetchone())

title: 参数化查询和 SQL 注入
dataset: clausecheck
--- body
客户名、主题、筛选条件，都来自用户或者模型。第 12 天的提示注入是骗模型，**SQL 注入**是骗数据库。

用 f-string 把值拼进 SQL，值里的 `'` 就变成了 SQL 的一部分：`O'Brien Legal` 让语句语法错误；`x' OR '1'='1` 让 WHERE 永远为真，拿到所有客户。有的驱动允许一次执行好几条语句（比如 Postgres 的 psycopg），那连 `'; DROP TABLE customers; --` 这种「删表」都能混进去；Python 的 `sqlite3` 的 `execute` 一次只执行一条，挡住了删表，但上面两种照样中招。

**参数化**：SQL 里只写占位符，值单独交给数据库。数据库把值永远只当数据，不会当成 SQL 去执行：

- `?` 配元组：`conn.execute("... WHERE name = ?", (name,))`。只有一个值也要写成 `(name,)`，`(name)` 只是一个字符串
- `:name` 配字典：`conn.execute("... WHERE contract_id = :cid", {"cid": 103})`
- 占位符只能代替**值**。表名、列名、`ASC` / `DESC` 不能用参数，只能先检查它在白名单里，再拼进 SQL
- Postgres 的 psycopg 占位符写 `%s`，BigQuery 写 `@name`，道理完全一样
--- code
conn = fresh_db()

def find_unsafe(name):
    sql = f"SELECT id, name FROM customers WHERE name = '{name}'"
    return conn.execute(sql).fetchall()

def find(name):
    return conn.execute("SELECT id, name FROM customers WHERE name = ?", (name,)).fetchall()

print(find_unsafe("Nordlys AB"))
print(len(find_unsafe("x' OR '1'='1")), "rows: injected!")
try:
    find_unsafe("O'Brien Legal")
except Exception as e:
    print(type(e).__name__, e)

print(find("x' OR '1'='1"))
conn.execute("INSERT INTO customers (name, country, plan, signed_up) VALUES (?, ?, ?, ?)", ("O'Brien Legal", "IE", "pro", "2026-09-22"))
print(find("O'Brien Legal"))
print(conn.execute("SELECT id FROM reviews WHERE contract_id = :cid AND risk = :risk", {"cid": 101, "risk": "high"}).fetchall())

@@ concept
title: 事务：要么全成，要么全不
dataset: clausecheck
--- body
一份合同 12 条审查结果，写到第 7 条时出错：库里留下 6 条「半份报告」，比一条都没写还糟，因为看起来像是审完了。

**事务**把一组改动绑在一起：要么全部生效，要么全部撤销。

- `with conn:` 块里全部成功 → 自动 `commit`；抛出异常 → 自动 `rollback`，异常继续往外抛
- `with conn:` **不会关闭连接**，这和 `with open(...)` 不一样，是最常见的误会
- 不用 `with` 也可以：成功后 `conn.commit()`，出错时 `conn.rollback()`
- `executemany(sql, 很多组参数)` 用同一条 SQL 插很多行。中途失败时，前面几行其实已经执行了，只是没提交：不回滚的话，同一个连接里还能看到它们，下次 commit 就一起写进去了

下面第一批里有一条坏数据（`maybe` 不在 CHECK 允许的值里），整批撤销；第二批只有好数据，写入成功。
--- code
import sqlite3

conn = fresh_db()
conn.execute("CREATE TABLE feedback (review_id INTEGER NOT NULL, reviewer TEXT NOT NULL, verdict TEXT NOT NULL CHECK (verdict IN ('accept', 'flag', 'redline')))")
rows = [
    (1062, "anna", "accept"),
    (1063, "anna", "flag"),
    (1064, "anna", "maybe"),
]

try:
    with conn:
        conn.executemany("INSERT INTO feedback VALUES (?, ?, ?)", rows)
except sqlite3.IntegrityError as e:
    print("rolled back:", e)
print("rows:", conn.execute("SELECT COUNT(*) FROM feedback").fetchone()[0])

with conn:
    conn.executemany("INSERT INTO feedback VALUES (?, ?, ?)", rows[:2])
print("rows:", conn.execute("SELECT COUNT(*) FROM feedback").fetchone()[0])

title: JSON 列：json_extract 和 json_each
lang: sql
dataset: clausecheck
--- body
样例数据里有两列存的是 JSON 文字：`reviews.rule_ids` 像 `'["PB-01", "PB-02"]'`，`tool_calls.args` 像 `'{"topic": "payment"}'`。SQLite 能直接读它们：

- `json_extract(args, '$.topic')`（或 `args ->> '$.topic'`）取出一个字段
- `json_array_length(rule_ids)`：数组有几个元素
- `json_each(rule_ids)` 把数组「炸开」成多行，每个元素一行，值在 `value` 列。它写在 FROM 里，用法像 JOIN 另一张表：`FROM reviews AS r, json_each(r.rule_ids) AS j`。BigQuery 里同样的事叫 `UNNEST`

什么时候不该用 JSON 列，而是拆成单独一张表（比如 `review_rules(review_id, rule_id)`，每个引用一行）？要按它**筛选、统计、JOIN**，要加**约束**（每个 rule_id 必须真的存在），要加**索引**。只是整块存、整块读的东西（模型的完整回复、工具参数），JSON 列就很合适。

下面把合同 101 每条审查引用的规则展开：1005 引用了两条规则，所以出现两次。
--- code
SELECT r.id, r.clause_id, j.value AS rule_id
FROM reviews AS r, json_each(r.rule_ids) AS j
WHERE r.contract_id = 101
ORDER BY r.id;

title: 生产环境：Postgres、pgvector 和索引
dataset: clausecheck
--- body
SQLite 是一个文件，适合单机、测试和小工具（项目的检查点就用它）。线上应用的数据库通常是 **Postgres**：很多服务同时读写、有权限和备份。今天的 SQL 在 Postgres 里几乎原样能用，区别是类型严格、外键总是检查、自增主键写 `GENERATED ALWAYS AS IDENTITY`、`LIKE` 区分大小写、JSON 用 `JSONB`、带时区的时间用 `TIMESTAMPTZ`。Python 里用 psycopg（占位符 `%s`）或 SQLAlchemy；TypeScript 里用 Prisma、Drizzle 或 node-postgres（占位符 `$1`）。

**pgvector** 是 Postgres 的扩展，能存 embedding，把第 11 天的 RAG 搬进数据库：

```sql
CREATE EXTENSION vector;
CREATE TABLE chunks (id BIGSERIAL PRIMARY KEY, text TEXT, embedding vector(1536));
CREATE INDEX ON chunks USING hnsw (embedding vector_cosine_ops);
SELECT id, text FROM chunks ORDER BY embedding <=> %s LIMIT 5;
```

`<=>` 是**余弦距离**（1 − 余弦相似度，越小越像）；1536 是 `text-embedding-3-small` 向量的长度。`%s` 传进去的是问题的 embedding：Python 里先装 `pgvector` 包，对连接调用一次 `register_vector(conn)`（`from pgvector.psycopg import register_vector`），psycopg 才认识向量类型（以 pgvector 文档为准）。

**索引**像书后面的目录：没有索引时按 `contract_id` 找要把整张表扫一遍（SCAN），有了索引就直接跳过去（SEARCH ... USING INDEX）。代价是写入稍慢、多占空间。`EXPLAIN QUERY PLAN`（Postgres 里是 `EXPLAIN`）告诉你数据库打算怎么查。
--- code
conn = fresh_db()
q = "SELECT id, verdict FROM reviews WHERE contract_id = ?"

def plan():
    return [row[3] for row in conn.execute("EXPLAIN QUERY PLAN " + q, (103,))]

print(plan())
conn.execute("CREATE INDEX idx_reviews_contract ON reviews (contract_id)")
print(plan())
print(conn.execute(q, (103,)).fetchall()[:3])

title: 复习：redline 多的合同
level: 2
lang: sql

--- prompt
复习第 22、23 天：找出 redline **至少 2 条**的合同。返回四列：`contract_id`、`title`、`customer`（客户名）、`redlines`（redline 条数），按 redlines 从多到少，同样多的按 contract_id 从小到大。
--- solution
SELECT c.id AS contract_id, c.title, cu.name AS customer, COUNT(*) AS redlines
FROM reviews AS r
JOIN contracts AS c ON c.id = r.contract_id
JOIN customers AS cu ON cu.id = c.customer_id
WHERE r.verdict = 'redline'
GROUP BY c.id, c.title, cu.name
HAVING COUNT(*) >= 2
ORDER BY redlines DESC, contract_id;
--- hints
- reviews → contracts → customers 两个 JOIN；先用 WHERE 只留下 redline 的行。
- 按合同分组（SELECT 里的非聚合列都放进 GROUP BY），「至少 2 条」是对分组的条件，写在 HAVING 里。
- 最后 `ORDER BY redlines DESC, contract_id`。

title: 约束挡住坏数据
level: 2
dataset: clausecheck
--- prompt
第 18 天的工作流里，律师要批准或驳回每一条 redline。把决定存进表 `approvals`：在字符串 `SCHEMA` 里写建表语句，要求：

- `id`：INTEGER，主键
- `review_id`：INTEGER，必填，外键指向 `reviews(id)`；**每条审查只能有一个决定**（UNIQUE）
- `decision`：TEXT，必填，只能是 `'approved'` 或 `'rejected'`
- `approver`：TEXT，必填
- `decided_at`：TEXT，必填，默认 `CURRENT_TIMESTAMP`

测试会在一个装好样例数据的新库里先执行 `PRAGMA foreign_keys = ON`，再执行你的 `SCHEMA`，然后插入一行好数据和各种坏数据：坏数据必须被数据库拒绝（抛出 `sqlite3.IntegrityError`）。起始代码的表能建出来，但什么都挡不住。
--- starter
SCHEMA = """
CREATE TABLE approvals (
  id INTEGER PRIMARY KEY,
  review_id INTEGER,
  decision TEXT,
  approver TEXT,
  decided_at TEXT
);
"""
--- solution
SCHEMA = """
CREATE TABLE approvals (
  id INTEGER PRIMARY KEY,
  review_id INTEGER NOT NULL UNIQUE REFERENCES reviews(id),
  decision TEXT NOT NULL CHECK (decision IN ('approved', 'rejected')),
  approver TEXT NOT NULL,
  decided_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP
);
"""
--- tests
import sqlite3
def _db():
    conn = fresh_db()
    conn.execute("PRAGMA foreign_keys = ON")
    conn.executescript(SCHEMA)
    return conn
def _ins(conn, review_id, decision, approver):
    conn.execute("INSERT INTO approvals (review_id, decision, approver) VALUES (?, ?, ?)", (review_id, decision, approver))
def _try(review_id, decision, approver, first=None):
    conn = _db()
    if first:
        _ins(conn, *first)
    try:
        _ins(conn, review_id, decision, approver)
    except sqlite3.IntegrityError:
        return "rejected"
    return "accepted"
def _good():
    conn = _db()
    _ins(conn, 1005, "approved", "anna")
    return conn.execute("SELECT review_id, decision, approver, decided_at IS NOT NULL FROM approvals").fetchall()
expect("好数据能插入，decided_at 自动填上", _good, [(1005, "approved", "anna", 1)])
expect("decision 不在允许的值里", lambda: _try(1005, "maybe", "anna"), "rejected")
expect("decision 是空的（CHECK 放过 NULL，要靠 NOT NULL）", lambda: _try(1005, None, "anna"), "rejected")
expect("approver 是空的（NULL）", lambda: _try(1005, "approved", None), "rejected")
expect("review_id 是空的（外键和 UNIQUE 都放过 NULL）", lambda: _try(None, "approved", "anna"), "rejected")
expect("同一条审查第二个决定", lambda: _try(1005, "rejected", "ben", first=(1005, "approved", "anna")), "rejected")
expect("review_id 在 reviews 里不存在（外键）", lambda: _try(9999, "approved", "anna"), "rejected")
expect("另一条审查的决定可以插入", lambda: _try(1022, "rejected", "ben", first=(1005, "approved", "anna")), "accepted")
--- hints

def search_reviews(conn, topic=None, risk=None, limit=20):
    if not isinstance(limit, int) or limit < 1:
        raise ValueError("limit must be a positive integer")
    where = []
    params = []
    if topic is not None:
        where.append("topic = ?")
        params.append(topic)
    if risk is not None:
        where.append("risk = ?")
        params.append(risk)
    sql = "SELECT id FROM reviews"
    if where:
        sql += " WHERE " + " AND ".join(where)
    sql += " ORDER BY id LIMIT ?"
    params.append(limit)
    return [row[0] for row in conn.execute(sql, params).fetchall()]
