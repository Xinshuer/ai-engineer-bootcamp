title: 数据仓库和 BigQuery
bq: yes
--- body
本页的 BigQuery 是模拟的：SQL 跑在浏览器里的 SQLite 上，模拟了几个 BigQuery 写法；Python 客户端的调用写法和返回结构与真 SDK（google-cloud-bigquery）一致（只实现了课程用到的部分）。真项目里 `pip install google-cloud-bigquery` 后配置凭证即可。

昨天的 SQLite / Postgres 是**业务数据库**（OLTP）：每次读写几行，要快、要有事务。Clause Check 上线后每条审查产生一行追踪数据，积累下来就是上亿行，负责人想看的是一张**看板**：每个客户每月花了多少钱、prompt 缓存命中率、延迟 p95、每个 prompt 版本的 redline 率和失败率。这种「扫一大片历史」的问题，是**数据仓库**（OLAP）的活。

BigQuery 是 Google Cloud 的数据仓库：

- **无服务器**：不用管机器，写 SQL 就行，按用量付费
- **列式存储**：每一列单独存，只读查询用到的列，所以扫几亿行也快
- 名字有三段：`项目.数据集.表`，比如 `clausecheck-dev.clausecheck.reviews`（本页的项目叫 clausecheck-dev，数据集叫 clausecheck）。写进 SQL 时，带项目的全名用反引号括起来，就像下面例子里的 FROM
- 它是给分析用的，不是应用的后台库：不适合频繁改单行
- 数据集建的时候要选**位置**（比如 `EU` 多区域，或 `europe-north1` 芬兰），建好以后改不了。追踪数据里可能有客户信息，按 GDPR 的习惯默认放在欧盟

AWS 对照：

- BigQuery ↔ Amazon Redshift（数据仓库）
- BigQuery 外部表（查 Cloud Storage 里的文件）↔ Amazon Athena（用 SQL 直接查 S3 里的文件）
--- code
SELECT model, COUNT(*) AS reviews, ROUND(SUM(cost_usd), 4) AS cost_usd
FROM `clausecheck-dev.clausecheck.reviews`
GROUP BY model
ORDER BY reviews DESC

title: 怎么收费：扫多少列、多少分区
lang: py
--- body
按需（on-demand）计费时，BigQuery 按查询**扫描的字节**收钱。官方价格页写的是每 TiB 6.25 美元、每月前 1 TiB 免费（价格会变，以官方价格页为准）。另一种是按容量（editions：按用了多少计算槽 slot、多少小时付费），用量大的团队常用，今天只讲按需。因为是列式存储：

- 扫描量 = 查询里**用到的每一列**的全部大小（SELECT、WHERE、JOIN、GROUP BY 里出现的都算），和返回几行无关。`SELECT *` 读所有列，最贵
- `LIMIT 10` **不会**少扫；在没分区、没聚簇的表上，`WHERE` 也不会
- 每个用到的表至少按 10 MB 算；报错的查询、命中缓存的查询不收钱。只想看看数据长什么样，用控制台里表的「预览」（免费）
- **分区表**：`PARTITION BY DATE(created_at)` 把表按天切块。WHERE 直接拿分区列和常量比较（`created_at >= TIMESTAMP('2026-09-01')`）时，只读那几天的分区。建表时在 `OPTIONS (require_partition_filter = TRUE)` 里打开这个开关，不带这种过滤的查询直接报错
- **聚簇**：`CLUSTER BY customer_id` 把同一客户的数据存在一起，按它过滤时能跳过很多块。省下多少要跑完才知道，所以聚簇表的 dry run 估算是个上限

分区和聚簇本页模拟不了，下面按一张假想的「一年 2 亿行」的表算算账。
--- code
TIB = 2 ** 40
PRICE_PER_TIB = 6.25                 # 示例价格，以官方价格页为准
ROWS = 200_000_000                   # 假想：上线一年，每条审查一行
BYTES_PER_ROW = {                    # 每列平均每行几个字节：数字和时间 8 个，文字约 2 + 长度
    "id": 8, "contract_id": 8, "clause_id": 6, "heading": 22, "topic": 15, "verdict": 8,
    "risk": 6, "model": 16, "prompt_version": 4, "prompt_tokens": 8, "completion_tokens": 8,
    "cache_hit_tokens": 8, "latency_ms": 8, "cost_usd": 8, "error": 2, "created_at": 8,
    "rationale": 400,                # 模型写的理由：最占地方的一列
}

def usd(columns, share_of_rows=1.0):
    scanned = ROWS * share_of_rows * sum(BYTES_PER_ROW[c] for c in columns)
    return scanned / TIB * PRICE_PER_TIB

runs_per_month = 12 * 24 * 30        # 看板每 5 分钟刷新一次
print(f"SELECT * ... LIMIT 10          ${usd(BYTES_PER_ROW):.3f} per run")
print(f"SELECT created_at, cost_usd    ${usd(['created_at', 'cost_usd']):.4f} per run")
print(f"  + 30 of 365 day partitions   ${usd(['created_at', 'cost_usd'], 30 / 365):.5f} per run")
print(f"dashboard with SELECT *        ${usd(BYTES_PER_ROW) * runs_per_month:,.0f} per month")
print(f"dashboard, 2 cols, partitions  ${usd(['created_at', 'cost_usd'], 30 / 365) * runs_per_month:,.2f} per month")

title: GoogleSQL 方言：表名、除法、COUNTIF
bq: yes
--- body
BigQuery 的 SQL 叫 GoogleSQL。前两天学的 SELECT、JOIN、CTE、窗口函数都照样能用。和 SQLite 不一样、今天常用的几处（本页模拟了它们，题目标着 BigQuery 写法时可以用）：

- 表名要带数据集：`clausecheck.reviews`；或者连项目一起写全名，用反引号（键盘左上角 Esc 下面那个键）括起来，像下面例子里的 FROM。只写 `reviews` 会报 missing dataset
- `/` 永远得到小数：`7 / 2 = 3.5`（SQLite 和 Postgres 里整数相除得 3）。要整数除法用 `DIV(7, 2)`
- `SAFE_DIVIDE(a, b)`：b 是 0 时得到 NULL，而不是报错。算比率（命中率、通过率）就用它
- `COUNTIF(条件)`：数满足条件的行，相当于 `SUM(CASE WHEN 条件 THEN 1 ELSE 0 END)`（一行都没有时 COUNTIF 得 0，SUM 得 NULL）
- `IF(条件, a, b)`：短一点的 CASE WHEN
- 类型名不一样：`CAST(x AS STRING)`、`INT64`、`FLOAT64`、`BOOL`

下面比较两个模型：大模型 v4-pro 平均输出的 token 是 flash 的三倍多，也慢得多。
--- code
SELECT
  model,
  COUNT(*) AS reviews,
  COUNTIF(verdict = 'flag') AS flags,
  ROUND(SAFE_DIVIDE(SUM(completion_tokens), COUNT(*)), 1) AS avg_output_tokens,
  IF(AVG(latency_ms) > 5000, 'slow', 'ok') AS speed,
  7 / 2 AS float_div,
  DIV(7, 2) AS int_div
FROM `clausecheck-dev.clausecheck.reviews`
GROUP BY model

title: 时间：DATE_TRUNC 和 TIMESTAMP_DIFF
bq: yes
--- body
BigQuery 里最常用的时间类型是 `DATE`（日期）和 `TIMESTAMP`（时刻，UTC）；另外还有不带时区的 `DATETIME` 和 `TIME`。本页的时间列存成文字，但下面这些函数按 BigQuery 的规则模拟了：

- `DATE(created_at)`：时刻 → 日期
- `DATE_TRUNC(日期, MONTH)`：截到月初（还有 WEEK、QUARTER、YEAR）。**值在前、单位在后**，单位是不带引号的关键字，和 Postgres 的 `date_trunc('month', ts)` 正好反过来。写成 `'MONTH'` 会报错
- 截断不改变类型：TIMESTAMP 截到月还是 TIMESTAMP（`2026-09-01 00:00:00`），所以「按月」通常写 `DATE_TRUNC(DATE(created_at), MONTH)`，得到 `2026-09-01`
- `WEEK` 从星期日算起（要从星期一算，真 BigQuery 里写 `ISOWEEK` 或 `WEEK(MONDAY)`，本页没有模拟）
- `TIMESTAMP_DIFF(晚, 早, SECOND)`：两个时刻差几个整秒（单位最大到 DAY；按 DAY 数的是满 24 小时的个数）。按日历算差几天、几个月，用 `DATE_DIFF(DATE(a), DATE(b), DAY)`（或 `MONTH`）

本页的小限制：列的别名别起成单独的时间单位词，比如 `month`、`week`、`day`、`hour`、`year`（模拟器可能把它当成单位，结果悄悄算错），用 `month_start` 这种名字。真 BigQuery 没有这个问题。

下面看两次评测各跑了多久：v1 和 v2 都在 3 分半钟左右跑完 24 次。
--- code
SELECT
  prompt_version,
  DATE(MIN(created_at)) AS run_date,
  DATE_TRUNC(DATE(MIN(created_at)), WEEK) AS week_start,
  TIMESTAMP_DIFF(MAX(created_at), MIN(created_at), SECOND) AS run_seconds,
  COUNT(*) AS runs
FROM clausecheck.evals
GROUP BY prompt_version
ORDER BY prompt_version

title: 本页跑不了的 BigQuery 写法
bq: yes
--- body
这几样在真 BigQuery 里天天用，本页模拟不了。要认得它们，面试时会写：

- `QUALIFY`：像 HAVING，但过滤的是窗口函数的结果。「每个条款最新的一条审查」一句就够：

```sql
SELECT contract_id, clause_id, verdict
FROM clausecheck.reviews
WHERE error IS NULL
QUALIFY ROW_NUMBER() OVER (PARTITION BY contract_id, clause_id ORDER BY created_at DESC) = 1
```

  本页的写法：把 ROW_NUMBER 放进 CTE，外面 `WHERE rn = 1`（第 23 天）
- `APPROX_QUANTILES(latency_ms, 100)[OFFSET(95)]`：近似的 p95。本页用窗口函数按 nearest-rank 算（第 13 天的算法），就是下面的例子
- `ARRAY_AGG(x)` 把一组值收成数组，`UNNEST(数组)` 把数组展开成多行（像昨天的 json_each），`STRUCT(a, b)` 把几个字段打包成一个
- `SELECT * EXCEPT (rationale)`：除了某几列都要（没选的列不扫，也就不收钱）
- 在仓库里做 AI：BigQuery ML 能在 SQL 里调用模型生成 embedding，`VECTOR_SEARCH` 在表里做向量相似度搜索（用法以官方文档为准）

例子里：`rn` 是排序后的名次，`n` 是这一组的行数。名次 ≥ 0.95 × n 的行里最小的延迟，正好是第 ceil(0.95 × n) 个，也就是 nearest-rank 的 p95。
--- code
WITH ranked AS (
  SELECT
    model,
    latency_ms,
    ROW_NUMBER() OVER (PARTITION BY model ORDER BY latency_ms) AS rn,
    COUNT(*) OVER (PARTITION BY model) AS n
  FROM clausecheck.reviews
)
SELECT
  model,
  MAX(n) AS n,
  MIN(IF(rn >= 0.95 * n, latency_ms, NULL)) AS p95_ms
FROM ranked
GROUP BY model
ORDER BY model

lang: py

--- body
Python 里用 `google-cloud-bigquery`：

```python
from google.cloud import bigquery
client = bigquery.Client()                    # 项目和凭证来自环境（第 26 天细讲）
config = bigquery.QueryJobConfig(
    query_parameters=[bigquery.ScalarQueryParameter("cid", "INT64", 103)],
    labels={"feature": "dashboard"},
)
job = client.query(sql, job_config=config)    # 提交一个查询任务
rows = list(job.result())                     # 等它跑完，拿到所有行
```

- SQL 里写 `@cid`，值用 `ScalarQueryParameter(名字, 类型, 值)` 传，类型写 `"STRING"`、`"INT64"`、`"FLOAT64"`、`"BOOL"`、`"DATE"`、`"TIMESTAMP"`。和昨天的 `?` 一个道理：**永远不要用 f-string 拼值**。表名、列名同样不能用参数
- 行可以用 `row["verdict"]`、`row.verdict`、`row[0]` 取值，`dict(row.items())` 变成字典。INT64 → int，FLOAT64 → float，TIMESTAMP → 带时区（UTC）的 `datetime`
- `job.result()` 只能遍历**一次**，要用两次就先 `list(...)`
- SQL 写错、表不存在：错误在 `job.result()` 时才抛出，不是在 `client.query()` 时
- `labels` 给查询贴标签，账单里就能按功能分摊成本
- 真 SDK 里 `job.result().to_dataframe()` 能直接变成 pandas 表（本页没有 pandas）
--- code
from google.cloud import bigquery

client = bigquery.Client()
sql = """
SELECT id, clause_id, verdict, created_at
FROM clausecheck.reviews
WHERE contract_id = @cid AND risk = @risk
ORDER BY id
"""
config = bigquery.QueryJobConfig(query_parameters=[
    bigquery.ScalarQueryParameter("cid", "INT64", 103),
    bigquery.ScalarQueryParameter("risk", "STRING", "high"),
])
job = client.query(sql, job_config=config)
rows = list(job.result())
for row in rows:
    print(row["id"], row.clause_id, row[2], row.created_at.isoformat())
print(dict(rows[0].items()))

bad = client.query("SELECT verdict FROM reviews")      # 忘了写数据集
print("client.query() did not raise")
try:
    bad.result()
except Exception as e:
    print(type(e).__name__, e)

title: dry run、字节上限和缓存
lang: py
cloud: yes
dataset: clausecheck
--- body
花钱之前先算：

- **dry run**（空跑）：`QueryJobConfig(dry_run=True)`。BigQuery 只检查 SQL、估算扫描量，不真跑，**不收钱**。读 `job.total_bytes_processed`。SQL 有错时 `client.query()` 当场就报错。官方的 Python 示例写的是 `QueryJobConfig(dry_run=True, use_query_cache=False)`：估算时不看缓存
- **字节上限**：`QueryJobConfig(maximum_bytes_billed=字节数)`。预计计费字节超过上限，查询直接失败，不收钱。因为每个表至少按 10 MB（10485760 字节）计费，上限低于它时，任何读表的查询都会失败
- 超限的错误原因（reason）是 `bytesBilledLimitExceeded`。用 `client.query()` + `result()` 时，SDK 的错误对照表里没有这个原因，就报成 500 `InternalServerError`，**不是** `BadRequest`；换一种调用方式，类型可能又不一样。所以要接住它们共同的父类 `GoogleAPICallError`，再看 `e.errors[0]["reason"]`
- **缓存**：一模一样的查询（连空格都一样）24 小时内再跑一次，只要表没变过，结果直接来自缓存（`job.cache_hit` 是 True），计费 0 字节。表刚被流式写入过、用了 `CURRENT_TIMESTAMP()` 这类每次都变的函数时，不走缓存

下面：三条查询的扫描量（注意 LIMIT 那条）；一个过低的上限；同一条查询跑两次。
--- code
from google.cloud import bigquery
from google.api_core.exceptions import GoogleAPICallError

client = bigquery.Client()
for sql in [
    "SELECT * FROM clausecheck.reviews",
    "SELECT verdict, cost_usd FROM clausecheck.reviews",
    "SELECT verdict, cost_usd FROM clausecheck.reviews LIMIT 1",
]:
    job = client.query(sql, job_config=bigquery.QueryJobConfig(dry_run=True, use_query_cache=False))
    print(f"{job.total_bytes_processed:>5} bytes  {sql}")

limited = bigquery.QueryJobConfig(maximum_bytes_billed=5_000_000)
try:
    client.query("SELECT verdict FROM clausecheck.reviews", job_config=limited).result()
except GoogleAPICallError as e:
    print(type(e).__name__, e.errors[0]["reason"])

first = client.query("SELECT COUNT(*) AS n FROM clausecheck.evals")
first.result()
again = client.query("SELECT COUNT(*) AS n FROM clausecheck.evals")
print("cache hit:", first.cache_hit, again.cache_hit, "| billed:", first.total_bytes_billed, again.total_bytes_billed)

title: 写入：流式和批量
lang: py
cloud: yes
dataset: clausecheck
--- body
追踪数据怎么进 BigQuery？两种方式：

- **流式写入** `client.insert_rows_json(表名, 行的列表)`：写进去几秒内就能查到，按写入量收费（官方价格页：每 200 MiB 0.01 美元，每行至少按 1 KB 算；以官方为准）。适合 worker 每审完一条就写一行。它用的是老的 insertAll（REST）接口，写起来最简单；新项目 Google 推荐走 gRPC 的 Storage Write API，更便宜
- **批量加载**：先把一批数据写成文件放进 Cloud Storage，再用 load job 导入。加载本身不收费，适合大批量、不着急的数据

行的数据有问题时，`insert_rows_json` **不抛异常，而是返回错误列表**，一定要检查：成功是 `[]`；失败时每项是 `{"index": 第几行, "errors": [...]}`。（表不存在、没权限这类整个请求的错误，才会抛异常。）默认**一行坏，整批都不写**：坏行的 reason 是 `invalid`，其他行是 `stopped`，可以原样重发。`skip_invalid_rows=True` 让好行直接写进去。

BigQuery 不会替你挡住重复行：表上可以声明主键，但不强制执行（只给查询优化用）。同一行发两次，通常就存成两行（`row_ids` 参数只能尽力去重）。所以看板查询常要自己去重，比如用 QUALIFY 取每组最新的一条。注意：本页的模拟把 `id` 当成主键，同一个 id 发两次只留一行，这一点和真 BigQuery 不一样。
--- code
from google.cloud import bigquery

client = bigquery.Client()
TABLE = "clausecheck-dev.clausecheck.reviews"
row = {
    "id": 1066, "contract_id": 110, "clause_id": "9.1", "heading": "Warranties", "topic": "warranty",
    "verdict": "accept", "risk": "low", "rule_ids": '["PB-00"]', "model": "deepseek-flash",
    "prompt_version": "v2", "prompt_tokens": 2104, "completion_tokens": 151, "cache_hit_tokens": 1650,
    "latency_ms": 2210, "cost_usd": 0.000327, "created_at": "2026-09-23 10:00:00",
}
bad = dict(row, id=1067, prompt_tokens="many")

errors = client.insert_rows_json(TABLE, [row, bad])
for e in errors:
    print(e["index"], e["errors"][0]["reason"], e["errors"][0]["message"])
print(client.insert_rows_json(TABLE, [row]))
n = list(client.query("SELECT COUNT(*) AS n FROM clausecheck.reviews").result())[0]["n"]
print("rows now:", n)

title: 复习：每个模型最慢的两条
level: 2
ordered: yes
cards: d23:窗口函数：每行都留下; d23:CTE：用 WITH 给每一步起名字
--- context
排查延迟问题时，常先把每种模型最慢的几次审查挑出来，看它们审的是哪些条款、有没有共同点。
--- prompt
复习第 23 天的窗口函数（这题用普通 SQLite 写法，表名不用带数据集）：找出每个模型延迟最高的**两条**审查。返回四列：`model`、`id`、`clause_id`、`latency_ms`，按 model 排序，同一个模型里按 latency_ms 从高到低。用 `ROW_NUMBER()`。
--- solution
WITH ranked AS (
  SELECT model, id, clause_id, latency_ms,
         ROW_NUMBER() OVER (PARTITION BY model ORDER BY latency_ms DESC) AS rn
  FROM reviews
)
SELECT model, id, clause_id, latency_ms
FROM ranked
WHERE rn <= 2
ORDER BY model, latency_ms DESC;
--- hints
- 在 CTE 里给每一行编号：`ROW_NUMBER() OVER (PARTITION BY model ORDER BY latency_ms DESC) AS rn`。
- 外面的查询只留 `rn <= 2` 的行。窗口函数的结果不能直接写在同一层的 WHERE 里，所以要套一层 CTE。
- 最后 `ORDER BY model, latency_ms DESC`。

--- context
假设 Clause Check 上线后，审查记录都放进 BigQuery（Google Cloud 的数据仓库）。在 SQLite 里写好的查询搬过去，常会因为方言（各家 SQL 写法上的小差别）而报错。
--- prompt
这条查询统计「已完成（status = 'reviewed'）的合同」里每种判定有几条成功的审查。它在 SQLite 里好好的，搬到 BigQuery 就报错。运行，读报错，修好它。结果两列：`verdict`、`n`，按 n 从多到少。
--- starter
SELECT r.verdict, COUNT(*) AS n
FROM reviews AS r
JOIN contracts AS c ON c.id = r.contract_id
WHERE c.status = 'reviewed' AND r.error IS NULL
GROUP BY r.verdict
ORDER BY n DESC, r.verdict;
--- solution
SELECT r.verdict, COUNT(*) AS n
FROM clausecheck.reviews AS r

延迟不能只看平均（第 13 天）。按 prompt_version 算延迟的 p50 和 p95，用 nearest-rank：排序后的第 ceil(p × n) 个。返回五列：`prompt_version`、`n`（条数）、`p50_ms`、`p95_ms`、`avg_ms`（`ROUND(AVG(latency_ms))`），按 prompt_version 排序。

真 BigQuery 里会写 `APPROX_QUANTILES(latency_ms, 100)[OFFSET(95)]`；本页用知识卡片里的窗口函数写法。看结果：v1 的 p95 为什么比 v2 高那么多？
--- solution
WITH ranked AS (
  SELECT
    prompt_version,
    latency_ms,
    ROW_NUMBER() OVER (PARTITION BY prompt_version ORDER BY latency_ms) AS rn,
    COUNT(*) OVER (PARTITION BY prompt_version) AS n
  FROM clausecheck.reviews
)
SELECT
  prompt_version,
  MAX(n) AS n,
  MIN(IF(rn >= 0.5 * n, latency_ms, NULL)) AS p50_ms,
  MIN(IF(rn >= 0.95 * n, latency_ms, NULL)) AS p95_ms,
  ROUND(AVG(latency_ms)) AS avg_ms
FROM ranked
GROUP BY prompt_version
ORDER BY prompt_version;
--- hints
- 照着知识卡片「本页跑不了的 BigQuery 写法」里的例子，把 `PARTITION BY model` 换成 `PARTITION BY prompt_version`。
- p50 和 p95 是同一个套路：`MIN(IF(rn >= 0.5 * n, latency_ms, NULL))`，把 0.5 换成 0.95 就是 p95。

from google.cloud import bigquery
from google.api_core.exceptions import GoogleAPICallError

def safe_query(client, sql, max_bytes):
    config = bigquery.QueryJobConfig(maximum_bytes_billed=max_bytes)
    job = client.query(sql, job_config=config)
    try:
        rows = job.result()
    except GoogleAPICallError as e:
        if e.errors and e.errors[0].get("reason") == "bytesBilledLimitExceeded":
            return None
        raise
    return [dict(row.items()) for row in rows]

from google.cloud import bigquery

TABLE = "clausecheck-dev.clausecheck.reviews"

def stream_reviews(client, rows):
    if not rows:
        return {"inserted": 0, "bad": []}
    errors = client.insert_rows_json(TABLE, rows)
    if not errors:
        return {"inserted": len(rows), "bad": []}
    bad = sorted(e["index"] for e in errors if any(x["reason"] == "invalid" for x in e["errors"]))
    retry = [row for i, row in enumerate(rows) if i not in bad]
    if retry:
        again = client.insert_rows_json(TABLE, retry)
        if again:
            raise RuntimeError(f"retry failed: {again}")
    return {"inserted": len(retry), "bad": bad}

from google.cloud import bigquery

def guarded_query(client, sql, params, max_usd, usd_per_tib=6.25):
    qp = [bigquery.ScalarQueryParameter(name, type_, value) for name, (type_, value) in params.items()]
    dry = client.query(sql, job_config=bigquery.QueryJobConfig(query_parameters=qp, dry_run=True, use_query_cache=False))
    usd = dry.total_bytes_processed / 2**40 * usd_per_tib
    if usd > max_usd:
        raise ValueError(f"query would cost {usd:.8f} USD, limit {max_usd}")
    job = client.query(sql, job_config=bigquery.QueryJobConfig(query_parameters=qp))
    return [dict(row.items()) for row in job.result()]
