@@ concept
title: JOIN：把几张表连起来
--- body
表之间靠「键」连起来：`reviews.contract_id` 指向 `contracts.id`，`contracts.customer_id` 指向 `customers.id`。`JOIN ... ON ...` 把两张表里键对得上的行拼成一行，就像 Python 里拿 id 去字典里查：`contracts_by_id[review["contract_id"]]`。

- 给表起短别名：`FROM reviews r JOIN contracts c`，之后写 `r.clause_id`、`c.title`
- 两张表都有 `id` 列，只写 `id` 会报 `ambiguous column name`：前面加上别名
- `ON` 写两张表**怎么对上**，`WHERE` 写**要哪些行**。对 JOIN 来说写在哪里结果一样，但分开写更清楚（LEFT JOIN 就不一样了，见下一张卡片）
- `JOIN` 就是 `INNER JOIN`：两边都对得上的行才留下
- 连三张表就写两个 JOIN，每个 JOIN 都有自己的 ON
--- code
SELECT r.id, c.title, r.clause_id, r.verdict, r.model
FROM reviews r
JOIN contracts c ON c.id = r.contract_id
WHERE r.clause_id = '8.1';

@@ concept
title: LEFT JOIN：没有对上的也留下
--- body
客户 6（Amsterdam Data BV，8 月 30 日刚注册）还没有合同。`customers JOIN contracts` 之后，它就消失了。**LEFT JOIN** 保留左边表的每一行，右边对不上的列都填 NULL。

- 数「每个客户几份合同」要写 `COUNT(c.id)`：没有合同的客户也有一行（右边全是 NULL），`COUNT(*)` 会把它数成 1
- 经典 bug：右边表的条件写在 WHERE 里，比如 `WHERE c.status = 'reviewed'`。没有合同的那一行 `c.status` 是 NULL，被 WHERE 丢掉，LEFT JOIN 悄悄变成了 JOIN
- 正确的写法：**右边表的条件写进 ON**：`LEFT JOIN contracts c ON c.customer_id = cu.id AND c.status = 'reviewed'`

运行下面的例子，看最后一行：客户还在，合同的列都是 NULL。
--- code
SELECT cu.name, c.id AS contract_id, c.title, c.status
FROM customers cu
LEFT JOIN contracts c ON c.customer_id = cu.id
ORDER BY cu.id, c.id;

@@ concept
title: JOIN 放大：总数为什么翻倍了
--- body
一份合同有很多条审查。`contracts JOIN reviews` 之后，合同的每一列都被**复制**到它的每一条审查上：合同 101 有 12 条审查，它的 `pages`（12 页）就出现了 12 次，`SUM(c.pages)` 算出来是 144，而不是 12。

解决办法：**先聚合，再 JOIN**。先把 reviews 汇总成「每份合同一行」，写在括号里当成一张临时的表（起个别名，后面才好用 `rs.contract_id` 引用它），再和合同 JOIN。两边都是每份合同一行，就不会放大：

```sql
JOIN (SELECT contract_id, COUNT(*) AS n
      FROM reviews
      GROUP BY contract_id) rs ON rs.contract_id = c.id
```

面试里被问「这个总数为什么翻倍了」，第一反应就应该是：JOIN 把行放大了。
--- code
SELECT c.id,
       c.pages,
       COUNT(*) AS rows_after_join,
       SUM(c.pages) AS wrong_pages
FROM contracts c
JOIN reviews r ON r.contract_id = c.id
GROUP BY c.id, c.pages
ORDER BY c.id;

@@ concept
title: 子查询：IN、EXISTS、一个数
--- body
查询里面还可以放查询（写在括号里），叫**子查询**：

- `WHERE id IN (SELECT contract_id FROM reviews WHERE model = 'deepseek-v4-pro')`：先算出一组值，再看在不在里面
- `WHERE EXISTS (SELECT 1 FROM ... WHERE ... = 外层的列)`：只问「有没有」，找到一行就够了；`NOT EXISTS` 找「一条都没有」的
- **标量子查询**：只返回一个值的子查询可以当成一个数来用，比如算占总数的百分比：`SUM(cost_usd) / (SELECT SUM(cost_usd) FROM reviews)`
- 坑：`NOT IN (子查询)` 里只要出现一个 NULL，就一行也不返回（昨天的 NULL 规则）。找「没有」时用 `NOT EXISTS` 更安全
--- code
SELECT topic,
       ROUND(SUM(cost_usd), 6) AS cost,
       ROUND(100.0 * SUM(cost_usd) / (SELECT SUM(cost_usd) FROM reviews), 1) AS pct_of_total
FROM reviews
GROUP BY topic
ORDER BY cost DESC;

@@ concept
title: CTE：用 WITH 给每一步起名字
--- body
查询一长，括号套括号就没法读了。`WITH` 给每一步起个名字，从上往下读，像在 Python 里先算好几个中间变量：

```sql
WITH per_contract AS (
  SELECT contract_id, COUNT(*) AS reviews
  FROM reviews
  GROUP BY contract_id
)
SELECT ... FROM per_contract p JOIN contracts c ON c.id = p.contract_id
```

- 可以写好几个，用逗号隔开：`WITH a AS (...), b AS (...)`，后面的可以用前面的
- CTE 里算出来的列（比如 `reviews`）在外层就是普通的列，可以直接放进 WHERE
- 它和「JOIN 放大」那张卡片里写在 FROM / JOIN 后面括号里、起了别名的子查询是一回事，只是有名字、写在最前面。Postgres、BigQuery、SQLite 都支持，面试写长查询时首选

下面的例子是 CTE 最典型的用法：两种不同的统计，先各自聚合成「每份合同一行」，再 JOIN 到一起（直接把三张表连起来再数，又会放大）。
--- code
WITH review_stats AS (
  SELECT contract_id, COUNT(*) AS reviews
  FROM reviews
  GROUP BY contract_id
),
tool_stats AS (
  SELECT r.contract_id, COUNT(*) AS tool_calls
  FROM tool_calls t
  JOIN reviews r ON r.id = t.review_id
  GROUP BY r.contract_id
)
SELECT rs.contract_id, rs.reviews, COALESCE(ts.tool_calls, 0) AS tool_calls
FROM review_stats rs
LEFT JOIN tool_stats ts ON ts.contract_id = rs.contract_id
ORDER BY rs.contract_id;

@@ concept
title: 窗口函数：每行都留下
--- body
GROUP BY 把一组行**压成一行**；窗口函数**每一行都留下**，只是在每行旁边多算一列「这一行在它那组里的情况」：

```sql
ROW_NUMBER() OVER (PARTITION BY contract_id ORDER BY cost_usd DESC)
```

- `PARTITION BY`：按什么分组（不写就是整张表一组）；`ORDER BY`：组内怎么排
- `ROW_NUMBER()`：1、2、3、4，并列也硬分先后
- `RANK()`：并列的名次相同，后面跳号：1、2、2、4
- `DENSE_RANK()`：并列的名次相同，不跳号：1、2、2、3
- 聚合函数也能加 OVER：`SUM(cost_usd) OVER (PARTITION BY contract_id)` 是整份合同的总费用，放在每一行旁边

窗口函数在 SELECT 这一步才算，所以**不能写在 WHERE 里**（WHERE 更早执行）。要按它筛选，先把它放进 CTE。
--- code
SELECT contract_id, clause_id, cost_usd,
       ROW_NUMBER() OVER (PARTITION BY contract_id ORDER BY cost_usd DESC) AS rn,
       ROUND(cost_usd / SUM(cost_usd) OVER (PARTITION BY contract_id), 2) AS share_of_contract
FROM reviews
WHERE contract_id IN (104, 108)
ORDER BY contract_id, rn;

@@ concept
title: 每组最新一条
--- body
合同 103 的 8.1 审查了两次：8 月 12 日用 v1 prompt 判了 redline，9 月 18 日换成 v2 又跑了一次，判 flag。合同 109 的 8.1 第一次 429 失败了，后来重跑成功。做报表时，每个条款只该算**最新**的那一次。

「每组取最新 / 最大的一条」是面试高频题，套路是两步：

1. CTE 里给每组从新到旧编号：`ROW_NUMBER() OVER (PARTITION BY contract_id, clause_id ORDER BY created_at DESC) AS rn`
2. 外层 `WHERE rn = 1`

只用 `GROUP BY` + `MAX(created_at)` 只能拿到最新的时间，要拿那一行的 verdict 还得再 JOIN 回原表；ROW_NUMBER 一步就能做到。注意：SQLite 有个特殊规则，`SELECT clause_id, verdict, MAX(created_at) ... GROUP BY clause_id` 里没分组的 `verdict` 会取到时间最大的那一行，在本页能跑出对的结果；可在 Postgres 和 BigQuery 里这是错误写法，会直接报错。别这么写。

BigQuery 有更短的 `QUALIFY`，本页跑不了（SQLite 不支持），认得就行（示意）：

```sql
SELECT clause_id, verdict
FROM `clausecheck.reviews`
WHERE contract_id = 103
QUALIFY ROW_NUMBER() OVER (PARTITION BY clause_id ORDER BY created_at DESC) = 1
```
--- code
WITH ranked AS (
  SELECT id, contract_id, clause_id, verdict, prompt_version, created_at,
         ROW_NUMBER() OVER (PARTITION BY contract_id, clause_id
                            ORDER BY created_at DESC) AS rn
  FROM reviews
  WHERE clause_id = '8.1'
)
SELECT *
FROM ranked
ORDER BY contract_id, rn;
-- 在 ORDER BY 那一行前面加上 WHERE rn = 1 再运行

@@ concept
title: LAG 和累计
--- body
- `LAG(latency_ms) OVER (ORDER BY created_at)`：**上一行**的值（第一行没有上一行，是 NULL）；`LEAD` 取下一行。用来算「和上一次比变了多少」
- `SUM(cost_usd) OVER (ORDER BY created_at)`：从第一行一直加到当前这一行，就是**累计**（running total）。小细节：排序值一样的几行（比如同一秒的两条）会一起加进去，拿到同一个累计值
- 加上 `PARTITION BY contract_id`，就在每份合同里面各算各的

按天、按月汇总时，先把时间变成日期：SQLite 用 `date(created_at)` 得到 `'2026-09-05'`，用 `strftime('%Y-%m', created_at)` 得到 `'2026-09'`。Postgres 写 `created_at::date`、`date_trunc('month', created_at)`；BigQuery 写 `DATE(created_at)`、`DATE_TRUNC(DATE(created_at), MONTH)`（第 25 天）。
--- code
SELECT id, clause_id, model, latency_ms,
       LAG(latency_ms) OVER (ORDER BY created_at) AS prev_ms,
       latency_ms - LAG(latency_ms) OVER (ORDER BY created_at) AS change_ms,
       ROUND(SUM(cost_usd) OVER (ORDER BY created_at), 6) AS running_cost
FROM reviews
WHERE contract_id = 103
ORDER BY created_at;

--- prompt
复习昨天的 GROUP BY 和 HAVING，顺便认识 `evals` 表：每一行是一个评测用例（`case_id`）用某个 prompt 版本（`prompt_version`）跑一次，`run` 是第几次，`passed` 是 1（通过）或 0。

找出「不稳定」的组合：同一个用例、同一个版本跑的几次里，**没有全部通过**的。三列：`case_id`、`prompt_version`、`passes`（通过了几次），按 `case_id`、`prompt_version` 排序。
--- solution
SELECT case_id, prompt_version, SUM(passed) AS passes
FROM evals
GROUP BY case_id, prompt_version
HAVING SUM(passed) < COUNT(*)
ORDER BY case_id, prompt_version;
--- hints
- 按两列分组：`GROUP BY case_id, prompt_version`。

@@ item d23-04
type: sql
title: 工具读了哪一条
level: 2
ordered: yes
cards: JOIN：把几张表连起来; d22:WHERE：挑出需要的行
--- context
审查时模型会调用工具，比如用 `get_clause` 读同一份合同里被引用的另一条条款。每次调用都记在 `tool_calls` 表里；排查模型的行为时，要把调用和它所在的那次审查放在一起看。
--- prompt
`tool_calls` 记录了每次审查调用的工具，参数 `args` 是一段 JSON 文字，比如 `'{"clause_id": "12"}'`。SQLite 用 `json_extract(args, '$.clause_id')` 取出里面的值（BigQuery 写 `JSON_VALUE(args, '$.clause_id')`，第 24 天再细讲 JSON 列）。

列出所有 `get_clause` 调用，四列：`review_id`、`clause_id`（被审查的条款，来自 `reviews`）、`requested`（模型想读的条款，来自 `args`）、`ok`。按 `review_id` 排序。

做完看看：失败的那一次，模型想读的是哪一条？这份合同里有这一条吗？
--- solution
SELECT t.review_id,
       r.clause_id,
       json_extract(t.args, '$.clause_id') AS requested,
       t.ok
FROM tool_calls t
JOIN reviews r ON r.id = t.review_id
WHERE t.tool = 'get_clause'
ORDER BY t.review_id;
--- hints
- 每次工具调用属于一次审查：`JOIN reviews r ON r.id = t.review_id`。
- `json_extract(t.args, '$.clause_id') AS requested`，再加 `WHERE t.tool = 'get_clause'`。
- 失败的那次（`ok` 是 0）要读第 99 条：工具没找到它，合同 103 审查过的条款最大才到 15.4，这多半是模型编出来的交叉引用。项目 `tools.py` 的 `get_clause` 这时返回 `NOT_FOUND` 和已有的条款编号，而不是编一段内容给模型，这正是第 17 天说的「错误是写给模型看的」。

--- context
月报要列出每个客户有几份合同，刚注册、还没上传合同的客户（Amsterdam Data BV）也在客户表里。写这种统计之前，先弄清查询对这样的客户会给出什么。
--- prompt
客户 6 Amsterdam Data BV 还没有任何合同。下面这条查询里，它那一行的 `n` 是多少？如果把 `LEFT JOIN` 换成 `JOIN` 呢？
--- code
SELECT cu.name, COUNT(*) AS n
FROM customers cu
LEFT JOIN contracts c ON c.customer_id = cu.id
GROUP BY cu.id, cu.name;
--- options
- LEFT JOIN 时 `n` 是 1；换成 JOIN，这一行不出现
- LEFT JOIN 时 `n` 是 0；换成 JOIN，`n` 还是 0
- LEFT JOIN 时 `n` 是 NULL；换成 JOIN，这一行不出现
- 两种写法 `n` 都是 1
answer: 1
--- explain
LEFT JOIN 保留了这位客户，右边的列全是 NULL，但这仍然是**一行**，`COUNT(*)` 数行，所以是 1。要写 `COUNT(c.id)`（只数不是 NULL 的）才会得到 0。JOIN 只留两边都对得上的行，没有合同的客户整行消失。而报表里「0 份合同的客户」往往最值得关注：刚注册、还没用起来。
